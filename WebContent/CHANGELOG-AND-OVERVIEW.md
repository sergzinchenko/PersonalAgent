Документ собран по итогам цикла ревью и доработок. Первая часть — что было
изменено и почему, вторая — актуальное состояние проекта на текущий момент.

# Часть I. Журнал доработок

## Цикл 1. Аудит и критические исправления

Первичный разбор кода выявил проблемы, из которых три были отнесены к
критическим и исправлены сразу.

### XSS через рендерер markdown

`renderMarkdown()` собирал HTML регулярками поверх сырого текста и **не
экранировал ничего**, а результат вставлялся через `innerHTML`. Содержимое
ответа модели полностью контролируется LLM-провайдером (адрес которого
пользователь вписывает сам), поэтому конструкция вида `<img src=x
onerror=...>` в ответе исполнялась бы в контексте страницы — там, где лежат
ключи API и вся история переписки.

Исправлено: текст экранируется **первым шагом**, разметка применяется уже к
безопасной строке. Отдельно блокируются схемы `javascript:`, `data:`,
`vbscript:` в ссылках — экранирование спецсимволов их не нейтрализует.

### Бесконечная рекурсия tool-calling

Цепочка вызовов инструментов рекурсивно вызывала `_generateResponse()` без
счётчика. Зацикливание модели на инструментах (обычное дело для локальных и
слабых моделей) означало исчерпание стека и неограниченный расход токенов.

Исправлено: счётчик глубины с лимитом и понятной остановкой. Позже развёрнуто
в полноценную систему ограничений (цикл 4).

### Автоматическая активация инструментов, созданных моделью

`create_tool` включал новый инструмент сразу (`enabled: params.enabled !== false`),
а `handlerCode` исполнялся через `new Function` без песочницы. В сочетании с
`http_fetch` это давало прямой путь: враждебный текст со стороннего сайта →
prompt injection → модель создаёт инструмент, читающий ключи из IndexedDB и
отправляющий их наружу → инструмент немедленно вызывается.

Исправлено:
- новый инструмент **всегда** сохраняется выключенным, независимо от запроса модели;
- убран «сухой прогон» — раньше непроверенный код исполнялся уже при создании;
- `update_tool` при смене `handlerCode` принудительно выключает инструмент, даже
  если в том же вызове передан `enabled: true`;
- описания инструментов переписаны так, чтобы модель сообщала пользователю о
  необходимости включить инструмент вручную.

## Цикл 2. Безопасность и чистка

- **SSRF в `http_fetch`.** Разрешены только `http`/`https`; заблокированы
  `localhost`, приватные подсети (`10.x`, `172.16–31.x`, `192.168.x`), loopback
  и link-local, включая cloud-metadata `169.254.169.254`.
- **Логирование под флагом.** Полное содержимое запросов, ответов и аргументов
  инструментов писалось в консоль безусловно. Вынесено под `debug`, по
  умолчанию выключено.
- **MCP-инструменты переживают перезагрузку.** Обработчики жили только в
  памяти, после `F5` вызовы падали с «No handler registered». Добавлено
  восстановление при старте.
- **Убрано дублирование.** Логика папок существовала в трёх копиях; операции
  сведены к `FoldersEngine`. Удалён мёртвый код (`_renderHierarchy` и
  закомментированные старые версии методов — сотни строк).
- **Порядок скриптов.** `folders-engine.js` подключался последним, а
  использовался раньше — работало лишь по случайности тайминга.

## Цикл 3. Шифрование секретов

Ключи API и токены MCP хранились в IndexedDB открытым текстом.

Добавлен `SecretsVault` (AES-GCM-256, ключ **non-extractable** — его нельзя
выгрузить в сырые байты даже кодом страницы). Предусмотрена обратная
совместимость: ранее сохранённые значения читаются как есть и перешифровываются
при следующем сохранении.

Границы защиты зафиксированы прямо в коде: она закрывает просмотр базы через
DevTools, расширения и бэкапы профиля, но **не защищает от XSS в том же
источнике** — код на странице может вызвать расшифровку так же, как это делает
приложение. Радикальное решение — серверный прокси, чтобы секреты вообще не
попадали в браузер.

## Цикл 4. Управление настройками

- Окно настроек разделено на **вкладки** вместо одной длинной формы.
- Добавлены **ограничения работы агента**: итерации, бюджет времени на ответ
  (через `AbortController`), таймаут одного инструмента, потолок вызовов за ход.
- Добавлена **настраиваемая детализация** вывода вызовов инструментов.
- **Журналирование** получило переключатели в интерфейсе; выбор сохраняется
  между сессиями (раньше — только через консоль, сбрасывалось на `F5`).

## Цикл 5. Чат и перенос данных

- **Голосовой ввод** (Web Speech API) с обработкой типовых ошибок и честным
  сообщением, если браузер не поддерживает.
- **Быстрый выбор модели** в панели чата.
- **Счётчик токенов и статистика инструментов**, хранящиеся в отдельном store
  `chat_stats`.
- **Экспорт/импорт с паролем**: PBKDF2-SHA256 (250 000 итераций) → AES-GCM-256.

## Цикл 6. Исправления по замечаниям

- **Статистика токенов не менялась.** Причина: большинство провайдеров
  игнорируют `stream_options` и не присылают `usage` при стриминге. Добавлена
  локальная оценка по объёму текста, помеченная знаком `≈`, плюс живое
  обновление панели после каждого запроса и вызова.
- **Выход блока за рамку.** Длинные JSON и URL не переносятся сами; добавлены
  `overflow-wrap: anywhere` и `min-width: 0` (обязателен для flex-элементов).
- **Прокрутка в окне настроек.** Введён широкий режим модалки и двухколоночная
  сетка.

## Цикл 7. Ошибка `await is only valid in async functions`

Код инструментов компилировался через `new Function`, создающий **синхронную**
функцию, тогда как системный промпт обещал модели поддержку `async`. Модель
писала `await fetch(...)`, получала синтаксическую ошибку, затем пыталась
обойти её через async IIFE — и цикл повторялся.

Исправлено: компиляция через `AsyncFunction`, тело `handlerCode` теперь
является телом async-функции, `await` работает напрямую. Инструкции для модели
приведены в соответствие с фактическим поведением.

Одновременно исправлены **дубли папок при импорте**: сопоставление шло только
по `id`, а у одной и той же по смыслу папки на другой машине `id` другой.
Добавлено сопоставление по имени в пределах уровня с перемаппингом `parentId`.
Импорт стал идемпотентным.

## Цикл 8. Контекст, прерывание, выборочный экспорт

- **Кнопка прерывания агента** — обрывает HTTP-запрос и останавливает цепочку
  между шагами.
- **Размер контекста** последнего запроса рядом со счётчиком токенов.
- **Окно контекста модели** — таблица известных семейств плюс ручная настройка
  (API почти никогда не сообщает `context_length`).
- **Предупреждения** при достижении порога и при исчерпании контекста — с
  предложением создать новый чат.
- **Выборочный экспорт** с отметкой конкретных объектов и учётом текущей папки.

## Цикл 9. Финальные исправления и реинжиниринг

- **Импорт отдельной кнопкой** в каждой панели; полное окно из настроек убрано.
- **Кнопка останова скрывается** сразу после нажатия.
- **Копирование кода** из чата с запасным путём для незащищённого контекста.
  Попутно исправлен давний баг рендерера: замена `\n → <br>` применялась внутри
  `<pre>`, из-за чего в коде двоились переносы, а `*` и `#` превращались в разметку.
- **Новые инструменты** `export_chat` и `search_chats`.
- **Разбиение `ui.js`** (2400 строк) на семь модулей.

### Об исправленных регрессиях

Две правки в этом цикле чинили последствия предыдущих:

- добавленный ранее `overflow-x: auto` попал в общий класс блока вызова
  инструмента и включил ненужную прокрутку в кратком режиме;
- список выборочного экспорта молча отбрасывал встроенные инструменты, из-за
  чего состав папки в окне не совпадал с тем, что видно на экране.

Обе устранены. Второй случай вскрыл смежный дефект импорта: встроенные
инструменты существуют локально всегда, поэтому общая проверка на дубликаты
отсекала их раньше, чем доходило до переноса размещения — папка встроенного
инструмента не восстанавливалась никогда.

## Цикл 10. Организация чатов

Чаты были единственным разделом без иерархии — плоский список, отсортированный
по дате. При десятках чатов ориентироваться в нём невозможно.

### Папки чатов

Иерархия чатов построена на том же `FoldersEngine`, что и у Tools/Skills/Prompts
(тип `chats`), — отдельной реализации не появилось. Отличие в отрисовке: у
остальных разделов элементы живут в панели справа, а чаты открываются кликом
прямо в дереве, поэтому они рисуются внутри самого дерева сайдбара.

Управление — и кнопками (`＋` подпапка, `✏` переименовать, `✕` удалить), и
перетаскиванием: чат можно перенести в папку, папку — в другую папку. Защита от
вложения папки в собственного потомка досталась от `FoldersEngine.move()`. При
удалении папки её чаты и подпапки поднимаются на уровень выше — сами чаты не
удаляются.

Добавлены встроенные инструменты, дающие агенту тот же набор операций:

- `chat_folder` — создание, переименование, перемещение, удаление, список папок
- `move_chat` — перемещение чата (по id или названию; без аргумента — текущий)

### Метка времени и текущая папка

Новый чат создаётся в папке, выбранной в дереве, и получает заголовок с датой и
временем вместо одинакового «Новый чат» — иначе список из десятка одноимённых
записей нечитаем. В дереве у каждого чата показывается время последнего
изменения.

### Импорт чата

Инструмент `import_chat` принимает содержимое JSON-выгрузки (формат
`export_chat`) и восстанавливает переписку в новом чате. Порядок сообщений
задаётся заново по возрастанию: исходные метки времени могут совпадать или
отсутствовать.

Попутно обнаружился пробел в самом экспорте: JSON-выгрузка не сохраняла поле
`model`, поэтому при обратном импорте терялась информация о том, какая модель
сформировала каждый ответ. Добавлены `model` и `tool_call_id`; round-trip
проверен тестом.

### Кнопки экспорта и импорта чата

В подвале сайдбара (видны только на вкладке чатов). Работают **через встроенные
инструменты** `export_chat` и `import_chat`, а не дублируют их логику — формат
выгрузки одинаков независимо от того, кто её инициировал: пользователь кнопкой
или агент вызовом инструмента.

### Тайминг и модель в истории

Под каждым ответом ассистента выводится подпись: время, модель-автор и
длительность генерации. Модель берётся **из самой записи сообщения**, а не из
текущих настроек, — иначе после смены модели старые ответы задним числом
«переприписывались» бы новой. Замер идёт вокруг обращения к модели; при
стриминге подпись дописывается к уже отрисованному ответу без его перерисовки.

## Цикл 11. Панель навигации, тайминги и перенос чатов

### Сворачиваемая и растягиваемая панель

Ширина панели навигации задавалась переменной `--sidebar-w`, которую использует
grid-раскладка, — поэтому и сворачивание, и изменение размера сводятся к
управлению одной величиной. Кнопка в шапке сворачивает панель целиком (колонка
схлопывается в ноль), правую границу можно перетаскивать в пределах 180–640 px,
двойной клик по разделителю возвращает ширину по умолчанию.

Состояние сохраняется в `settings/layout` и восстанавливается при запуске.
Использовано собственное хранилище приложения, а не `localStorage`: заводить
второй механизм ради двух чисел незачем.

### Тайминг запроса пользователя

Раньше длительность показывалась только у ответа ассистента и охватывала одну
генерацию. Теперь у сообщения пользователя выводится **полное время обработки
хода** — от отправки до финального ответа, включая все вызовы инструментов.
Значение становится известно уже после отрисовки сообщения, поэтому подпись
обновляется точечно по `data-msg-id`, без перерисовки переписки.

### Отметка смены модели в истории

При отправке сообщения текущая модель сравнивается с той, что была записана в
чате; при расхождении в переписку добавляется служебная запись
`kind: 'model-switch'`. Без такой отметки в чате со сменой модели невозможно
понять, где проходит граница между ответами разных моделей.

Важная деталь: служебные записи **исключены из контекста, отправляемого в API**.
Иначе они попали бы туда вторым `system`-сообщением и сбивали бы модель.

### Массовый экспорт и импорт чатов

Инструменты `export_chats` и `import_chats` переносят чаты целиком: переписку,
структуру папок (со всей цепочкой родителей), статистику чата, а также модель-
автор каждого ответа, время генерации и время обработки запроса. Кнопки в
подвале сайдбара вызывают эти же инструменты, а не дублируют их логику.

Экспорт даёт выбрать конкретные чаты (по умолчанию отмечены те, что лежат в
текущей папке). Импорт поддерживает режимы «добавить» и «перезаписать»; при
перезаписи старые сообщения чата удаляются, иначе они удвоились бы. Папка с тем
же именем на том же уровне переиспользуется — то же правило, что и при импорте
разделов.

### Попутно исправлено

Автоматическое переименование чата по первому сообщению сверялось со строкой
«Новый чат», хотя предыдущий цикл сменил формат заголовка на «Чат ДД.ММ, ЧЧ:ММ»
— то есть переименование молча перестало работать. Проверка заменена на шаблон,
понимающий оба формата.

## Цикл 12. Прерывание хода и обрыв ответа

Две жалобы («кнопка останова остаётся активной после срабатывания лимита» и
«ответ выглядит неполным») оказались проявлениями трёх разных дефектов.

### Кнопка останова оставалась активной

Перед рекурсивным переходом к следующему шагу цепочки стоял сырой сброс
состояния — `isStreaming = false` и `send-btn.disabled = false`, минуя
`_setBusy()`. Два следствия:

1. Кнопка останова при этом не скрывалась, а следующий шаг снова показывал её.
2. Между шагами открывалось окно, в котором `sendMessage()` пропускал новое
   сообщение — запускалась **вторая цепочка параллельно первой**. Две цепочки
   затирали состояние друг друга: одна завершалась и сбрасывала флаги, вторая
   продолжала работу с уже «свободным» интерфейсом.

Исправлено введением единственного владельца состояния: занятость снимает
только корневой кадр цепочки (`depth === 0`), и делает это в `finally` — то
есть на любом пути выхода, включая `return` из середины цикла вызовов
инструментов, прерывание по таймауту и необработанную ошибку. Вложенные кадры
и `_stopTurn()` больше не трогают занятость. Поведение проверено симуляцией
модели состояния: воспроизведён прежний дефект и подтверждено исправление.

### Частичный ответ терялся при прерывании

Запись ответа в БД выполнялась **после** `await` на запросе к модели. При
прерывании — по таймауту хода или кнопкой «⏹» — уже полученный и отрисованный
текст никуда не сохранялся: ответ выглядел неполным, после перезагрузки чата
исчезал совсем и не попадал в контекст следующего запроса.

Теперь частичный текст сохраняется с пометкой `interrupted`, отображается в
подписи и остаётся в истории. Сообщение о таймауте дополнено указанием, что
полученная часть сохранена, и подсказкой, где менять лимит.

### Обрыв по лимиту токенов был невидим

`finish_reason` возвращался только в отладочный лог не-потоковой ветви, а в
стриминге не захватывался вовсе. Ответ, обрезанный провайдером на
`max_tokens` (по умолчанию 4096), внешне не отличался от завершённого — это и
выглядело как «не хватило памяти».

Gateway теперь возвращает `finish_reason` из обеих ветвей (в стриминге он
приходит отдельным чанком). При значении `length` ответ помечается как
`truncated`, под ним появляется предупреждение с фактическим значением
`max_tokens` и кнопка «Продолжить ответ»: она отправляет запрос на продолжение,
а обрезанный ответ уже лежит в истории, поэтому модель видит, где остановилась.

### Что делать при повторении

- **Лимит 180 с срабатывает регулярно** — увеличьте бюджет времени в
  ⚙ Настройки → Ограничения либо сократите число итераций tool-calling;
  на медленных или локальных моделях цепочка из нескольких вызовов
  инструментов легко выходит за три минуты.
- **Ответы обрываются** — поднимите `max_tokens` в ⚙ Настройки → Модель.
  Значение 4096 мало для длинных разборов кода; ориентир — несколько десятков
  тысяч для моделей с большим окном контекста.

## Цикл 13. Индикация работы и шифрование архива чатов

### Что происходит прямо сейчас

Во время работы висели три статичные точки, которые к тому же убирались перед
вызовами инструментов — то есть на самом долгом этапе пользователь не видел
вообще ничего и не мог отличить работу от зависания.

Теперь показывается панель состояния с текущей стадией: отправка запроса, сбор
контекста, ожидание ответа, потоковая генерация, выполнение конкретного
инструмента (с его именем и номером вызова), обработка результата, остановка.
Рядом — счётчик прошедшего времени и, если бюджет задан, остаток: `47 с из 180`.
При приближении к границе счётчик подсвечивается, чтобы обрыв по таймауту не
становился неожиданностью.

Таймер запускается один раз на весь ход, а не на каждую стадию: важно общее
время ожидания, а не длительность отдельного шага.

### Необязательное шифрование архива чатов

Массовая выгрузка чатов получила ту же опцию, что уже была у tools/skills/
промптов: галочка «Зашифровать архив паролем» в окне экспорта. Применяется тот
же механизм — PBKDF2-SHA256 (250 000 итераций) → AES-GCM-256.

Шифрование именно **необязательное**: без пароля файл остаётся обычным JSON,
который удобно просматривать и обрабатывать сторонними средствами. С паролем
получается конверт формата `ai-agent-archive-v1`, а к имени файла добавляется
`.enc`.

При импорте пароль спрашивать не нужно: формат определяется автоматически по
полю `format`. Если архив зашифрован, а пароль не введён, инструмент возвращает
`needsPassword`, и интерфейс подсказывает это отдельным сообщением вместо сухой
ошибки. Параметр `password` добавлен и в описания инструментов `export_chats` /
`import_chats` — агент может пользоваться шифрованием наравне с пользователем.

Проверено тестом: без пароля содержимое читаемо, с паролем скрыто, обе
разновидности архива корректно распознаются при импорте, все метаданные
(тайминги, модель-автор) переживают шифрование, неверный пароль отклоняется.

## Цикл 14. Файлы как ссылки

Новый раздел «📎 Файлы» с той же иерархией папок, что у остальных разделов.

### Почему ссылка, а не путь

Требование «не хранить файлы, а запоминать расположение» в браузере не
реализуется хранением текстового пути: из строки `C:\docs\spec.md` файл не
открыть — песочница это запрещает, и самого пути JS не видит.

Рабочий механизм — **File System Access API**. При выборе файла браузер выдаёт
`FileSystemFileHandle`, который переживает перезагрузку (кладётся в IndexedDB
структурным клонированием) и позволяет перечитать файл позже. В базе хранятся
только метаданные и дескриптор — содержимое не копируется, память не
расходуется, а правки файла на диске видны при следующем чтении.

### Границы, о которых нужно знать

- API поддерживают **Chrome и Edge**; в Firefox и Safari его нет. Для них
  предусмотрен запасной режим через `<input type="file">`: ссылка работает до
  перезагрузки страницы, запись помечается `needsRelink`, а интерфейс прямо
  сообщает об этом вместо молчаливого отказа.
- Даже с дескриптором браузер может заново спросить разрешение — после
  перезапуска это штатное поведение. Разрешение запрашивается только из
  действия пользователя (кнопка «Просмотр»), иначе браузер молча откажет.
- Если файл перемещён, переименован или удалён, чтение возвращает
  `needsRelink`, и файл переуказывается кнопкой «Перевыбрать».

### Доступ из чатов, инструментов, навыков и промптов

Три встроенных инструмента:

- `list_files` — список ссылок с путями, размерами, заметками и признаком
  доступности (`available`)
- `read_file` — чтение по id, имени или пути «Папка/файл.txt»; содержимое
  берётся с диска в момент вызова
- `search_files` — поиск подстроки внутри текстовых файлов с фрагментами

Список доступных файлов добавляется в системный промпт — модель знает, на что
можно сослаться. **Содержимое при этом не подставляется**: файлы читаются
инструментом по мере надобности, иначе контекст забивался бы текстами, которые
в конкретном запросе не нужны.

В промптах и навыках работает плейсхолдер `{{file:путь}}` — содержимое
подставляется в текст при использовании промпта.

Ссылка на файл разрешается по id, точному имени, полному или частичному пути —
проверено тестом, включая корректную деградацию при потерянном дескрипторе.

### Что осталось за рамками

Запись в файлы не реализована: она требует отдельного разрешения `readwrite` и
несёт риск порчи данных пользователя — записывающий инструмент, доступный
модели, должен проектироваться с подтверждением каждой операции.

## Цикл 15. Аудит: контекст, гонки, производительность

Плановый аудит кода целиком, а не последних правок. Исправления перечислены
в порядке практической важности.

### Контекст рос неограниченно — чат неизбежно ломался

В API уходила **вся** история чата. Приложение при этом считало токены,
предупреждало о заполнении на 75 % и 100 % и предлагало создать новый чат — но
ничего не предпринимало. После превышения лимита чат становился нерабочим:
каждый следующий запрос снова слал переполненный контекст и получал ошибку
провайдера.

Добавлена обрезка: системный промпт неприкосновенен, дальше сообщения берутся
с конца, пока укладываются в бюджет (окно контекста минус место под ответ минус
запас). Вытесненное заменяется краткой пометкой, чтобы модель знала о свёрнутом
начале разговора.

Ключевая тонкость — **целостность пар «вызов инструмента → результат»**.
Сообщение `role:'tool'` без предшествующего `assistant` с `tool_calls` ломает
запрос: провайдеры отвечают ошибкой на «сироту». Граница обрезки сдвигается
вперёд, пока первое сообщение не перестанет быть осиротевшим результатом.
Проверено тестом на истории из 120 сообщений с tool-парами.

### Гонка при записи статистики

`_recordUsage`, `_recordContextSize` и `_recordToolCall` работали по схеме
read-modify-write в отдельных транзакциях и вызывались подряд, а последний —
ещё и в цикле по вызовам инструментов. Перекрывающиеся обновления читали одно
и то же состояние, и изменения затирались.

Смоделировал на 10 параллельных обновлениях: вместо ожидаемых 1000 токенов
записывалось **100** — терялось 90 % данных. Все обновления пропущены через
последовательную очередь; после исправления результат точный.

### Транзакция на каждую операцию

`_tx()` открывал новую транзакцию под каждый `put`/`delete`. Импорт архива на
50 чатов с 2000 сообщений — это 2000+ транзакций подряд.

Добавлены пакетные `putAll()` и `deleteAll()`, выполняющие всё в одной
транзакции; переведены импорт чатов, удаление чата и `FoldersEngine.remove()`.
Побочный плюс — атомарность: при сбое пакет откатывается целиком.

### Молчаливый провал запуска

`app.js` при ошибке инициализации писал в консоль и всё — пользователь видел
пустой интерфейс без объяснений. Наиболее вероятная причина такого отказа —
неудачная миграция схемы (версия поднималась до 8) или недоступное хранилище
в приватном окне.

Теперь показывается экран ошибки с текстом проблемы, кнопкой перезагрузки и —
для ошибок хранилища — кнопкой удаления базы с явным предупреждением о потере
данных. Заодно обработаны два случая, которые раньше вызывали молчаливое
зависание: `onblocked` при открытии базы (другая вкладка мешает апгрейду схемы)
и `onversionchange` (база закрыта из другой вкладки).

### Прочее

- **Нативные `prompt`/`confirm` заменены** на модальные окна приложения
  (9 мест). Помимо несогласованного вида, нативный `prompt` отключён в части
  окружений — функция молча переставала бы работать.
- **Кэш индекса папок** в `FilesEngine.pathOf()`: раньше на каждый файл шёл
  линейный поиск по всем папкам.
- **Понятная ошибка при переполнении хранилища**: `QuotaExceededError`
  подменяется текстом с указанием, что именно делать.

## Цикл 16. Дополнительный аудит безопасности

Проверка мест, которые раньше не рассматривались пристально.

### XSS через поле icon у навыков

Найдена работающая дыра. Поле `icon` подставлялось в разметку **без
экранирования** (`${s.icon}` в панели чата и в карточке навыка), при том что
задаёт его модель через `create_skill`. Строка вида `<img src=x onerror=...>`
в этом поле выполнилась бы как разметка — то есть повторение уже закрытой
однажды проблемы, но по другому пути.

Исправлено на обоих рубежах: вывод экранируется, а на входе значок
ограничивается по длине и очищается от символов разметки.

Остальные подстановки проверены выборочно — `ask_user`, названия, описания,
заметки к файлам экранируются корректно; inline-обработчиков (`onclick=`
в шаблонах) в коде нет.

### Поток не закрывался при прерывании

При остановке кнопкой «⏹» или по таймауту выход из цикла чтения SSE шёл через
исключение, и `reader` оставался заблокированным — соединение висело до сборки
мусора. Добавлено явное освобождение (`releaseLock` + `cancel`) в `finally`.

## Цикл 17. Набор для начинающих и импорт навыков

### Помощь новичку

Четыре встроенных навыка (все выключены по умолчанию):

- **🧭 Помощник новичка** — объясняет возможности простым языком, ведёт от задачи
  пользователя, а не от списка функций, предлагает по одному шагу за раз.
- **🗂 Организатор** — наводит порядок в чатах, навыках, промптах и файлах;
  сначала смотрит, что есть, показывает план и ждёт согласия перед перемещением.
- **🎓 Эксперт по агенту** — разбор настроек и типичных жалоб: обрыв ответа,
  прерывание по времени, зацикливание, пропавшие токены.
- **📥 Импортёр навыков** — перенос навыков из внешних источников с обязательной
  проверкой.

Плюс два инструмента и четыре промпта-заготовки на вкладке «Промпты».

`explain_agent` объясняет устройство агента и **одновременно возвращает
статистику рабочего пространства** — сколько у пользователя чатов, навыков,
инструментов. Объяснение получается не абстрактным, а про то, что у него
реально есть.

`diagnose` проверяет состояние: выбрана ли модель, не малы ли лимиты, есть ли
выключенные инструменты в ожидании проверки, битые ссылки на файлы, близко ли
заполнение контекста. Каждая находка сопровождается точным путём в настройках.

### Импорт навыков и его безопасность

Здесь важна оговорка, определившая всю реализацию: **навык — это системный
промпт, то есть инструкции, управляющие поведением агента**. Импорт чужого
навыка ближе к запуску чужого кода, чем к копированию текста: промпт из
сомнительного репозитория может содержать указания скрывать информацию от
пользователя, обращаться к посторонним адресам или переопределять правила
агента.

Поэтому `import_skill_from_text`:

- сохраняет навык **всегда выключенным** — тот же принцип, что у инструментов
  с кодом;
- **не выполняет** импортируемый текст, а анализирует его: возвращает список
  найденных подозрительных мест (попытки отменить прежние инструкции,
  требования секретности, внешние ссылки, упоминания ключей, указания на
  передачу данных наружу);
- инструктирует агента показать разбор пользователю до включения.

Навык «Импортёр навыков» дублирует это правило на уровне поведения: чужой текст
для него — данные, а не команды.

Проверено на промпте с тремя закладками сразу — все три распознаны, навык создан
выключенным.

### Ограничение, которое стоит знать

Прямая загрузка из репозиториев (GitHub и т. п.) через `http_fetch` упирается
в CORS: большинство сайтов не отдают содержимое стороннему скрипту. Рабочий
путь — скопировать текст навыка и передать агенту; он разберёт и сохранит.

## Цикл 18. Механизм безопасности

Агент выполняет действия сам, по решению модели. Решение может быть ошибочным
или подсказанным враждебным текстом, попавшим в контекст — веб-страницей через
`http_fetch`, содержимым файла, импортированным навыком. Добавлен слой политик,
управляющий тем, что агент делает сразу, а что — только с подтверждения.

### Где живёт проверка

В одной точке — `executeTool()`, перед исполнением любого инструмента.
Размазывать проверки по обработчикам нельзя: новый инструмент легко забыть
закрыть, и дыра появится незаметно. Незнакомый инструмент с собственным кодом
классифицируется как `execute` — по умолчанию строже, а не мягче.

Операции классифицируются по **последствиям**, а не по технической природе:
чтение, изменение, удаление, обращение в сеть, исполнение кода или подмена
поведения агента.

### Режимы

| Режим | Что требует подтверждения |
|---|---|
| **Отключено** | ничего |
| **Минимальный** | только необратимое: удаление папок, перезапись при импорте |
| **Оптимальный** | плюс создание и изменение инструментов, импорт навыков, обращения в сеть, подозрительные операции |
| **Максимальный** | любая операция, изменяющая данные, и чтение файлов; создание инструментов агентом **запрещено полностью**; сеть — только по белому списку доменов |

### Что предложено для максимального режима

Помимо тотального подтверждения, добавлено то, что в мягких режимах было бы
избыточным:

- **Полный запрет `create_tool` и `update_tool`.** Это самая опасная операция:
  код инструмента исполняется в браузере. В строгом режиме его место — ручное
  создание пользователем через интерфейс, а не решение модели.
- **Белый список доменов.** Обращения за его пределы блокируются без вопроса —
  диалог подтверждения не спасает, если пользователь устал нажимать «да».
- **Подтверждение чтения файлов** — единственных данных, лежащих вне агента.

### Детали, влияющие на практическую полезность

- **Анализ кода инструмента.** При `create_tool` код проверяется на признаки
  выхода за рамки задачи: обращения к IndexedDB, localStorage, сети, странице
  приложения, `eval`, упоминания ключей. Найденное показывается в диалоге —
  пользователь решает, видя основание, а не голый вопрос «разрешить?».
- **Потолок изменений за один ответ** (по умолчанию 20) — защита от случая
  «агент увлёкся и переделал всё». Считается на ход, а не на сессию.
- **Запоминание домена на сессию.** Повторно спрашивать про тот же адрес —
  верный способ приучить нажимать «да» не читая.
- **Действия из интерфейса не переспрашиваются** (`bypassSecurity`): требовать
  подтверждения того, что человек только что нажал сам, — бессмысленный шум.
- **Отказ не ломает работу.** Агент получает сообщение, что операция не
  разрешена, и подсказку не искать обходной путь, а спросить пользователя.
- **Журнал решений** — что запрашивалось, что разрешено, что заблокировано.

### Честная граница механизма

Политики ограничивают действия агента **через инструменты**. Они не изолируют
код самого инструмента: включённый инструмент выполняется в браузере и может
обращаться к сети напрямую, минуя проверки. Настоящая песочница требует Worker
или sandboxed iframe. Поэтому главный барьер остаётся прежним — созданный
моделью инструмент включает пользователь вручную. Это предупреждение выведено
прямо на вкладке настроек, чтобы механизм не создавал ложного чувства защиты.

## Цикл 19. Файлы: инициатива агента и доступ после перезапуска

### Агент анализировал файлы без просьбы

Ошибка проектирования с моей стороны: перечень всех файлов вставлялся в
системный промпт **при каждом запросе**. Само его присутствие работало как
приглашение — агент начинал разбирать файлы даже в ответ на «с чего начать».
Смягчения формулировки оказалось мало: список в контексте провоцирует сам по
себе.

Теперь по умолчанию модель знает лишь **факт наличия** файлов, а перечень
получает инструментом `list_files` — то есть когда пользователь о файлах
заговорил. Режим настраивается (⚙ Настройки → Отображение): не упоминать /
только факт / полный перечень. Дополнительно в навык «Помощник новичка»
добавлено прямое правило не трогать данные пользователя по своей инициативе:
знакомство с агентом не требует изучать чужие материалы.

Побочный выигрыш — контекст не расходуется на список файлов, не нужных
в текущем запросе.

### Доступ к файлам после перезапуска браузера

Здесь важно различать два разных случая, которые раньше сливались в один флаг
«требуется повторный выбор»:

- **Разрешение сброшено.** Дескриптор цел, ссылка не потеряна — браузер просто
  требует подтвердить доступ заново. Это штатное поведение File System Access
  API после перезапуска.
- **Файл недоступен.** Перемещён, переименован, удалён или дескриптора не было
  вовсе (запасной режим в Firefox и Safari).

Панель теперь показывает реальное состояние каждой ссылки (проверкой
`queryPermission`, без запроса), а не флаг из базы.

Для первого случая добавлено **пакетное восстановление**: одна кнопка на все
файлы. Разрешение можно запрашивать только из действия пользователя, поэтому
серия запросов идёт в рамках одного нажатия. Часть браузеров прерывает серию
после первого диалога — тогда оставшиеся файлы показываются отдельно, и нажатие
повторяется. Это всё равно лучше, чем подтверждать каждый файл вручную через
«Просмотр».

Инструменты тоже стали точнее: `list_files` возвращает `status`
(`ready` / `needs-permission` / `needs-relink`), а `read_file` при отсутствии
разрешения объясняет агенту, что ссылка цела и нужно нажать «Восстановить
доступ», — вместо тупика, из которого агент пытался выкрутиться другими
инструментами.

## Цикл 20. Компактная панель навыков

После добавления обучающих навыков их стало восемь, и панель под полем ввода
занимала заметную часть экрана в каждом чате — при том что включены обычно
один-два.

Два режима с переключателем прямо в панели:

- **Только включённые** (по умолчанию) — отключённый навык исчезает из панели;
  кнопка показывает, сколько скрыто: «▾ все навыки (6)».
- **Все** — прежнее поведение.

Выбор сохраняется между сессиями; продублирован в ⚙ Настройки → Отображение.

Одна деталь потребовала внимания: в компактном режиме отключённый навык
пропадает из панели, и при первом разе это выглядит как потеря. Поэтому после
первого такого отключения выводится разовая подсказка, где его найти — дальше
поведение уже очевидно и повторять её незачем.

## Цикл 21. Разбивка tools, контроль MCP и отказоустойчивые подключения

### Реинжиниринг tools-engine.js

Файл вырос до 2515 строк. В нём вперемешку лежали описания инструментов,
их обработчики, механизм исполнения и проверки безопасности: правка одного
инструмента заставляла листать весь файл, а изменения в разных инструментах
постоянно конфликтовали между собой.

Разбит на семь модулей. Границы проведены по **роли кода** — что описывает,

### Контроль MCP в блоке безопасности

Раньше MCP-инструмент попадал в общую категорию `network` и подчинялся тем
же правилам, что и `http_fetch`. Это неверно: у MCP-вызова аргументы
формирует модель и отправляет на чужой сервер, а ответ возвращается прямо
в контекст диалога. Заведена отдельная категория `mcp` со своим набором
политик:

- белый список разрешённых хостов — сильнее режима безопасности;
- требование https (localhost по http допускается отдельной настройкой,
  поскольку локальный MCP-сервер — обычный сценарий);
- переиспользование чёрного списка адресов от `http_fetch` — защита от
  обращений во внутреннюю сеть здесь нужна ровно та же;
- таймаут запроса: у `fetch` своего предела нет, а таймаут в `executeTool`
  отпускает ожидание, но не разрывает соединение;
- потолок размера ответа: ответ вытесняет из контекста историю и системный
  промпт, то есть в том числе правила поведения агента;
- лимит MCP-вызовов за один ход;
- пометка ответа как данных, а не указаний.

Подтверждённые MCP-хосты хранятся отдельно от подтверждённых адресов
`http_fetch`: разрешение «звонить на этот MCP-сервер» и разрешение «сходить
по этому адресу» — разные по смыслу решения.

**Отдельно:** если в аргументах вызова обнаружена строка, похожая на ключ
доступа, подтверждение запрашивается всегда — даже на уже одобренном
сервере и в минимальном режиме. Пользователь разрешил обращаться к адресу;
он не разрешал отправлять туда ключи, и одно из другого не следует.

### Исправленный дефект в клиенте MCP

JSON-RPC возвращает ошибки со статусом 200, поэтому проверка `resp.ok`
их не ловила: объект с полем `error` уходил модели как успешный результат,
и она принимала неудачу за ответ. Теперь разбираются и `error` уровня
протокола, и признак `isError` уровня MCP. Попутно разделены случаи
«сервер недоступен» и «запрос заблокирован CORS» — браузер отдаёт на оба
одинаковый `TypeError`, и без подсказки причина ищется не там.

### Контроль зацикливания инструментов

Общий счётчик `writes` не ловил случай, когда агент застревает на одном
инструменте: сто вызовов `http_fetch` — это ноль записей. Добавлен потолок
вызовов **одного** инструмента за ход, срабатывающий во всех режимах, в том
числе для безобидных read-инструментов: бесконечный цикл из `calculator`
ничем не лучше бесконечного цикла из чего угодно другого.

Статический анализ кода создаваемых инструментов дополнен шестью
признаками: обращение к хранилищу секретов, чтение настроек подключения,
подгрузка стороннего скрипта, декодирование строк (`atob`, `fromCharCode`),
работа с буфером обмена и `sendBeacon`, обмен сообщениями между контекстами.

### Набор подключений к LLM

Раньше подключение было одно, в записи `settings/llm`. Заведено отдельное
хранилище `llm_connections` (версия схемы 8 → 9): подключений много, они
перебираются при отказе и сортируются по приоритету — для этого нужен
индекс, которого у key-value записи в `settings` быть не может.

Секреты (`apiKey`, `customHeaderValue`) шифруются существующим
`SecretsVault`. Остальные поля лежат открыто: они нужны, чтобы построить
список и выбрать подключение, а расшифровывать всю таблицу на каждый выбор
бессмысленно — модель угроз от этого не меняется.

Старая одиночная запись `settings/llm` мигрирует в первое подключение
списка при первом запуске.

У каждого подключения есть флаг `allowAgentSwitch`: снятый, он оставляет
подключение доступным пользователю вручную, но закрывает его для агента.
Это для дорогих или чувствительных по приватности провайдеров.

### Переключение при отказе

Новый `llm-pool.js`. Три режима, выбираются в интерфейсе:

- **priority** — цепочка: работает первое доступное, после сбоя агент
  остаётся на запасном;
- **priority-restore** — то же, но с автоматическим возвратом на основное
  после его восстановления;
- **round-robin** — запросы распределяются по кругу между рабочими
  подключениями.

Поверх всех режимов работает размыкатель: после N подряд неудач
подключение выводится из ротации на время остывания. Состояние здоровья
живёт **в памяти** и обнуляется при перезагрузке страницы — иначе один
неудачный вечер помечал бы подключение нерабочим навсегда, хотя провайдер
давно починился.

`LLMGateway.chat()` стал обёрткой над `_chatOnce()`. Публичный интерфейс не
изменился, поэтому `ui-chat.js` не потребовал правок; если пул не
подключён, поведение остаётся прежним.

Два ограничения заложены намеренно и вынесены в комментарии к модулю:

1. **Переключение возможно только до первого полученного токена.** Если
   поток оборвался на середине ответа, повтор на другой модели начал бы
   генерацию заново, и пользователь увидел бы склейку двух разных ответов.
   Такие ошибки помечаются `streamStarted` и пробрасываются без повтора.

2. **Ошибки конфигурации перебор не вызывают.** Неверный ключ, отсутствующая
   модель, опечатка в адресе — это не отказ провайдера. Перебор в таком
   случае показал бы пользователю ошибку от последнего подключения в списке
   вместо настоящей причины.

Число переключений за один ход ограничено (по умолчанию 3), иначе цикл
«переключился → снова ошибка → переключился» прошёл бы по всему списку,
потратив по запросу на каждом провайдере. Каждое переключение попадает в
журнал безопасности и показывается в чате отдельной строкой: смена модели
меняет качество и стиль ответа, и молчать об этом нельзя — иначе
пользователь решит, что модель внезапно поглупела, и будет искать причину
не там.

### Инструменты и навык управления моделями

Пять инструментов: `llm_list`, `llm_status`, `llm_switch`, `llm_test`,
`llm_strategy`. Секреты через них не отдаются — всё проходит через
`pool.sanitize()`.

Пользователь выбрал вариант, в котором агент переключается **без
подтверждения**. Сдерживают его четыре независимых механизма: инструменты
и навык созданы выключенными; флаг `allowAgentSwitch` у каждого
подключения; предел переключений за ход; запись каждого переключения в
журнал. В максимальном режиме безопасности подтверждение всё же
запрашивается.

Добавлен встроенный навык «Маршрутизация моделей» (выключен по умолчанию).
В его системном промпте отдельно оговорено, чего делать нельзя: перебирать
подключения в поисках устраивающего ответа (это подгонка, а не работа),
переключаться молча, дублировать автоматический failover и предлагать смену
модели как ответ на любую ошибку.

### Интерфейс

Новый `ui-connections.js` — список подключений с проверкой доступности,
редактор подключения, настройки режима и порогов. Вынесен в отдельный файл,
а не добавлен вкладкой в настройки: настройки описывают **одно** подключение
полями формы, а здесь список объектов со своим жизненным циклом. Смешивать
их — значит получить форму, где половина полей относится к выбранному
элементу, а половина к приложению.

Пустое поле ключа при редактировании означает «не менять»: иначе открытие
редактора ради смены модели стирало бы ключ.

### Доработка: рассогласования, найденные при сверке

После разбивки проведена сверка всех мест, которых коснулось изменение
источника правды. Найдено и исправлено шесть расхождений.

**Форма настроек и список подключений расходились.** Окно «⚙ Настройки»
писало в `settings/llm`, а пул читал список — изменения из формы терялись
при первом же переключении или при перезагрузке. Форма теперь считается
редактором **активного** подключения: `pool.syncFromSettingsForm()`
переносит в него введённое, сохраняя поля, которых в старой форме нет
(приоритет, окно контекста, разрешение агенту). Если список пуст, форма
создаёт первое подключение — привычный путь настройки «с нуля» работает
по-прежнему.

**Уведомление о переключении писалось в несуществующий контейнер.**
`notifyModelSwitch` обращалось к `#messages`, тогда как в разметке
`#chat-messages`: сообщение о смене модели просто не появлялось.

**Журнал безопасности не показывал новые записи.** Он знал только о
решениях `approved/denied/blocked` и о полях `risks/reason`, а
переключения пишутся как `executed/switched` с полем `detail` — строки
выводились без значка и без причины.

**Окно контекста не учитывало подключение.** `effectiveContextLimit()`
угадывал предел по имени модели, хотя у подключения есть заданное
пользователем поле. Одна и та же модель у разных провайдеров может
отдаваться с разным окном — урезанные тарифы, self-hosted сборки, — и имя
модели об этом ничего не говорит. Порядок теперь: ручная настройка →
окно подключения → таблица моделей.

**Диагностика описывала устаревшую картину.** `diagnose` видел только поля
шлюза. Добавлены проверки: подключений нет вовсе; подключение только одно
(переключаться не на что); выведенные из ротации после сбоев; включённые
без ключа или без выбранной модели.

**Справка не знала о подключениях.** В `explain_agent` добавлена тема
`models`, объясняющая устройство переключения — включая оба его
ограничения, чтобы агент не обещал пользователю невозможного.

### Интерфейс политик MCP

Политики, добавленные в этом цикле, настраивались только через запись в
БД. В раздел безопасности добавлены: список разрешённых MCP-серверов,

данных, таймаут, предел размера ответа, лимит вызовов за ход и потолок
вызовов одного инструмента.

Отдельная панель показывает подключённые MCP-серверы, сгруппированные по
адресу, с числом включённых инструментов и отметкой, проходит ли сервер

Подсказки к режимам безопасности дополнены — раньше они не упоминали ни

## Цикл 22. Провайдеры и модели: двухуровневая настройка

Настройка подключений из цикла 21 оказалась неудобной: список подключений
жил в отдельном окне, модель задавалась строкой в другой вкладке, а связи
между ними в интерфейсе видно не было. Переделано.

### Один уровень стал двумя

Вкладки «Подключение» и «Модель» слиты в одну — «Провайдеры и модели».
Внутри раскрывающийся список: провайдер, под ним его модели. Разделять их
не имело смысла — настраивают их всегда вместе: добавил провайдера, сразу
выбираешь у него модели.

| Уровень | Что описывает |
|---|---|
| Провайдер | адрес API, ключ, способ авторизации |
| Модель | идентификатор, класс сложности, окно контекста, max_tokens, температура, заметка |

Модели вложены в запись провайдера, а не лежат отдельным хранилищем:
модель не существует без провайдера, читаются они всегда вместе, и
вложенность избавляет от каскадного удаления и рассинхронизации. Ссылка
на модель — строка `идентификатор_провайдера::идентификатор_модели`; её
можно положить в запись чата, не заводя вторичных индексов.

### Добавление моделей из списка провайдера

Кнопка «Загрузить у провайдера» запрашивает `/models` и показывает, что
там есть. Из выдачи в отдельный спойлер убраны эмбеддинги, озвучка,
генерация изображений и модерация — для чата они не годятся, но и
выбрасывать их совсем нельзя: у самодельных сборок имена бывают любые.

Класс сложности и окно контекста подставляются по имени модели и помечены
как догадка. Окно контекста провайдеры в API не сообщают вовсе, поэтому
оно задаётся руками — по нему считается индикатор заполнения и
подрезается история.

Класс сложности — «Простая», «Обычная», «Сильная», «Рассуждающая» — ни на
что в работе не влияет и нужен только при выборе модели в чате: по
идентификатору вроде `qwen2.5-72b-instruct` непонятно, за чем к этой
модели идти.

### Выбор модели в чате

Устроено как навыки: у чата свой короткий набор моделей, из которого
выбрана ровно одна. Плоский выпадающий список всех моделей провайдера не
годился — их бывают десятки, а в конкретном чате нужны две-три.

Клик по значку выбирает модель, правая кнопка убирает её из набора.
Отдельного крестика на значке нет: он занимал бы место в и без того
плотной панели.

Модель применяется к шлюзу и при переключении чата, и перед каждой
отправкой. Шлюз один на приложение, а модель — свойство чата: без этого
открытый ранее чат оставлял бы в шлюзе свою модель.

Ссылки на удалённые модели отфильтровываются при чтении, а не вычищаются
при удалении: чатов могут быть сотни, и переписывать их все ради одной
убранной модели неоправданно.

### Убрано автоматическое переключение

Механизм failover из цикла 21 удалён по требованию: `llm-pool.js`,
стратегии, размыкатель, лимит переключений за ход, обёртка `chat()` в
шлюзе. `LLMGateway.chat()` снова просто транспорт.

Причина, по которой это правильно: подмена модели посреди работы меняет
качество и стиль ответа, а пользователю причина не видна. Инструмент
`llm_strategy` удалён, `llm_switch` теперь меняет модель текущего чата, а
не активное подключение.

Код механизма остался в истории цикла 21 — если отказоустойчивость
понадобится, восстанавливать его с нуля не придётся.

### Ручной лимит контекста убран

Он был один на всё приложение и врал, как только в чатах оказывались
разные модели. Теперь окно контекста — свойство модели. В настройках
остался только порог, при котором предупреждать о заполнении.

### Что переехало следом

- `diagnose` проверяет реестр: нет провайдеров, нет моделей, провайдер без
  ключа, модель без окна контекста, не выбрана модель по умолчанию.
- `explain_agent`, тема `models` — переписана под двухуровневую настройку.
- Навык переименован в «Выбор модели»; из промпта убрано всё про
  автоматическое переключение, добавлен запрет выдумывать названия моделей.
- Категория `llm` в блоке безопасности сохранена: `llm_switch` меняет то,
  чем агент думает дальше, и в максимальном режиме подтверждается.

### Перенос старых настроек

Реестр при первом запуске переносит `settings/llm` в первого провайдера с
одной моделью. Повторный запуск дубля не создаёт. Записи `llm_connections`
из цикла 21 читаются как провайдеры без моделей — модели к ним добавляются
кнопкой «Загрузить у провайдера».

### Тесты

`test-pool.js` удалён вместе с механизмом, который проверял. Добавлен
`test-registry.js` (44 проверки): два уровня и вложенность, ссылки на
модели, применение к шлюзу, модель по умолчанию и её судьба при удалении,
каскад при удалении провайдера, перенос старых настроек и защита от
повторного переноса, запрос списка моделей с обоими способами авторизации,
разбор ошибок.

Общий счёт: 118 проверок в трёх наборах.

## Цикл 23. Модальные окна настроек и модель чата при старте

Три жалобы на панель «Провайдеры и модели» оказались тремя независимыми
дефектами — исправлены по очереди, каждый следующий вскрылся только после
починки предыдущего.

### «Сохранить» не закрывал редактор провайдера/модели

`_backToProviders()` вызывал `this.showSettings()` — метода с таким именем
не существует, правильное имя `showSettingsModal()`. Данные при этом реально
сохранялись в БД, но возврат к списку падал с `TypeError`, и в обработчике
кнопки «Сохранить» строка, закрывающая модалку, не выполнялась: окно
оставалось висеть открытым без видимой причины.

### Клик мимо окна закрывал редактор

`showProviderEditor`, `showModelEditor` и `showModelPicker` открывались без
`{ modal: true }` — в отличие от главного окна настроек, где это уже сделано
специально. Добавлен флаг всем трём; заодно найден и исправлен более общий
дефект в `_showModal()`: кнопка «Сохранить» стирала контейнер `#modals`
**после** вызова `onSave`, а `onSave` в этих окнах сам открывает следующее —
возврат к настройкам или повторный показ формы при ошибке валидации — и эта
строка сносила то, что `onSave` только что отрисовал. Стирание сделано
условным: только если после `onSave` в DOM всё ещё то самое окно, а не
новое, показанное самим `onSave`.

### Кнопка «+ В чат» ничего не делала

Окно «Модели для этого чата» позволяло добавить только одну модель за заход
— после первого клика оно закрывалось целиком, вместо того чтобы остаться
открытым для добавления следующей. Исправлено: список моделей теперь
перерисовывается на месте через делегирование клика на контейнер, а не
закрывается.

После этой правки кнопка отвечала клику, но по-прежнему не добавляла
модель — без единой ошибки в консоли. Причина оказалась глубже: `agent.js`
после инициализации сразу вызывал `updateChatToolbar()`, ни разу не загрузив
ни один чат — панель чата (быстрый выбор модели, статистика) рисовалась и
выглядела рабочей, а `this.currentChatId` оставался `null`. `setChatModel()`
при отсутствии текущего чата тихо ничего не делает — ни ошибки, ни эффекта.

Исправлено в источнике: при запуске приложение теперь открывает последний
использованный чат (по `updatedAt`), а не оставляет пустое состояние — как
это делает большинство чат-приложений. Отдельно, на случай самого первого
запуска без единого чата, `showChatModelPicker()` создаёт чат сам, если
`currentChatId` всё ещё пуст.

## Цикл 24. MCP-серверы как отдельная сущность

До этого цикла MCP-сервер не существовал как сущность вовсе: адрес и
токен просто повторялись на каждом импортированном с него tool. Изменить
имя или токен можно было только пересоздав все инструменты заново, удалить
сервер целиком — только вручную, по одному tool, а органайзер (иерархия
папок) не различал, какому серверу что принадлежит.

### Новое хранилище и связь с деревом Tools

Добавлен store `mcp_servers` (версия схемы БД 9 → 10): имя, URL, токен
(зашифрован), ссылка на папку-контейнер. При подключении сервера
(`connectMcpServer` в `tools-mcp.js`) создаётся папка-контейнер в корне
раздела Tools с полем `mcpServerId` — она и представляет сервер в дереве
(значок 🧩 вместо 📁, действия «Настроить»/«Удалить сервер» вместо
переименования/удаления папки). Импортированные tools получают то же поле
и кладутся в эту папку.

Внутри контейнера разрешена обычная вложенная иерархия подпапок — тот же
`FoldersEngine`, без изменений. Изоляция обеспечена не структурой данных, а
проверкой при перетаскивании: `_mcpScopeOf()` в `ui-navigation.js` находит
у папки (поднимаясь по `parentId`) ближайшего предка с `mcpServerId` и
сравнивает область видимости источника и цели. Перемещение, смешивающее
инструменты разных серверов — или сервер с обычными папками, — молча
отклоняется, тем же приёмом, что уже применён к защите от циклов в
`FoldersEngine.move()`. Контейнер сервера сам не перетаскивается: он всегда
лежит в корне.

### Правка и удаление

`updateMcpServer` меняет имя и токен; адрес — нет, он совпадает с
`mcpServer` на уже импортированных tools, и его смена потребовала бы либо
их перепривязки, либо расхождения между записью сервера и его же
инструментами. Пустой токен при правке означает «не менять» — та же
договорённость, что и в редакторе провайдеров LLM. Смена токена обновляет
`mcpToken` у всех tools сервера и переоткрывает их обработчики — иначе
следующий вызов ушёл бы со старым токеном, застрявшим в замыкании
`_registerMcpHandler`.

`removeMcpServer` удаляет сервер целиком: все его tools (в каком бы
подпапке поддерева они ни лежали — поиск идёт по `mcpServerId`, а не по
структуре папок), все папки поддерева и саму запись сервера. Обычный
`FoldersEngine.remove()` здесь не годится — он поднимает содержимое папки
на уровень выше, а сервер должен исчезнуть вместе со всем, что в нём
организовано.

### Что переехало следом

- Карточка MCP-инструмента помечена значком 🧩; кнопка «Редактировать»
  для неё скрыта — общая форма показывает поле Handler Code, бессмысленное
  для проксированного вызова.
- Ручное создание custom-tool внутри чужого сервера автоматически уводится
  в корень раздела — та же граница, что и при перетаскивании.
- `listMcpServers()` (панель безопасности, диагностика) стал гибридным:
  именованные серверы — из `mcp_servers`, а инструменты без `mcpServerId`
  (данные, добавленные до этого цикла) по-прежнему группируются по хосту,
  как раньше, — не выпадают из списка молча.

### Тесты

12 новых проверок в `test-tools.js`: подключение с импортом tools, вложенная
подпапка, переименование, смена токена (с обновлением у всех tools),
каскадное удаление (tools, вложенные папки, запись сервера). Общий счёт
пакета — 66 проверок.

## Цикл 25. Структура `js/` по подпапкам

К 30 файлам без единой вложенности плоский список перестал быть навигируемым
списком — стал вычитыванием оглавления. Разложено по той же логике, что уже
применена внутри `tools-*.js` и `ui-*.js`: по **роли кода**, а не по
предметным группам.

| Подпапка | Состав |
|---|---|
| `core/` | `agent.js`, `db.js`, `crypto-utils.js`, `markdown.js` — то, на чём держится всё остальное |
| `llm/` | `llm-gateway.js`, `llm-registry.js` |
| `tools/` | все семь модулей `tools-*.js` |
| `engines/` | `skills-engine.js`, `prompts-library.js`, `folders-engine.js`, `files-engine.js`, `security-engine.js` — движки без общего префикса имени |
| `ui/` | все восемь модулей `ui-*.js` |
| `tests/` | четыре набора функциональных тестов на Node |

`app.js` остался в корне `js/` — как единственная точка входа, ему не нужна
подпапка. Ни один файл не переименован и не объединён с другим — изменились

путям (`load('tools-engine.js')` и подобные) — эти пути обновлены на
`load('tools/tools-engine.js')` и так далее, иначе тесты продолжали бы
искать файлы по старым, уже не существующим путям. Сам базовый путь
(`/home/claude/app/`, унаследованный от прежней облачной среды выполнения)
остался как есть — он не имеет отношения к переносу и ломает локальный
запуск тестов независимо от него.

Правильность переноса проверена в два прохода: все четыре набора тестов
(132 проверки) выполнены заново по новым путям без единого расхождения, а
цепочка загрузки `index.html` — эмулирована в Node (`vm`, тот же общий
глобальный контекст, что и у реального `<script>` без `type="module"`) в
точности в объявленном порядке: все 27 файлов нашлись по обновлённым путям
и связались друг с другом (примеси `Object.assign(X.prototype, {...})`
нашли свои классы) вплоть до реального вызова `AgentDB.open()` — то есть
до точки, где для дальнейшей проверки нужен уже настоящий браузерный
IndexedDB, а не заглушка.

# Часть II. Описание проекта

## Что это

Клиентское веб-приложение: персональный AI-агент с поддержкой tool-calling,
работающий целиком в браузере. Без сборки, без бэкенда, без внешних
зависимостей — только нативные Web API. Данные хранятся локально в IndexedDB,
запросы идут напрямую к любому OpenAI-совместимому API.

## Возможности

- **Чат с LLM** — потоковый вывод, любой OpenAI-совместимый эндпоинт
- **Tools** — встроенные, собственные на JS, внешние MCP-серверы (сервер как
  сущность: своё имя и авторизация, узел в дереве, вложенная иерархия папок
  внутри, удаляется целиком)
- **Самораcширение** — агент создаёт и правит свои инструменты, навыки и промпты
- **Skills** — наборы системных промптов, переключаемые прямо в чате
- **Библиотека промптов** — шаблоны с подстановкой `{{переменных}}`
- **Папки** — произвольная вложенность с drag-and-drop, включая чаты и файлы
- **Файлы** — ссылки на файлы диска без копирования содержимого
- **Голосовой ввод**, **прерывание агента**, **копирование кода**
- **Панель навигации** — сворачивается и меняет ширину, состояние запоминается
- **Метрики** — токены, размер контекста, статистика вызовов
- **Провайдеры и модели** — несколько провайдеров, у каждого свой набор моделей;
  быстрое переключение прямо в чате, и у каждого чата свой набор для этого
- **Политики безопасности** — режимы подтверждения от «отключено» до
  «максимальный», отдельные правила для MCP, белый список доменов, журнал решений
- **Ограничения** — итерации, время, таймауты, потолок вызовов
- **Экспорт/импорт** — архив со структурой папок, шифрование паролем
  (обязательное для tools/skills/промптов, необязательное для чатов)
- **Выгрузка и загрузка чата** — html, json, markdown, excel; поиск по всем чатам

`js/` разложен по подпапкам по роли кода (Цикл 25): `core` — БД, оркестратор,

движок инструментов целиком; `engines` — независимые движки без общего
префикса файлов (навыки, промпты, папки, файлы, безопасность); `ui` —

точка входа, подпапки не требует.

Порядок подключения важен: `crypto-utils.js` после `db.js`, `tools-engine.js`
перед остальными `tools/*.js`, `ui-core.js` перед остальными `ui/*.js` (он
объявляет класс, который те дополняют), `agent.js` после всех движков.


Затем `http://localhost:8000` → ⚙ **Настройки → Провайдеры и модели** →
добавить провайдера и его модели.

> часть Web Crypto API требуют защищённого контекста (HTTPS или localhost).

## Инструменты

**Общего назначения:** `get_current_time`, `calculator`, `http_fetch`,
`format_json`, `format_xml`, `generate_password`, `persistent_memory`,
`ask_user`, `list_workspace`, `export_chat`, `import_chat`, `export_chats`,
`import_chats`, `search_chats`,
`list_files`, `read_file`, `search_files`,
`explain_agent`, `diagnose`, `import_skill_from_text`

**Управление подключениями к LLM:** `llm_list`, `llm_status`, `llm_switch`,
`llm_test` — читают и меняют модель **текущего чата**; секреты через них не
отдаются, всё проходит через `sanitize()`.

**Самомодификация:** `create_tool`, `update_tool`, `create_skill`,
`update_skill`, `create_prompt`, `update_prompt`, `create_folder`,
`rename_folder`, `move_folder`, `delete_folder`, `move_item`, `chat_folder`, `move_chat`

**Собственные инструменты** описываются именем, описанием, JSON Schema
параметров и `handlerCode` — телом функции, получающей `params`. Тело
выполняется как тело **async-функции**, поэтому `await` доступен напрямую. Код
компилируется заново при каждом вызове, правки применяются без перезагрузки.

**MCP-серверы** — отдельная сущность (`mcp_servers`, Цикл 24), а не просто
URL, повторённый на каждом её tool. Подключаются по HTTP: инструменты
импортируются через `tools/list`, вызовы проксируются через JSON-RPC
`tools/call`. В дереве раздела Tools сервер — узел со своей папкой-
контейнером и произвольной вложенной иерархией подпапок внутри; имя и
токен редактируются, адрес — нет; удаление убирает сервер целиком со всеми
его инструментами и подпапками. Смешать в одном поддереве инструменты
разных серверов (или сервер с обычными папками) нельзя — перемещение
отклоняется при несовпадении области видимости источника и цели.

### Окно контекста

Определяется по названию модели (таблица известных семейств) либо задаётся
вручную — приоритет у ручного значения. API почти никогда не сообщает
`context_length`, поэтому автоматика приблизительна. При заполнении на 75 %
(настраивается) выводится предупреждение, при 100 % — предложение создать новый
чат.

| Формат | Результат |

## Экспорт и импорт объектов

Кнопки «📦 Экспорт» и «📥 Импорт» — в шапке каждой панели, работают со своим
разделом. Экспорт учитывает текущую папку: можно выгрузить только её, её со
вложенными или весь раздел, отметив объекты галочками.

Архив шифруется паролем: **PBKDF2-SHA256 (250 000 итераций) → AES-GCM-256**.
Ключ выводится из пароля, поэтому файл открывается на любой машине. GCM
гарантирует, что неверный пароль даст явную ошибку, а не тихий мусор.

При экспорте вырезаются токены MCP-серверов. При импорте папка с тем же именем
на том же уровне переиспользуется, а не дублируется; инструменты с собственным
кодом добавляются выключенными.

## Безопасность

### Политики подтверждения (`security-engine.js`)

Агент выполняет действия сам, по решению модели. Перед исполнением любого
инструмента `executeTool()` классифицирует операцию по последствиям (чтение,
изменение, удаление, сеть, исполнение кода, смена модели) и сверяется с
режимом:

| Режим | Что требует подтверждения |
|---|---|
| Отключено | ничего |
| Минимальный | необратимое: удаление папок, перезапись при импорте |
| Оптимальный | плюс создание/изменение инструментов, импорт навыков, сеть, подозрительные операции |
| Максимальный | любая операция, изменяющая данные, и чтение файлов; `create_tool`/`update_tool` запрещены полностью; сеть — только по белому списку |

Отдельная категория `mcp` — у MCP-вызова аргументы формирует модель и
отправляет на чужой сервер, а ответ уходит прямо в контекст: свой белый
список хостов, требование https, лимит размера ответа и вызовов за ход,
пометка ответа как данных, а не указаний. Строка, похожая на ключ доступа, в
аргументах вызова требует подтверждения всегда — даже на уже одобренном
сервере.

Код инструмента, создаваемого через `create_tool`, проверяется статическим
анализом на признаки выхода за рамки задачи (обращения к секретам, сети,
`eval`, decode-функции, буфер обмена) — находки показываются в диалоге
подтверждения, а не остаются голым вопросом «разрешить?». Журнал решений
(что запрошено, что разрешено, что заблокировано) доступен в настройках.

Граница механизма зафиксирована прямо в интерфейсе: политики ограничивают
действия **через инструменты**, но не изолируют код уже включённого
инструмента — тот выполняется в браузере и может обратиться к сети напрямую.
Главный барьер остаётся прежним: инструмент, созданный моделью, включает
пользователь вручную.

### Что реализовано на уровне кода

- **Экранирование HTML** в рендерере — ответ модели не исполняется как разметка
- **Инструменты создаются выключенными** — модель не может написать код и сразу
  его запустить
- **Шифрование секретов** в IndexedDB (AES-GCM, non-extractable ключ)
- **Ограничение `http_fetch`** — блокировка локальных и приватных адресов
- **Логирование выключено по умолчанию**
- **Лимиты и таймауты** на цепочку вызовов

Ограничения, которые стоит понимать:

- **`handlerCode` исполняется без песочницы** — через `AsyncFunction` в основном
  контексте страницы, с доступом к `fetch` и `window`. Подтверждение
  пользователем снижает риск, но не изолирует код. Полная изоляция требует
  Worker или sandboxed iframe.
- **Шифрование секретов не спасает от XSS** в том же источнике.
- **Таймаут не прерывает синхронный код** — JS не умеет прерывать выполняющуюся
  функцию.
- **SSRF-фильтр не защищает от DNS rebinding** — проверяется имя хоста, не
  итоговый IP соединения.
- **Стойкость архива определяется паролем** — PBKDF2 замедляет перебор, но
  слабый пароль остаётся слабым.

Первые два пункта закрываются одним архитектурным решением — выносом вызовов
LLM и исполнения инструментов на серверный прокси.

## Требования

Современный браузер с поддержкой IndexedDB, Web Crypto API и ES2020. Голосовой
ввод работает в Chrome и Edge (в Firefox Web Speech API по умолчанию отключён)
и требует HTTPS или localhost.

Счётчик токенов зависит от провайдера: запрашивается
`stream_options: {include_usage: true}`, при игнорировании этого поля значения
оцениваются локально и помечаются знаком `≈`.
