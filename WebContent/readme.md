# AI Agent — Personal Assistant

Клиентское веб-приложение: персональный AI-агент с поддержкой tool-calling, работающий целиком в браузере. Без бэкенда, без рантайм-зависимостей — только нативные Web API; для разработки и запуска сборка тоже не нужна (см. «Быстрый старт»). Данные хранятся локально в IndexedDB, запросы идут напрямую к любому OpenAI-совместимому API.

Для раздачи наружу есть отдельный необязательный шаг — продакшен-сборка с обфускацией в `dist/` (см. ниже).

Документ единый: сначала — актуальное состояние проекта, в конце — [история доработок](#история-доработок) по циклам. Раньше это были два файла (`readme.md` и `CHANGELOG-AND-OVERVIEW.md`), и описание состояния в них приходилось править синхронно — то есть оно неизбежно расходилось.

## Возможности

- **Чат с LLM** — потоковый вывод (streaming), поддержка любого OpenAI-совместимого эндпоинта; переключение между чатами во время генерации ответа не рвёт визуализацию и не путает, в какой чат что записано
- **Провайдеры и модели** — несколько провайдеров, у каждого свой набор моделей; быстрое переключение прямо в чате, и у каждого чата свой набор моделей для этого
- **Tools** — встроенные инструменты, инструменты со своим JS-кодом, запросы через локальный прокси (интранет, CORS, доменная аутентификация) и подключение внешних MCP-серверов; включаются поштучно или папкой целиком, выключенный инструмент модели не передаётся и не исполняется
- **Самораcширение** — агент умеет создавать и редактировать собственные инструменты, skills и промпты по ходу диалога
- **Skills** — наборы системных промптов, включаемые переключателем прямо в чате; каждому можно привязать инструменты, которыми он пользуется (многие-ко-многим). Есть неотключаемый навык «Системный», описывающий устройство самого агента
- **Библиотека промптов** — шаблоны с подстановкой переменных `{{var}}`
- **Внутренние вики** — Confluence и xWiki (On-Premise) через REST API: поиск, чтение и правка страниц
- **Файлы** — ссылки на файлы диска через File System Access API, без копирования содержимого
- **Папки** — произвольная вложенная иерархия для чатов/tools/skills/промптов/файлов с drag-and-drop
- **Политики безопасности** — режимы подтверждения действий агента от «отключено» до «максимальный», белые списки доменов и MCP-серверов, журнал решений
- **Оформление** — тема Системная / Тёмная / Светлая; все диалоговые окна строго модальны (клик мимо окна не закрывает форму)
- **Голосовой ввод** — диктовка сообщений через Web Speech API
- **Работа по частям и экономия контекста** — большие результаты инструментов выносятся из переписки в артефакты, длинная черновая работа выполняется подзадачей с чистым контекстом, ход задачи ведётся планом, а вытесняемое начало переписки сворачивается в резюме, а не теряется
- **Устойчивость к сбоям** — ход агента пишется в журнал: после закрытой вкладки или падения браузера работу можно продолжить с места остановки, а оборванные вызовы инструментов чинятся автоматически
- **Статистика** — израсходованные токены, размер контекста и метрики вызовов инструментов по каждому чату
- **Экспорт/импорт** — зашифрованный паролем архив с сохранением структуры папок; отдельно — экспорт/импорт самих чатов (html/json/markdown/excel, поиск по всем чатам)

`js/` разложен по подпапкам по **роли кода**, а не по предметным группам —
тот же принцип, что уже применён к разбивке `tools-*.js` и `ui-*.js` внутри
самих файлов:

| Подпапка | Что в ней |
|---|---|
| `core/` | БД, оркестратор, шифрование, markdown — то, на чём держится всё остальное |
| `llm/` | Клиент API и реестр провайдеров/моделей |
| `tools/` | Движок инструментов и все его модули (реестр, исполнение, встроенные tools, MCP) |
| `engines/` | Независимые движки без общего префикса файлов — навыки, промпты, папки, файлы, безопасность |
| `ui/` | Интерфейс — единый класс `UI`, разнесённый по файлам-примесям |
| `tests/` | Функциональные тесты на Node (`vm`-песочница и `jsdom`, без браузера) |

Рядом с `js/` лежит **`proxy/`** — необязательный Node-процесс (`proxy.js` + `config.js`) для инструмента `proxy_fetch`: он не входит в приложение, не подключается в `index.html` и запускается отдельно, когда нужны интранет-адреса, обход CORS или доменная аутентификация (см. «Запросы через локальный прокси»).

Порядок подключения в `index.html` важен: `crypto-utils.js` — после `db.js`, `tools-engine.js` — перед остальными `tools/*.js` (тот же приём примесей, что и у `ui/*.js`), `ui-core.js` — перед остальными `ui/*.js` (он объявляет класс, который те дополняют), а `agent.js` — после всех движков. Порядок между подпапками не поменялся при переносе — сменились только пути, ни один файл не переименован.

Разложив файлы, откройте `index.html` через локальный веб-сервер:

```bash
python3 -m http.server 8000
```

Затем перейдите на `http://localhost:8000` и в ⚙ **Настройки → Провайдеры и модели** добавьте провайдера (API URL, ключ, способ авторизации) и его модели — кнопкой «Загрузить у провайдера» (запрос `/models`) или вручную.

> Открытие через `file://` работать не будет: голосовой ввод и часть Web Crypto API требуют защищённого контекста (HTTPS или localhost).

## Продакшен-сборка

Для разработки сборка не нужна — см. «Быстрый старт» выше. Но для раздачи
наружу есть отдельный, необязательный шаг: `dist/` — самодостаточная
папка с одним обфусцированным JS-бандлом вместо 28 читаемых файлов.

```bash
npm install         # один раз — тянет devDependency javascript-obfuscator
npm run build       # собирает dist/ целиком
npm run smoke:proxy # необязательно: проверяет собранный dist/proxy/proxy.js вживую
```

Что оказывается в `dist/`:

| Файл | Как собран |
|---|---|
| `index.html` | исходный, но 27 тегов `<script>` заменены одним |
| `app.min.js` | все `js/**` склеены по порядку и обфусцированы **одним проходом** |
| `css/styles.css` | копия — обфусцировать CSS смысла нет |
| `proxy/proxy.js` | обфусцирован отдельным проходом с `target: 'node'` |
| `proxy/config.js` | копия — это файл настроек, его правят руками |

Скрипт сборки (`scripts/build-prod.js`) сам вычитывает порядок `<script>`
из `index.html` и склеивает файлы в этом же порядке в одну строку —
поведение не меняется, файлы и так делят один глобальный scope. Дальше
результат обфусцируется **одним проходом**, а не файл за файлом: у классов
вроде `ToolsEngine` или `UI` имя должно остаться одинаковым между файлом,
где класс объявлен, и файлами, что дополняют его прототип — обфускация по
отдельности почти гарантированно рассинхронизировала бы эти имена и
сломала бы приложение без единой ошибки при сборке.

Переименование верхнеуровневых имён (`renameGlobals`) выключено намеренно:
это не только связки между файлами, но и точка входа для отладки прямо в
консоли браузера (`agent.tools.debug = true`, `agent.llm.debug = true`).
Обфускация локальных переменных, строк и структуры внутри функций работает
как обычно и даёт основной эффект.

`proxy.js` обфусцируется **своим** проходом, а не вместе с бандлом: это код
для Node, и обфускатору об этом нужно сказать явно (`target: 'node'`),
иначе он добавит браузерные обёртки. Строка `'./config.js'` в `require`
оставлена нетронутой (`reservedStrings`) — пользователь кладёт `config.js`
рядом руками, и подмена этой строки превратила бы понятное «не найден
config.js» в невнятный сбой на старте.

Результат каждого прохода проверяется на разбираемость (`vm.Script`) прямо
в сборке: сломанный вывод обфускатора иначе обнаружился бы только у
пользователя — пустой страницей или падением прокси при запуске.

`dist/` коммитится в репозиторий как есть — вместе с `node_modules/`
инструмент сборки не нужен, чтобы просто раздать готовый продакшен-бандл
любым статическим веб-сервером.

## Архитектура

Приложение построено на классах в глобальной области видимости, без модулей и сборщика. Точка входа — `app.js`, создающий `AIAgent`, который поднимает остальные подсистемы.

Интерфейс разнесён по нескольким файлам `ui-*.js`, но остаётся **единым классом `UI`**: `ui-core.js` объявляет класс, остальные дополняют его через `Object.assign(UI.prototype, {...})`. Это позволяет разделить код по смыслу, не вводя сборщик и не меняя способ подключения через `<script>`.

### Хранилище

IndexedDB `ai_agent_db`, версия схемы **12**:

| Store | Ключ | Содержимое |
|---|---|---|
| `chats` | `id` | Чаты: заголовок, даты, папка (`parentId`), набор моделей (`modelRefs`/`modelRef`) |
| `messages` | `id` | Сообщения, включая tool-вызовы и их результаты |
| `tools` | `id` | Инструменты: встроенные, кастомные, MCP; `locked` — системные, их нельзя выключить |
| `skills` | `id` | Skills: системный промпт + `toolIds` (привязанные инструменты) + `locked` у системного |
| `prompts` | `id` | Шаблоны промптов |
| `folders` | `id` | Папки для всех разделов, включая чаты и файлы (поле `type`); у папки-контейнера MCP-сервера — `mcpServerId` |
| `files` | `id` | Ссылки на файлы: метаданные и дескриптор, без содержимого |
| `llm_connections` | `id` | Провайдеры LLM с вложенными моделями (ключ и заголовки зашифрованы) |

### Кастомные

Инструмент задаётся именем, описанием, JSON Schema параметров и `handlerCode` — телом JS-функции, получающей объект `params`. Код компилируется заново при каждом вызове, поэтому правки применяются без перезагрузки страницы.

### MCP-серверы

Сервер — отдельная сущность (`mcp_servers`), а не просто повторённый на каждом его tool URL. Подключение (кнопка «+ MCP Server» на вкладке Tools) спрашивает название, адрес и токен, импортирует инструменты через `tools/list`; вызовы проксируются через JSON-RPC `tools/call`, обработчики восстанавливаются при каждом старте приложения.

В дереве раздела Tools сервер — узел 🧩 со своей папкой-контейнером; все его инструменты живут внутри, организовать их можно произвольной вложенной иерархией подпапок. Название и токен сервера редактируются (адрес — нет, он совпадает с `mcpServer` у уже импортированных tools); удаление сервера убирает его целиком — все инструменты и подпапки. Перетащить инструмент или папку так, чтобы смешать содержимое разных серверов (или сервера с обычными папками), нельзя — перемещение отклоняется, если области видимости источника и цели не совпадают.

### Включение и выключение

У каждого инструмента — тумблер на карточке. Модель получает описание только включённых (`getEnabledToolsForAPI`), а `executeTool` вдобавок отказывает в вызове выключенного инструмента напрямую по имени — так модель не может обратиться к нему в обход тумблера, даже помня его из более раннего момента диалога, когда он ещё был включён.

У каждой папки в дереве раздела Tools — свой переключатель рядом с названием: включает или выключает разом все инструменты прямо в ней и во всех вложенных папках. Если часть включена, а часть нет, переключатель показывает промежуточное состояние; клик выравнивает всё содержимое папки в одну сторону.

### Связь навыков и инструментов

Навык можно привязать к инструментам, которыми он пользуется. Связь **многие-ко-многим**: у навыка сколько угодно инструментов, один инструмент — в сколь угодно многих навыках. Настраивается с обеих сторон и одинаково выглядит: в редакторе навыка — список инструментов с галочками и фильтром, на карточке инструмента — кнопка «🧩 Навыки» с таким же списком навыков. Видна связь тоже на обеих карточках: у навыка — его инструменты (выключенные зачёркнуты), у инструмента — навыки, где он задействован.

**Привязка не управляет доступностью.** Инструмент вызывается, только если включён его собственный тумблер; навык действует, только если включён он сам — эти переключатели работают ровно как раньше. Привязка отвечает на другой вопрос — «чем пользуется навык» — и попадает в системный промпт: активный навык перечисляет свои инструменты, а отдельной строкой называет привязанные, но выключенные, чтобы модель не пыталась их вызвать и сказала, какой именно нужно включить. `diagnose` сообщает о таких расхождениях отдельно.

Из инструментов агента связью управляют `link_skill_tools` (`add` / `remove` / `set` / `list`), `create_skill` и `update_skill` (параметр `tools`), а `list_workspace` отдаёт её в обе стороны. Удаление инструмента снимает его привязки, чтобы в навыках не оставалось ссылок на несуществующее.

Когда навык включают **чипом прямо в чате**, агент один раз показывает окно с его выключенными инструментами и предлагает включить отмеченные. Это происходит ровно в момент включения: постоянной проверки нет — состояние инструментов пользователь меняет сам и видит на вкладке Tools, а напоминание в каждом ответе быстро превратилось бы в шум. Расхождения в остальное время ловит `diagnose`.

### Запросы через локальный прокси

В папке `proxy/` лежит отдельный Node-процесс (`proxy.js` + `config.js`), который пользователь запускает сам:

```bash
node proxy/proxy.js     # порт и белый список хостов — в proxy/config.js
```

Инструмент **`proxy_fetch`** ходит через него и потому умеет то, чего не может `http_fetch`: не ограничен CORS, достаёт внутренние (интранет) адреса, поддерживает любые методы, тело и заголовки, а с `sso: true` — доменную аутентификацию текущего пользователя Windows (NTLM/Negotiate через `curl` на стороне прокси).

| | `http_fetch` | `proxy_fetch` |
|---|---|---|
| Путь | напрямую из браузера | через прокси на машине пользователя |
| Нужен запущенный процесс | нет | да |
| Внутренние адреса | запрещены | разрешены (кроме link-local и cloud-metadata) |
| CORS | ограничивает | не мешает |
| Методы | GET, POST | GET, POST, PUT, DELETE, PATCH, HEAD |
| Тело и заголовки | нет | тело; `Content-Type` и `Authorization` |
| Доменная аутентификация | нет | `sso: true` |
| По умолчанию | включён | **выключен** |

Правило выбора, зашитое в описания обоих инструментов: `http_fetch` — первый выбор для публичного интернета; `proxy_fetch` — когда цель внутренняя, `http_fetch` уже отказал из-за CORS или запрета адреса, нужен метод/тело/заголовок или доменная аутентификация. Автоматического переключения между каналами нет намеренно: молча подменять канал, у которого есть режим SSO, — плохая идея. Подробное правило вынесено в навык **«Работа через прокси»** с привязанными к нему обоими инструментами.

Параметры `proxy_fetch`: `url` (обязательный), `method`, `body`, `headers`, `sso`, `max_chars`. Адрес самого прокси в параметрах отсутствует намеренно — он берётся только из настроек, иначе модель могла бы назвать «прокси» любой хост и отправить туда тело и заголовки.

Настройки — ⚙ **Настройки → 🛡 Безопасность → «Локальный прокси»**: адрес, разрешение SSO и кнопка проверки связи.

**Файлы прокси можно не искать вручную.** Кнопка «📦 Сгенерировать файлы прокси» открывает форму (порт, белый список хостов, разрешённые методы, размеры, параметры curl для SSO) и собирает комплект: `config.js` с вашими значениями и сохранёнными комментариями, сам `proxy.js` и скрипты запуска `start-proxy.bat` / `start-proxy.sh`. Файлы предлагается сохранить в одну папку через выбор каталога; если браузер этого не умеет — скачиваются по одному. Адрес прокси при этом можно сразу прописать в настройках.

`proxy.js` не хранится копией внутри приложения, а забирается с того же адреса, откуда открыта страница (поэтому сборка кладёт `proxy/` и в `dist/`): вторая копия исходника рано или поздно разошлась бы с оригиналом.

В `dist/` файл `proxy.js` **обфусцирован** — отдельным проходом и своими настройками (`target: 'node'`), потому что это код для Node, а не для страницы. `config.js` при этом остаётся исходником: его правят руками, обфусцировать файл настроек значило бы сломать саму возможность настроить прокси. Обратная сторона: тот, кто получит комплект из продакшен-сборки, запустит у себя нечитаемый код, который в режиме SSO работает с его доменными правами. Если такой человек — не вы, дайте ему исходный `proxy/proxy.js` из репозитория: он совпадает с обфусцированным построчно, сборка ничего в него не добавляет.

Проверка собранного прокси — `npm run smoke:proxy`: поднимает реальный процесс из `dist/`, ставит рядом временный `config.js`, гоняет через него GET и POST к локальной цели и проверяет, что тело, заголовки и коды ошибок доходят как надо, а также выпускает настоящий самоподписанный сертификат и проверяет на нём все три уровня доверия TLS. Нужна именно потому, что обфусцированный файл уже не прочитать глазами.

**Про SSO.** Флаг необязательный и по умолчанию `false`. Запрос уходит с доменными правами пользователя, а адрес выбирает модель — в том числе под влиянием текста, пришедшего из внешнего источника. Поэтому: режим разрешается отдельной галочкой в настройках (по умолчанию выключена), а каждый вызов с `sso: true` подтверждается вручную — **в любом режиме безопасности, включая «отключено», и без варианта «больше не спрашивать про этот адрес»**. Один вопрос = один запрос с чужими правами.

### Сертификаты внутренних серверов

Внутренние серверы обычно предъявляют сертификат, выпущенный корпоративным удостоверяющим центром, которого нет в списке доверенных у Node. Такой запрос падает, и прокси отвечает **502**. В `proxy/config.js` для этого есть раздел `tls` — три варианта, от правильного к крайнему:

| Настройка | Что делает | Когда брать |
|---|---|---|
| `tls.caFile` | путь к PEM с вашим CA; проверка **остаётся включённой**, Node просто узнаёт про ваш центр | всегда, когда до файла CA можно добраться |
| `tls.insecureHosts` | не проверять сертификат только у перечисленных хостов (`corp.local` покрывает и поддомены) | до CA не добраться, а ходить нужно на один-два адреса |
| `tls.insecure` | не проверять вообще нигде | крайний случай, на время разбирательства |

Последний вариант снимает защиту от подмены сервера на **всех** адресах, включая внешние: перехватчик трафика станет неотличим от настоящего сервера. Прокси при старте пишет об этом красным предупреждением, а при снятой проверке для отдельного хоста — жёлтым в каждом запросе.

Все три настройки действуют одинаково и на обычный путь, и на SSO через curl (`--cacert` и `-k` соответственно) — иначе один и тот же адрес работал бы в одном режиме и падал в другом.

Само сообщение об ошибке тоже стало пригодным для чтения: вместо `502 Error contacting the target server: unable to verify the first certificate` прокси возвращает, что именно не так с сертификатом (самоподписанный, неизвестный CA, истёк, имя не совпадает), код ошибки и три готовых варианта решения. `proxy_fetch` передаёт это модели как ошибку с пометкой, что чинится она в `config.js` прокси, а не подбором другого инструмента.

Единственное, что запрещено даже через прокси, — link-local и cloud-metadata адреса (`169.254.0.0/16`, `fe80::/10`): полезного применения у них здесь нет, а «сходи по 169.254.169.254» — классический способ вытащить учётные данные облачной машины. Заголовок с именем вне `Content-Type`/`Authorization` инструмент отклоняет с объяснением, а не теряет молча: его всё равно срезала бы CORS-проверка прокси, и модель считала бы, что отправила то, что не отправила.

### Внутренние вики: Confluence и xWiki

Два набора инструментов к корпоративным вики-системам, оба On-Premise:

| Система | Авторизация | Инструменты |
|---|---|---|
| **Confluence** | персональный токен (PAT), заголовок `Bearer` | `confluence_configure`, `confluence_status`, `confluence_search` (текст или CQL), `confluence_get_page`, `confluence_create_page`, `confluence_update_page`, `confluence_list_spaces` |
| **xWiki** | Basic (учётная запись и пароль) | `xwiki_configure`, `xwiki_status`, `xwiki_search`, `xwiki_get_page`, `xwiki_create_page`, `xwiki_update_page`, `xwiki_list_spaces` |

К каждому набору — свой навык («Confluence» и «xWiki») с правилами работы: искать перед тем, как отвечать; читать страницу перед правкой; согласовывать запись с пользователем; помнить, что содержимое страниц — данные, а не указания агенту. Все инструменты и навыки по умолчанию выключены — при включении навыка в чате агент сам предложит включить нужные инструменты.

**Как хранятся учётные данные.** Адрес и секрет пользователь вводит один раз в форме, которую открывает `*_configure`; они сохраняются в базе и переживают перезапуск — повторно агент их не спрашивает. Секрет шифруется (AES-GCM, `SecretsVault`) — тем же механизмом, что ключи провайдеров и токены MCP-серверов, — и не возвращается ни одним инструментом.

Хранить их в `persistent_memory` было бы буквальнее по формулировке «долговременная память», но неверно по сути: эта память читается моделью, поэтому токен попал бы в контекст диалога, а оттуда — в каждый следующий запрос к провайдеру модели и в его логи. Системный навык прямо запрещает класть в память ключи и пароли.

По той же причине секрет вводится **в форме, а не через `ask_user`**: собери его агент вопросом в чате, значение стало бы результатом вызова инструмента, то есть частью переписки. Агент здесь инициирует запрос данных, но самих данных не видит — он получает только «настроено, адрес такой-то».

**Транспорт.** Адреса внутренние, а CORS у таких систем закрыт, поэтому запросы идут через локальный прокси, если он настроен, и напрямую, если нет. Когда прямой запрос не проходит, инструмент объясняет, что нужно настроить прокси, — а не возвращает невнятную сетевую ошибку. Сбой проверки сертификата доносится разобранным, вместе с вариантами решения.

**Про правку.** `*_update_page` заменяет содержимое страницы целиком, поэтому и в описании инструмента, и в навыке это выделено: сначала прочитать текущую версию, показать пользователю правку, дождаться согласия. Номер версии Confluence инструмент берёт с сервера сам — если бы его подставляла модель, правка молча уходила бы в конфликт. `xwiki_create_page` откажется трогать существующую страницу и подскажет `xwiki_update_page`, чтобы существующее не перезаписывалось по недоразумению.

Чтение возвращает текст без разметки: таблицы и макросы при этом теряются, и навык требует говорить об этом прямо, а не додумывать их содержимое.

### Системный навык и системные инструменты

Навык **«Системный»** нельзя выключить, удалить и **изменить** — он участвует в каждом запросе и описывает не роль, а устройство самого агента: память, подтверждение операций, судьбу выключенных инструментов, подрезку истории при переполнении контекста, момент вступления в силу смены модели, правила работы с файлами и самомодификации, требование не выдавать предположение за результат. Без этого каждый такой механизм выглядит для модели как необъяснимый сбой: отказ политики — как поломка инструмента, подрезка истории — как собственная забывчивость.

Неотключаемы и четыре инструмента, на которых эти механизмы держатся:

| Инструмент | Зачем |
|---|---|
| `persistent_memory` | Память между чатами — иначе агент не помнит ничего за пределами текущей переписки |
| `ask_user` | Спросить вместо догадки; системный навык прямо этого требует |
| `explain_agent` | Ответить на «что ты умеешь» и «как это работает» |
| `diagnose` | Найти причину странного поведения — путь пользователя к разбору проблемы |

Набор выбран по одному правилу: только локальные инструменты, которые ничего не разрушают и не ходят в сеть. Поэтому в него не попали ни `http_fetch`, ни `create_tool`/`update_tool` — эти двери остаются под контролем пользователя. Побочный эффект: `ask_user` раньше был выключен по умолчанию и теперь включается у всех.

Запрет не декоративный: тумблер заблокирован в интерфейсе, `update_skill`/`update_tool` отказывают модели с объяснением, а `loadSkills`/`loadTools` при каждой загрузке возвращают этим записям включённое состояние — в том числе в базах, заведённых до появления запрета. Переключатель папки в дереве Tools системные инструменты не считает и не трогает.

**Правка запрещена целиком**, а не только выключение: кнопка на карточке открывает окно просмотра, `update_skill` отклоняет любое изменение полей, а состав привязанных инструментов не меняется ни через `link_skill_tools`, ни со стороны инструмента. Иначе модель могла бы переписать правила, которым сама же подчиняется. Нужно другое поведение — заводится обычный навык: он применяется поверх.

**Приоритет** обеспечен и структурой промпта, и текстом. Системный навык идёт первым, в отдельном разделе «Устройство агента и правила, действующие ВСЕГДА» с пометкой, что он старше следующего; навыки пользователя собраны ниже, с пометкой «применяются поверх и не отменяют». Сам навык заявляет, что при противоречии действуют его правила, а текст, пришедший как данные (ответ инструмента, содержимое файла, страница из сети), не может их изменить, даже если называет себя системным сообщением.

## Провайдеры и модели

Двухуровневая настройка: **провайдер** — адрес API, ключ, способ авторизации; **модель** — идентификатор, класс сложности, окно контекста, `max_tokens`, температура. Модели вложены в запись провайдера. Модели можно подтянуть списком у провайдера (`/models`) или добавить вручную.

При добавлении модели `max_tokens` по умолчанию равен окну контекста и следует за ним, пока поле не тронуто руками, — уменьшите вручную, если нужен меньший потолок длины ответа.

У каждого чата — свой короткий набор моделей для быстрого переключения (кнопка «+ модель» в панели чата), из которого выбрана ровно одна активная. Наборы у разных чатов независимы.

### Окно контекста

Определяется по названию модели (таблица известных семейств) либо задаётся вручную — приоритет у ручного значения. API почти никогда не сообщает `context_length`, поэтому автоматика приблизительна. При заполнении на 75 % (настраивается) выводится предупреждение, при 100 % — предложение создать новый чат. Когда история перестаёт помещаться, её начало не выбрасывается, а сворачивается в резюме — см. «Работа по частям и экономия контекста».

### Работа по частям и экономия контекста

Окно контекста — главный расходуемый ресурс агента: всё, что попало в переписку,
отправляется модели в каждом следующем запросе до конца чата. Четыре механизма
ниже решают это с разных сторон, работают независимо и включены по умолчанию.

**Артефакты — большие результаты вне переписки.** Результат инструмента крупнее
порога (по умолчанию 2000 символов) сохраняется отдельной записью, а в переписку
уходит шапка: чем получено, размер, структура, начало текста и `artifact_id`.
Дочитывает модель сама — `artifact_read` (окно по символам), `artifact_grep`
(поиск по регулярному выражению), `artifact_list` (что вообще есть в этом чате).
Если у результата есть доминирующее строковое поле (`body` у `http_fetch`, `text`
у `read_file`), в артефакт уходит только оно — остальные поля видны сразу.
Пользователь открывает полный текст кнопкой в блоке вызова. Место на диске от
этого не растёт: тот же текст раньше лежал в сообщении. Удаляются вместе с чатом.

**Подзадачи — часть работы отдельным ходом.** `run_subtask` выполняет кусок
задачи в отдельном чате с чистым контекстом: свой системный промпт, своя
переписка, свои артефакты, при желании — своя, более дешёвая модель. В основной
разговор возвращается только итог, поэтому подзадача из двадцати шагов стоит там
один короткий ответ. Подзадача не видит переписку родителя (всё нужное передаётся
в `goal` и `context`) и не может запускать вложенные подзадачи. Действуют бюджет
времени хода и кнопка останова; у самой подзадачи свой потолок шагов. Её переписка
в списке чатов скрыта, открывается кнопкой из блока вызова и удаляется вместе с
родительским чатом.

**План задачи — состояние работы вне переписки.** `task_plan` хранит цель, шаги,
их состояние и попутно выясненные факты. Компактная сводка подставляется в
системный промпт при каждом запросе, поэтому «что сделано и что осталось»
переживает и подрезку истории, и перезагрузку страницы. Пользователь видит то же
самое: чип в панели чата и окно со списком шагов, откуда план можно прекратить.
Один активный план на чат.

**Свёртка вместо потери.** Когда история перестаёт помещаться в окно, вытесняемая
часть один раз прогоняется через модель и превращается в структурированное
резюме — задача, сделанное, выясненное, решения, открытые вопросы, — которое
дальше едет в запросы вместо покрытых сообщений. Раньше на этом месте оставалась
заглушка «попроси пользователя повторить», то есть работа начала разговора для
агента просто исчезала. Свёртка стоит одного дополнительного запроса и делается
только при реальном переполнении; при сбое работает прежнее поведение, ответ не
срывается. Отдельно и без всякой модели старые результаты инструментов (кроме
последних шести) уходят в запрос сокращёнными, с пометкой, где взять полный текст.

### Устойчивость к сбоям и возобновление

Ход агента живёт в памяти вкладки, поэтому её закрытие, обновление страницы или
падение браузера обрывали работу молча. Хуже того, обрыв посреди цепочки
инструментов оставлял в истории вызов без результата — а такой запрос провайдер
отвергает целиком, и чат становился нерабочим совсем.

Теперь ход пишется в журнал (`runs`): стадия, номер шага, модель и накопленный,
но ещё не сохранённый текст ответа — не чаще раза в полторы секунды, чтобы не
тормозить стриминг. При следующем запуске ходы, оставшиеся в состоянии
«выполняется», разбираются:

- недописанный ответ сохраняется в переписку с пометкой «прерван»;
- незакрытые вызовы инструментов получают честный результат «выполнение прервано»,
  и цепочка снова становится валидной;
- в чате появляется предложение продолжить с места остановки — с указанием, на
  какой стадии всё оборвалось.

Возобновление не создаёт нового сообщения пользователя: агент продолжает с той
истории, что уже есть, включая результаты инструментов, успевшие выполниться.
Само оно не запускается — после сбоя решение принимает пользователь: автоматический
перезапуск повторил бы действие, из-за которого всё и упало, и потратил бы деньги
на ход, который может быть уже не нужен. Пока агент работает, браузер
предупреждает при попытке закрыть вкладку.

### Переключение между чатами во время генерации ответа

Состояние хода (стриминг, статус-панель, счётчики) привязано к конкретному чату, а не к приложению в целом: пока один чат ждёт ответ модели, можно свободно смотреть любые другие — их отрисовка не пострадает, а при возврате в отвечающий чат восстановятся и уже полученный текст, и индикатор хода. Общий шлюз LLM обслуживает один запрос за раз — попытка отправить сообщение в другом чате в это время не срабатывает молча, а показывает, в каком именно чате идёт ответ. В списке чатов отвечающий сейчас чат помечен спиннером.

## Настройки

Окно ⚙ разделено на вкладки. Как и все прочие диалоги приложения, оно строго модально: клик мимо окна не закрывает его — почти в каждой форме лежат несохранённые правки, и промах мышью не должен их стирать. Закрыть можно кнопками «Отмена»/«Сохранить» или клавишей Esc (равносильна «Отмене»).

- **🔌 Провайдеры и модели** — список провайдеров и их моделей, порог предупреждения о заполнении контекста
- **⏱ Ограничения** — лимиты работы агента при вызове инструментов
- **👁 Отображение** — тема оформления, детализация вывода tool-вызовов, навыки и файлы в контексте чата
- **🛡 Безопасность** — режим подтверждения операций агента, белые списки доменов и MCP-серверов, потолки изменений, локальный прокси, журнал решений
- **🪵 Журналирование** — подробные логи запросов к LLM и вызовов инструментов в консоль

### Тема оформления

Три варианта: **Системная** (по умолчанию, следует за `prefers-color-scheme` браузера/ОС), **Тёмная**, **Светлая**. Переключатель — на вкладке «👁 Отображение». Реализовано через один атрибут `data-theme` на `<html>` и переменные CSS в `styles.css`: явный выбор задаёт атрибут (`light`/`dark`), «Системная» его снимает и отдаёт решение медиа-запросу. Выбор сохраняется (`settings/theme`) и применяется сразу при следующем запуске, до отрисовки интерфейса.

### Ограничения работы агента

Применяются к одному ответу — всей цепочке вызовов, запущенной сообщением пользователя. Значение `0` отключает лимит.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| Итерации tool-calling | 25 | Защита от зацикливания модели на вызовах |
| Бюджет времени на ответ | 180 с | Прерывает запрос через `AbortController` |
| Таймаут одного инструмента | 30 с | Зависший инструмент вернёт ошибку вместо блокировки. Действует на все каналы, включая MCP |
| Вызовов за ответ | 50 | Суммарный потолок |
| Предел ответа инструмента | 20 000 символов | Сколько чужого ответа пустить в контекст. Общий для MCP, `proxy_fetch` и `http_fetch` |
| Выносить результат в артефакт от | 2000 символов | Крупнее этого порога результат сохраняется отдельно, а модели уходит шапка с `artifact_id`. `0` — передавать всё целиком, как раньше |
| Максимум шагов внутри подзадачи | 10 | Собственный потолок итераций у `run_subtask`; агент может запросить меньший |
| Сворачивать переписку вместо потери начала | включено | Вытесняемая часть сжимается моделью в резюме (один дополнительный запрос в момент переполнения) |

Предел ответа и таймаут намеренно заданы **по одному разу на все внешние каналы**. Раньше предел существовал в трёх видах — своя настройка у MCP-серверов, своя у прокси и зашитые 4000 символов внутри `http_fetch`, — а таймаут в двух, хотя смысл везде один и тот же; при разных значениях оставался вопрос, какое из них сработало. У MCP осталось только то, чего у остальных нет: свой, более узкий потолок числа вызовов за ответ. Параметр `max_chars` у `proxy_fetch` может предел **понизить**, но не поднять — иначе модель обходила бы настройку пользователя одним аргументом.

## Экспорт чата и поиск

Инструмент `export_chat` выгружает переписку с хронологией в один из форматов:

| Формат | Что получается |
|---|---|
| `html` | Самодостаточный документ со встроенными стилями, готовый к просмотру |
| `json` | Структурированные данные со статистикой чата |
| `markdown` | Текст с заголовками ролей и блоками кода |

его в браузере без внешней библиотеки нельзя. Выгружается HTML-таблица с расширением
`.xls`, которую Excel и LibreOffice открывают штатно.

Инструмент `search_chats` ищет подстроку по всем чатам (или в одном), возвращая
фрагменты вокруг совпадений с указанием чата, роли и даты. Поиск буквальный, не
семантический; есть фильтры по роли автора и учёту регистра.

## Экспорт и импорт

Кнопки «📦 Экспорт» и «📥 Импорт» находятся в шапке каждой панели (Tools, Skills, Промпты) и работают со своим разделом. Экспорт учитывает текущую папку: можно выгрузить только её, её вместе с вложенными или весь раздел, отметив конкретные объекты галочками.

Архив вместе со структурой папок шифруется паролем: **PBKDF2-SHA256 (250 000 итераций)** → **AES-GCM-256**. Файл открывается на любой машине — ключ выводится из пароля, а не из локального хранилища.

При экспорте встроенные инструменты пропускаются (создаются автоматически при запуске), а токены MCP-серверов вырезаются из архива. При импорте доступны режимы «добавить» и «перезаписать».

## Безопасность

### Политики подтверждения

Перед выполнением любого инструмента `security-engine.js` классифицирует
операцию по последствиям (чтение, изменение, удаление, сеть, исполнение
кода, смена модели) и сверяется с режимом, выбранным во вкладке
🛡 **Безопасность**:

| Режим | Что требует подтверждения |
|---|---|
| Отключено | ничего |
| Минимальный | необратимое: удаление папок, перезапись при импорте |
| Оптимальный | плюс создание/изменение инструментов, импорт навыков, сеть, подозрительные операции |
| Максимальный | любая операция, изменяющая данные, и чтение файлов; `create_tool`/`update_tool` запрещены полностью; сеть — только по белому списку |

У MCP-вызовов отдельная, более строгая категория: аргументы формирует
модель и отправляет на чужой сервер, а ответ уходит прямо в контекст —
поэтому свой белый список хостов, требование https, пометка ответа как
данных, а не указаний, и отдельный потолок вызовов за ход. Строка, похожая
на ключ доступа, в аргументах требует подтверждения всегда — даже на уже
одобренном адресе. Запрос через `proxy_fetch` с `sso: true` подтверждается
всегда и в любом режиме, включая «отключено» (см. «Запросы через локальный
прокси»). Все решения — разрешено, отклонено, заблокировано — попадают в
журнал.

Граница механизма: политики ограничивают действия **через инструменты**, но
не изолируют код уже включённого инструмента — тот выполняется в браузере и
может обратиться к сети напрямую. Поэтому созданный моделью инструмент
всё равно включает пользователь вручную.

### Что реализовано на уровне кода

- **Экранирование HTML** в markdown-рендерере — ответ модели не может выполниться как разметка, ссылки с `javascript:`/`data:` блокируются
- **Системные инструменты нельзя выключить.** Память, вопрос пользователю, объяснение устройства и самодиагностика доступны всегда — на них держатся базовые механизмы агента; в этот набор намеренно не попали сетевые и создающие код инструменты
- **Инструменты создаются выключенными.** Инструмент, созданный или изменённый моделью, требует ручного включения пользователем — модель не может одним вызовом написать код и сразу его запустить
- **Выключенный инструмент не исполняется.** Он не только не попадает в схему function-calling, но и отклоняется исполнителем при прямом вызове по имени — тумблер нельзя обойти, сославшись на инструмент из более раннего момента диалога
- **Шифрование секретов.** API-ключи и MCP-токены хранятся в IndexedDB зашифрованными (AES-GCM, ключ non-extractable), а не открытым текстом
- **Ограничение `http_fetch`.** Заблокированы не-HTTP(S) протоколы и обращения к `localhost`, приватным подсетям и cloud-metadata адресам
- **Логирование выключено по умолчанию** — иначе переписка и аргументы инструментов писались бы в консоль

Известные ограничения, о которых стоит знать:

- **`handlerCode` исполняется без песочницы** — через `AsyncFunction` в основном контексте страницы, с доступом к `fetch` и `window`. Подтверждение пользователем снижает риск, но не изолирует код. Полная изоляция требует Worker или sandboxed iframe.
- **Шифрование секретов не защищает от XSS** в том же источнике: код на странице может вызвать расшифровку так же, как это делает приложение. Защищает от просмотра БД через DevTools, расширения и бэкапы профиля.
- **Таймаут инструмента не прерывает синхронный код** — JS не умеет прерывать выполняющуюся функцию. Зависший в цикле handler продолжит занимать поток.
- **SSRF-фильтр не защищает от DNS rebinding** — проверяется имя хоста из URL, а не итоговый IP соединения.
- **Стойкость архива определяется паролем** — PBKDF2 замедляет перебор, но слабый пароль остаётся слабым.

Радикальное решение первых двух пунктов — вынести вызовы LLM и исполнение инструментов на серверный прокси, чтобы секреты и чужой код вообще не попадали в браузер.

## Требования

Современный браузер с поддержкой IndexedDB, Web Crypto API и ES2020. Голосовой ввод работает в Chrome и Edge (в Firefox Web Speech API по умолчанию отключён) и требует HTTPS или localhost.

Счётчик токенов зависит от провайдера: в потоковом режиме запрашивается `stream_options: {include_usage: true}`, и если API это поле игнорирует, статистика токенов останется пустой.

# История доработок

Журнал циклов: что менялось, почему и какой ценой. Разделы выше описывают
актуальное состояние — здесь только хронология, включая причины решений,
которые из готового кода уже не видны, и найденные по дороге ошибки.

## Цикл 1. Аудит и критические исправления

Первичный разбор кода выявил проблемы, из которых три были отнесены к
критическим и исправлены сразу.

### XSS через рендерер markdown

`renderMarkdown()` собирал HTML регулярками поверх сырого текста и **не
экранировал ничего**, а результат вставлялся через `innerHTML`. Содержимое
ответа модели полностью контролируется LLM-провайдером (адрес которого
пользователь вписывает сам), поэтому конструкция вида `<img src=x
onerror=...>` в ответе исполнялась бы в контексте страницы — там, где лежат
ключи API и вся история переписки.

Исправлено: текст экранируется **первым шагом**, разметка применяется уже к
безопасной строке. Отдельно блокируются схемы `javascript:`, `data:`,
`vbscript:` в ссылках — экранирование спецсимволов их не нейтрализует.

### Бесконечная рекурсия tool-calling

Цепочка вызовов инструментов рекурсивно вызывала `_generateResponse()` без
счётчика. Зацикливание модели на инструментах (обычное дело для локальных и
слабых моделей) означало исчерпание стека и неограниченный расход токенов.

Исправлено: счётчик глубины с лимитом и понятной остановкой. Позже развёрнуто
в полноценную систему ограничений (цикл 4).

### Автоматическая активация инструментов, созданных моделью

`create_tool` включал новый инструмент сразу (`enabled: params.enabled !== false`),
а `handlerCode` исполнялся через `new Function` без песочницы. В сочетании с
`http_fetch` это давало прямой путь: враждебный текст со стороннего сайта →
prompt injection → модель создаёт инструмент, читающий ключи из IndexedDB и
отправляющий их наружу → инструмент немедленно вызывается.

Исправлено:
- новый инструмент **всегда** сохраняется выключенным, независимо от запроса модели;
- убран «сухой прогон» — раньше непроверенный код исполнялся уже при создании;
- `update_tool` при смене `handlerCode` принудительно выключает инструмент, даже
  если в том же вызове передан `enabled: true`;
- описания инструментов переписаны так, чтобы модель сообщала пользователю о
  необходимости включить инструмент вручную.

## Цикл 2. Безопасность и чистка

- **SSRF в `http_fetch`.** Разрешены только `http`/`https`; заблокированы
  `localhost`, приватные подсети (`10.x`, `172.16–31.x`, `192.168.x`), loopback
  и link-local, включая cloud-metadata `169.254.169.254`.
- **Логирование под флагом.** Полное содержимое запросов, ответов и аргументов
  инструментов писалось в консоль безусловно. Вынесено под `debug`, по
  умолчанию выключено.
- **MCP-инструменты переживают перезагрузку.** Обработчики жили только в
  памяти, после `F5` вызовы падали с «No handler registered». Добавлено
  восстановление при старте.
- **Убрано дублирование.** Логика папок существовала в трёх копиях; операции
  сведены к `FoldersEngine`. Удалён мёртвый код (`_renderHierarchy` и
  закомментированные старые версии методов — сотни строк).
- **Порядок скриптов.** `folders-engine.js` подключался последним, а
  использовался раньше — работало лишь по случайности тайминга.

## Цикл 3. Шифрование секретов

Ключи API и токены MCP хранились в IndexedDB открытым текстом.

Добавлен `SecretsVault` (AES-GCM-256, ключ **non-extractable** — его нельзя
выгрузить в сырые байты даже кодом страницы). Предусмотрена обратная
совместимость: ранее сохранённые значения читаются как есть и перешифровываются
при следующем сохранении.

Границы защиты зафиксированы прямо в коде: она закрывает просмотр базы через
DevTools, расширения и бэкапы профиля, но **не защищает от XSS в том же
источнике** — код на странице может вызвать расшифровку так же, как это делает
приложение. Радикальное решение — серверный прокси, чтобы секреты вообще не
попадали в браузер.

## Цикл 4. Управление настройками

- Окно настроек разделено на **вкладки** вместо одной длинной формы.
- Добавлены **ограничения работы агента**: итерации, бюджет времени на ответ
  (через `AbortController`), таймаут одного инструмента, потолок вызовов за ход.
- Добавлена **настраиваемая детализация** вывода вызовов инструментов.
- **Журналирование** получило переключатели в интерфейсе; выбор сохраняется
  между сессиями (раньше — только через консоль, сбрасывалось на `F5`).

## Цикл 5. Чат и перенос данных

- **Голосовой ввод** (Web Speech API) с обработкой типовых ошибок и честным
  сообщением, если браузер не поддерживает.
- **Быстрый выбор модели** в панели чата.
- **Счётчик токенов и статистика инструментов**, хранящиеся в отдельном store
  `chat_stats`.
- **Экспорт/импорт с паролем**: PBKDF2-SHA256 (250 000 итераций) → AES-GCM-256.

## Цикл 6. Исправления по замечаниям

- **Статистика токенов не менялась.** Причина: большинство провайдеров
  игнорируют `stream_options` и не присылают `usage` при стриминге. Добавлена
  локальная оценка по объёму текста, помеченная знаком `≈`, плюс живое
  обновление панели после каждого запроса и вызова.
- **Выход блока за рамку.** Длинные JSON и URL не переносятся сами; добавлены
  `overflow-wrap: anywhere` и `min-width: 0` (обязателен для flex-элементов).
- **Прокрутка в окне настроек.** Введён широкий режим модалки и двухколоночная
  сетка.

## Цикл 7. Ошибка `await is only valid in async functions`

Код инструментов компилировался через `new Function`, создающий **синхронную**
функцию, тогда как системный промпт обещал модели поддержку `async`. Модель
писала `await fetch(...)`, получала синтаксическую ошибку, затем пыталась
обойти её через async IIFE — и цикл повторялся.

Исправлено: компиляция через `AsyncFunction`, тело `handlerCode` теперь
является телом async-функции, `await` работает напрямую. Инструкции для модели
приведены в соответствие с фактическим поведением.

Одновременно исправлены **дубли папок при импорте**: сопоставление шло только
по `id`, а у одной и той же по смыслу папки на другой машине `id` другой.
Добавлено сопоставление по имени в пределах уровня с перемаппингом `parentId`.
Импорт стал идемпотентным.

## Цикл 8. Контекст, прерывание, выборочный экспорт

- **Кнопка прерывания агента** — обрывает HTTP-запрос и останавливает цепочку
  между шагами.
- **Размер контекста** последнего запроса рядом со счётчиком токенов.
- **Окно контекста модели** — таблица известных семейств плюс ручная настройка
  (API почти никогда не сообщает `context_length`).
- **Предупреждения** при достижении порога и при исчерпании контекста — с
  предложением создать новый чат.
- **Выборочный экспорт** с отметкой конкретных объектов и учётом текущей папки.

## Цикл 9. Финальные исправления и реинжиниринг

- **Импорт отдельной кнопкой** в каждой панели; полное окно из настроек убрано.
- **Кнопка останова скрывается** сразу после нажатия.
- **Копирование кода** из чата с запасным путём для незащищённого контекста.
  Попутно исправлен давний баг рендерера: замена `\n → <br>` применялась внутри
  `<pre>`, из-за чего в коде двоились переносы, а `*` и `#` превращались в разметку.
- **Новые инструменты** `export_chat` и `search_chats`.
- **Разбиение `ui.js`** (2400 строк) на семь модулей.

### Об исправленных регрессиях

Две правки в этом цикле чинили последствия предыдущих:

- добавленный ранее `overflow-x: auto` попал в общий класс блока вызова
  инструмента и включил ненужную прокрутку в кратком режиме;
- список выборочного экспорта молча отбрасывал встроенные инструменты, из-за
  чего состав папки в окне не совпадал с тем, что видно на экране.

Обе устранены. Второй случай вскрыл смежный дефект импорта: встроенные
инструменты существуют локально всегда, поэтому общая проверка на дубликаты
отсекала их раньше, чем доходило до переноса размещения — папка встроенного
инструмента не восстанавливалась никогда.

## Цикл 10. Организация чатов

Чаты были единственным разделом без иерархии — плоский список, отсортированный
по дате. При десятках чатов ориентироваться в нём невозможно.

### Папки чатов

Иерархия чатов построена на том же `FoldersEngine`, что и у Tools/Skills/Prompts
(тип `chats`), — отдельной реализации не появилось. Отличие в отрисовке: у
остальных разделов элементы живут в панели справа, а чаты открываются кликом
прямо в дереве, поэтому они рисуются внутри самого дерева сайдбара.

Управление — и кнопками (`＋` подпапка, `✏` переименовать, `✕` удалить), и
перетаскиванием: чат можно перенести в папку, папку — в другую папку. Защита от
вложения папки в собственного потомка досталась от `FoldersEngine.move()`. При
удалении папки её чаты и подпапки поднимаются на уровень выше — сами чаты не
удаляются.

Добавлены встроенные инструменты, дающие агенту тот же набор операций:

- `chat_folder` — создание, переименование, перемещение, удаление, список папок
- `move_chat` — перемещение чата (по id или названию; без аргумента — текущий)

### Метка времени и текущая папка

Новый чат создаётся в папке, выбранной в дереве, и получает заголовок с датой и
временем вместо одинакового «Новый чат» — иначе список из десятка одноимённых
записей нечитаем. В дереве у каждого чата показывается время последнего
изменения.

### Импорт чата

Инструмент `import_chat` принимает содержимое JSON-выгрузки (формат
`export_chat`) и восстанавливает переписку в новом чате. Порядок сообщений
задаётся заново по возрастанию: исходные метки времени могут совпадать или
отсутствовать.

Попутно обнаружился пробел в самом экспорте: JSON-выгрузка не сохраняла поле
`model`, поэтому при обратном импорте терялась информация о том, какая модель
сформировала каждый ответ. Добавлены `model` и `tool_call_id`; round-trip
проверен тестом.

### Кнопки экспорта и импорта чата

В подвале сайдбара (видны только на вкладке чатов). Работают **через встроенные
инструменты** `export_chat` и `import_chat`, а не дублируют их логику — формат
выгрузки одинаков независимо от того, кто её инициировал: пользователь кнопкой
или агент вызовом инструмента.

### Тайминг и модель в истории

Под каждым ответом ассистента выводится подпись: время, модель-автор и
длительность генерации. Модель берётся **из самой записи сообщения**, а не из
текущих настроек, — иначе после смены модели старые ответы задним числом
«переприписывались» бы новой. Замер идёт вокруг обращения к модели; при
стриминге подпись дописывается к уже отрисованному ответу без его перерисовки.

## Цикл 11. Панель навигации, тайминги и перенос чатов

### Сворачиваемая и растягиваемая панель

Ширина панели навигации задавалась переменной `--sidebar-w`, которую использует
grid-раскладка, — поэтому и сворачивание, и изменение размера сводятся к
управлению одной величиной. Кнопка в шапке сворачивает панель целиком (колонка
схлопывается в ноль), правую границу можно перетаскивать в пределах 180–640 px,
двойной клик по разделителю возвращает ширину по умолчанию.

Состояние сохраняется в `settings/layout` и восстанавливается при запуске.
Использовано собственное хранилище приложения, а не `localStorage`: заводить
второй механизм ради двух чисел незачем.

### Тайминг запроса пользователя

Раньше длительность показывалась только у ответа ассистента и охватывала одну
генерацию. Теперь у сообщения пользователя выводится **полное время обработки
хода** — от отправки до финального ответа, включая все вызовы инструментов.
Значение становится известно уже после отрисовки сообщения, поэтому подпись
обновляется точечно по `data-msg-id`, без перерисовки переписки.

### Отметка смены модели в истории

При отправке сообщения текущая модель сравнивается с той, что была записана в
чате; при расхождении в переписку добавляется служебная запись
`kind: 'model-switch'`. Без такой отметки в чате со сменой модели невозможно
понять, где проходит граница между ответами разных моделей.

Важная деталь: служебные записи **исключены из контекста, отправляемого в API**.
Иначе они попали бы туда вторым `system`-сообщением и сбивали бы модель.

### Массовый экспорт и импорт чатов

Инструменты `export_chats` и `import_chats` переносят чаты целиком: переписку,
структуру папок (со всей цепочкой родителей), статистику чата, а также модель-
автор каждого ответа, время генерации и время обработки запроса. Кнопки в
подвале сайдбара вызывают эти же инструменты, а не дублируют их логику.

Экспорт даёт выбрать конкретные чаты (по умолчанию отмечены те, что лежат в
текущей папке). Импорт поддерживает режимы «добавить» и «перезаписать»; при
перезаписи старые сообщения чата удаляются, иначе они удвоились бы. Папка с тем
же именем на том же уровне переиспользуется — то же правило, что и при импорте
разделов.

### Попутно исправлено

Автоматическое переименование чата по первому сообщению сверялось со строкой
«Новый чат», хотя предыдущий цикл сменил формат заголовка на «Чат ДД.ММ, ЧЧ:ММ»
— то есть переименование молча перестало работать. Проверка заменена на шаблон,
понимающий оба формата.

## Цикл 12. Прерывание хода и обрыв ответа

Две жалобы («кнопка останова остаётся активной после срабатывания лимита» и
«ответ выглядит неполным») оказались проявлениями трёх разных дефектов.

### Кнопка останова оставалась активной

Перед рекурсивным переходом к следующему шагу цепочки стоял сырой сброс
состояния — `isStreaming = false` и `send-btn.disabled = false`, минуя
`_setBusy()`. Два следствия:

1. Кнопка останова при этом не скрывалась, а следующий шаг снова показывал её.
2. Между шагами открывалось окно, в котором `sendMessage()` пропускал новое
   сообщение — запускалась **вторая цепочка параллельно первой**. Две цепочки
   затирали состояние друг друга: одна завершалась и сбрасывала флаги, вторая
   продолжала работу с уже «свободным» интерфейсом.

Исправлено введением единственного владельца состояния: занятость снимает
только корневой кадр цепочки (`depth === 0`), и делает это в `finally` — то
есть на любом пути выхода, включая `return` из середины цикла вызовов
инструментов, прерывание по таймауту и необработанную ошибку. Вложенные кадры
и `_stopTurn()` больше не трогают занятость. Поведение проверено симуляцией
модели состояния: воспроизведён прежний дефект и подтверждено исправление.

### Частичный ответ терялся при прерывании

Запись ответа в БД выполнялась **после** `await` на запросе к модели. При
прерывании — по таймауту хода или кнопкой «⏹» — уже полученный и отрисованный
текст никуда не сохранялся: ответ выглядел неполным, после перезагрузки чата
исчезал совсем и не попадал в контекст следующего запроса.

Теперь частичный текст сохраняется с пометкой `interrupted`, отображается в
подписи и остаётся в истории. Сообщение о таймауте дополнено указанием, что
полученная часть сохранена, и подсказкой, где менять лимит.

### Обрыв по лимиту токенов был невидим

`finish_reason` возвращался только в отладочный лог не-потоковой ветви, а в
стриминге не захватывался вовсе. Ответ, обрезанный провайдером на
`max_tokens` (по умолчанию 4096), внешне не отличался от завершённого — это и
выглядело как «не хватило памяти».

Gateway теперь возвращает `finish_reason` из обеих ветвей (в стриминге он
приходит отдельным чанком). При значении `length` ответ помечается как
`truncated`, под ним появляется предупреждение с фактическим значением
`max_tokens` и кнопка «Продолжить ответ»: она отправляет запрос на продолжение,
а обрезанный ответ уже лежит в истории, поэтому модель видит, где остановилась.

### Что делать при повторении

- **Лимит 180 с срабатывает регулярно** — увеличьте бюджет времени в
  ⚙ Настройки → Ограничения либо сократите число итераций tool-calling;
  на медленных или локальных моделях цепочка из нескольких вызовов
  инструментов легко выходит за три минуты.
- **Ответы обрываются** — поднимите `max_tokens` в ⚙ Настройки → Модель.
  Значение 4096 мало для длинных разборов кода; ориентир — несколько десятков
  тысяч для моделей с большим окном контекста.

## Цикл 13. Индикация работы и шифрование архива чатов

### Что происходит прямо сейчас

Во время работы висели три статичные точки, которые к тому же убирались перед
вызовами инструментов — то есть на самом долгом этапе пользователь не видел
вообще ничего и не мог отличить работу от зависания.

Теперь показывается панель состояния с текущей стадией: отправка запроса, сбор
контекста, ожидание ответа, потоковая генерация, выполнение конкретного
инструмента (с его именем и номером вызова), обработка результата, остановка.
Рядом — счётчик прошедшего времени и, если бюджет задан, остаток: `47 с из 180`.
При приближении к границе счётчик подсвечивается, чтобы обрыв по таймауту не
становился неожиданностью.

Таймер запускается один раз на весь ход, а не на каждую стадию: важно общее
время ожидания, а не длительность отдельного шага.

### Необязательное шифрование архива чатов

Массовая выгрузка чатов получила ту же опцию, что уже была у tools/skills/
промптов: галочка «Зашифровать архив паролем» в окне экспорта. Применяется тот
же механизм — PBKDF2-SHA256 (250 000 итераций) → AES-GCM-256.

Шифрование именно **необязательное**: без пароля файл остаётся обычным JSON,
который удобно просматривать и обрабатывать сторонними средствами. С паролем
получается конверт формата `ai-agent-archive-v1`, а к имени файла добавляется
`.enc`.

При импорте пароль спрашивать не нужно: формат определяется автоматически по
полю `format`. Если архив зашифрован, а пароль не введён, инструмент возвращает
`needsPassword`, и интерфейс подсказывает это отдельным сообщением вместо сухой
ошибки. Параметр `password` добавлен и в описания инструментов `export_chats` /
`import_chats` — агент может пользоваться шифрованием наравне с пользователем.

Проверено тестом: без пароля содержимое читаемо, с паролем скрыто, обе
разновидности архива корректно распознаются при импорте, все метаданные
(тайминги, модель-автор) переживают шифрование, неверный пароль отклоняется.

## Цикл 14. Файлы как ссылки

Новый раздел «📎 Файлы» с той же иерархией папок, что у остальных разделов.

### Почему ссылка, а не путь

Требование «не хранить файлы, а запоминать расположение» в браузере не
реализуется хранением текстового пути: из строки `C:\docs\spec.md` файл не
открыть — песочница это запрещает, и самого пути JS не видит.

Рабочий механизм — **File System Access API**. При выборе файла браузер выдаёт
`FileSystemFileHandle`, который переживает перезагрузку (кладётся в IndexedDB
структурным клонированием) и позволяет перечитать файл позже. В базе хранятся
только метаданные и дескриптор — содержимое не копируется, память не
расходуется, а правки файла на диске видны при следующем чтении.

### Границы, о которых нужно знать

- API поддерживают **Chrome и Edge**; в Firefox и Safari его нет. Для них
  предусмотрен запасной режим через `<input type="file">`: ссылка работает до
  перезагрузки страницы, запись помечается `needsRelink`, а интерфейс прямо
  сообщает об этом вместо молчаливого отказа.
- Даже с дескриптором браузер может заново спросить разрешение — после
  перезапуска это штатное поведение. Разрешение запрашивается только из
  действия пользователя (кнопка «Просмотр»), иначе браузер молча откажет.
- Если файл перемещён, переименован или удалён, чтение возвращает
  `needsRelink`, и файл переуказывается кнопкой «Перевыбрать».

### Доступ из чатов, инструментов, навыков и промптов

Три встроенных инструмента:

- `list_files` — список ссылок с путями, размерами, заметками и признаком
  доступности (`available`)
- `read_file` — чтение по id, имени или пути «Папка/файл.txt»; содержимое
  берётся с диска в момент вызова
- `search_files` — поиск подстроки внутри текстовых файлов с фрагментами

Список доступных файлов добавляется в системный промпт — модель знает, на что
можно сослаться. **Содержимое при этом не подставляется**: файлы читаются
инструментом по мере надобности, иначе контекст забивался бы текстами, которые
в конкретном запросе не нужны.

В промптах и навыках работает плейсхолдер `{{file:путь}}` — содержимое
подставляется в текст при использовании промпта.

Ссылка на файл разрешается по id, точному имени, полному или частичному пути —
проверено тестом, включая корректную деградацию при потерянном дескрипторе.

### Что осталось за рамками

Запись в файлы не реализована: она требует отдельного разрешения `readwrite` и
несёт риск порчи данных пользователя — записывающий инструмент, доступный
модели, должен проектироваться с подтверждением каждой операции.

## Цикл 15. Аудит: контекст, гонки, производительность

Плановый аудит кода целиком, а не последних правок. Исправления перечислены
в порядке практической важности.

### Контекст рос неограниченно — чат неизбежно ломался

В API уходила **вся** история чата. Приложение при этом считало токены,
предупреждало о заполнении на 75 % и 100 % и предлагало создать новый чат — но
ничего не предпринимало. После превышения лимита чат становился нерабочим:
каждый следующий запрос снова слал переполненный контекст и получал ошибку
провайдера.

Добавлена обрезка: системный промпт неприкосновенен, дальше сообщения берутся
с конца, пока укладываются в бюджет (окно контекста минус место под ответ минус
запас). Вытесненное заменяется краткой пометкой, чтобы модель знала о свёрнутом
начале разговора.

Ключевая тонкость — **целостность пар «вызов инструмента → результат»**.
Сообщение `role:'tool'` без предшествующего `assistant` с `tool_calls` ломает
запрос: провайдеры отвечают ошибкой на «сироту». Граница обрезки сдвигается
вперёд, пока первое сообщение не перестанет быть осиротевшим результатом.
Проверено тестом на истории из 120 сообщений с tool-парами.

### Гонка при записи статистики

`_recordUsage`, `_recordContextSize` и `_recordToolCall` работали по схеме
read-modify-write в отдельных транзакциях и вызывались подряд, а последний —
ещё и в цикле по вызовам инструментов. Перекрывающиеся обновления читали одно
и то же состояние, и изменения затирались.

Смоделировал на 10 параллельных обновлениях: вместо ожидаемых 1000 токенов
записывалось **100** — терялось 90 % данных. Все обновления пропущены через
последовательную очередь; после исправления результат точный.

### Транзакция на каждую операцию

`_tx()` открывал новую транзакцию под каждый `put`/`delete`. Импорт архива на
50 чатов с 2000 сообщений — это 2000+ транзакций подряд.

Добавлены пакетные `putAll()` и `deleteAll()`, выполняющие всё в одной
транзакции; переведены импорт чатов, удаление чата и `FoldersEngine.remove()`.
Побочный плюс — атомарность: при сбое пакет откатывается целиком.

### Молчаливый провал запуска

`app.js` при ошибке инициализации писал в консоль и всё — пользователь видел
пустой интерфейс без объяснений. Наиболее вероятная причина такого отказа —
неудачная миграция схемы (версия поднималась до 8) или недоступное хранилище
в приватном окне.

Теперь показывается экран ошибки с текстом проблемы, кнопкой перезагрузки и —
для ошибок хранилища — кнопкой удаления базы с явным предупреждением о потере
данных. Заодно обработаны два случая, которые раньше вызывали молчаливое
зависание: `onblocked` при открытии базы (другая вкладка мешает апгрейду схемы)
и `onversionchange` (база закрыта из другой вкладки).

### Прочее

- **Нативные `prompt`/`confirm` заменены** на модальные окна приложения
  (9 мест). Помимо несогласованного вида, нативный `prompt` отключён в части
  окружений — функция молча переставала бы работать.
- **Кэш индекса папок** в `FilesEngine.pathOf()`: раньше на каждый файл шёл
  линейный поиск по всем папкам.
- **Понятная ошибка при переполнении хранилища**: `QuotaExceededError`
  подменяется текстом с указанием, что именно делать.

## Цикл 16. Дополнительный аудит безопасности

Проверка мест, которые раньше не рассматривались пристально.

### XSS через поле icon у навыков

Найдена работающая дыра. Поле `icon` подставлялось в разметку **без
экранирования** (`${s.icon}` в панели чата и в карточке навыка), при том что
задаёт его модель через `create_skill`. Строка вида `<img src=x onerror=...>`
в этом поле выполнилась бы как разметка — то есть повторение уже закрытой
однажды проблемы, но по другому пути.

Исправлено на обоих рубежах: вывод экранируется, а на входе значок
ограничивается по длине и очищается от символов разметки.

Остальные подстановки проверены выборочно — `ask_user`, названия, описания,
заметки к файлам экранируются корректно; inline-обработчиков (`onclick=`
в шаблонах) в коде нет.

### Поток не закрывался при прерывании

При остановке кнопкой «⏹» или по таймауту выход из цикла чтения SSE шёл через
исключение, и `reader` оставался заблокированным — соединение висело до сборки
мусора. Добавлено явное освобождение (`releaseLock` + `cancel`) в `finally`.

## Цикл 17. Набор для начинающих и импорт навыков

### Помощь новичку

Четыре встроенных навыка (все выключены по умолчанию):

- **🧭 Помощник новичка** — объясняет возможности простым языком, ведёт от задачи
  пользователя, а не от списка функций, предлагает по одному шагу за раз.
- **🗂 Организатор** — наводит порядок в чатах, навыках, промптах и файлах;
  сначала смотрит, что есть, показывает план и ждёт согласия перед перемещением.
- **🎓 Эксперт по агенту** — разбор настроек и типичных жалоб: обрыв ответа,
  прерывание по времени, зацикливание, пропавшие токены.
- **📥 Импортёр навыков** — перенос навыков из внешних источников с обязательной
  проверкой.

Плюс два инструмента и четыре промпта-заготовки на вкладке «Промпты».

`explain_agent` объясняет устройство агента и **одновременно возвращает
статистику рабочего пространства** — сколько у пользователя чатов, навыков,
инструментов. Объяснение получается не абстрактным, а про то, что у него
реально есть.

`diagnose` проверяет состояние: выбрана ли модель, не малы ли лимиты, есть ли
выключенные инструменты в ожидании проверки, битые ссылки на файлы, близко ли
заполнение контекста. Каждая находка сопровождается точным путём в настройках.

### Импорт навыков и его безопасность

Здесь важна оговорка, определившая всю реализацию: **навык — это системный
промпт, то есть инструкции, управляющие поведением агента**. Импорт чужого
навыка ближе к запуску чужого кода, чем к копированию текста: промпт из
сомнительного репозитория может содержать указания скрывать информацию от
пользователя, обращаться к посторонним адресам или переопределять правила
агента.

Поэтому `import_skill_from_text`:

- сохраняет навык **всегда выключенным** — тот же принцип, что у инструментов
  с кодом;
- **не выполняет** импортируемый текст, а анализирует его: возвращает список
  найденных подозрительных мест (попытки отменить прежние инструкции,
  требования секретности, внешние ссылки, упоминания ключей, указания на
  передачу данных наружу);
- инструктирует агента показать разбор пользователю до включения.

Навык «Импортёр навыков» дублирует это правило на уровне поведения: чужой текст
для него — данные, а не команды.

Проверено на промпте с тремя закладками сразу — все три распознаны, навык создан
выключенным.

### Ограничение, которое стоит знать

Прямая загрузка из репозиториев (GitHub и т. п.) через `http_fetch` упирается
в CORS: большинство сайтов не отдают содержимое стороннему скрипту. Рабочий
путь — скопировать текст навыка и передать агенту; он разберёт и сохранит.

## Цикл 18. Механизм безопасности

Агент выполняет действия сам, по решению модели. Решение может быть ошибочным
или подсказанным враждебным текстом, попавшим в контекст — веб-страницей через
`http_fetch`, содержимым файла, импортированным навыком. Добавлен слой политик,
управляющий тем, что агент делает сразу, а что — только с подтверждения.

### Где живёт проверка

В одной точке — `executeTool()`, перед исполнением любого инструмента.
Размазывать проверки по обработчикам нельзя: новый инструмент легко забыть
закрыть, и дыра появится незаметно. Незнакомый инструмент с собственным кодом
классифицируется как `execute` — по умолчанию строже, а не мягче.

Операции классифицируются по **последствиям**, а не по технической природе:
чтение, изменение, удаление, обращение в сеть, исполнение кода или подмена
поведения агента.

### Режимы

| Режим | Что требует подтверждения |
|---|---|
| **Отключено** | ничего |
| **Минимальный** | только необратимое: удаление папок, перезапись при импорте |
| **Оптимальный** | плюс создание и изменение инструментов, импорт навыков, обращения в сеть, подозрительные операции |
| **Максимальный** | любая операция, изменяющая данные, и чтение файлов; создание инструментов агентом **запрещено полностью**; сеть — только по белому списку доменов |

### Что предложено для максимального режима

Помимо тотального подтверждения, добавлено то, что в мягких режимах было бы
избыточным:

- **Полный запрет `create_tool` и `update_tool`.** Это самая опасная операция:
  код инструмента исполняется в браузере. В строгом режиме его место — ручное
  создание пользователем через интерфейс, а не решение модели.
- **Белый список доменов.** Обращения за его пределы блокируются без вопроса —
  диалог подтверждения не спасает, если пользователь устал нажимать «да».
- **Подтверждение чтения файлов** — единственных данных, лежащих вне агента.

### Детали, влияющие на практическую полезность

- **Анализ кода инструмента.** При `create_tool` код проверяется на признаки
  выхода за рамки задачи: обращения к IndexedDB, localStorage, сети, странице
  приложения, `eval`, упоминания ключей. Найденное показывается в диалоге —
  пользователь решает, видя основание, а не голый вопрос «разрешить?».
- **Потолок изменений за один ответ** (по умолчанию 20) — защита от случая
  «агент увлёкся и переделал всё». Считается на ход, а не на сессию.
- **Запоминание домена на сессию.** Повторно спрашивать про тот же адрес —
  верный способ приучить нажимать «да» не читая.
- **Действия из интерфейса не переспрашиваются** (`bypassSecurity`): требовать
  подтверждения того, что человек только что нажал сам, — бессмысленный шум.
- **Отказ не ломает работу.** Агент получает сообщение, что операция не
  разрешена, и подсказку не искать обходной путь, а спросить пользователя.
- **Журнал решений** — что запрашивалось, что разрешено, что заблокировано.

### Честная граница механизма

Политики ограничивают действия агента **через инструменты**. Они не изолируют
код самого инструмента: включённый инструмент выполняется в браузере и может
обращаться к сети напрямую, минуя проверки. Настоящая песочница требует Worker
или sandboxed iframe. Поэтому главный барьер остаётся прежним — созданный
моделью инструмент включает пользователь вручную. Это предупреждение выведено
прямо на вкладке настроек, чтобы механизм не создавал ложного чувства защиты.

## Цикл 19. Файлы: инициатива агента и доступ после перезапуска

### Агент анализировал файлы без просьбы

Ошибка проектирования с моей стороны: перечень всех файлов вставлялся в
системный промпт **при каждом запросе**. Само его присутствие работало как
приглашение — агент начинал разбирать файлы даже в ответ на «с чего начать».
Смягчения формулировки оказалось мало: список в контексте провоцирует сам по
себе.

Теперь по умолчанию модель знает лишь **факт наличия** файлов, а перечень
получает инструментом `list_files` — то есть когда пользователь о файлах
заговорил. Режим настраивается (⚙ Настройки → Отображение): не упоминать /
только факт / полный перечень. Дополнительно в навык «Помощник новичка»
добавлено прямое правило не трогать данные пользователя по своей инициативе:
знакомство с агентом не требует изучать чужие материалы.

Побочный выигрыш — контекст не расходуется на список файлов, не нужных
в текущем запросе.

### Доступ к файлам после перезапуска браузера

Здесь важно различать два разных случая, которые раньше сливались в один флаг
«требуется повторный выбор»:

- **Разрешение сброшено.** Дескриптор цел, ссылка не потеряна — браузер просто
  требует подтвердить доступ заново. Это штатное поведение File System Access
  API после перезапуска.
- **Файл недоступен.** Перемещён, переименован, удалён или дескриптора не было
  вовсе (запасной режим в Firefox и Safari).

Панель теперь показывает реальное состояние каждой ссылки (проверкой
`queryPermission`, без запроса), а не флаг из базы.

Для первого случая добавлено **пакетное восстановление**: одна кнопка на все
файлы. Разрешение можно запрашивать только из действия пользователя, поэтому
серия запросов идёт в рамках одного нажатия. Часть браузеров прерывает серию
после первого диалога — тогда оставшиеся файлы показываются отдельно, и нажатие
повторяется. Это всё равно лучше, чем подтверждать каждый файл вручную через
«Просмотр».

Инструменты тоже стали точнее: `list_files` возвращает `status`
(`ready` / `needs-permission` / `needs-relink`), а `read_file` при отсутствии
разрешения объясняет агенту, что ссылка цела и нужно нажать «Восстановить
доступ», — вместо тупика, из которого агент пытался выкрутиться другими
инструментами.

## Цикл 20. Компактная панель навыков

После добавления обучающих навыков их стало восемь, и панель под полем ввода
занимала заметную часть экрана в каждом чате — при том что включены обычно
один-два.

Два режима с переключателем прямо в панели:

- **Только включённые** (по умолчанию) — отключённый навык исчезает из панели;
  кнопка показывает, сколько скрыто: «▾ все навыки (6)».
- **Все** — прежнее поведение.

Выбор сохраняется между сессиями; продублирован в ⚙ Настройки → Отображение.

Одна деталь потребовала внимания: в компактном режиме отключённый навык
пропадает из панели, и при первом разе это выглядит как потеря. Поэтому после
первого такого отключения выводится разовая подсказка, где его найти — дальше
поведение уже очевидно и повторять её незачем.

## Цикл 21. Разбивка tools, контроль MCP и отказоустойчивые подключения

### Реинжиниринг tools-engine.js

Файл вырос до 2515 строк. В нём вперемешку лежали описания инструментов,
их обработчики, механизм исполнения и проверки безопасности: правка одного
инструмента заставляла листать весь файл, а изменения в разных инструментах
постоянно конфликтовали между собой.

Разбит на семь модулей. Границы проведены по **роли кода** — что описывает,
что исполняет, что охраняет, — а не по предметным группам инструментов.
Предметная группировка («файловые», «сетевые», «работа с папками»)
развалилась бы на первом же инструменте вроде `export_chat`, который
относится сразу к чатам, к папкам и к скачиванию файла.

|---|---|---|
| `tools-engine.js` | 76 | класс, конструктор, точки расширения |
| `tools-registry.js` | 75 | реестр обработчиков, загрузка, выдача в API |
| `tools-executor.js` | 150 | исполнение, таймаут, шлюз безопасности |

Новый набор инструментов теперь подключается отдельным файлом, без правки
ядра и без разрастания `_builtinDefs()`.

### Контроль MCP в блоке безопасности

Раньше MCP-инструмент попадал в общую категорию `network` и подчинялся тем
же правилам, что и `http_fetch`. Это неверно: у MCP-вызова аргументы
формирует модель и отправляет на чужой сервер, а ответ возвращается прямо
в контекст диалога. Заведена отдельная категория `mcp` со своим набором
политик:

- белый список разрешённых хостов — сильнее режима безопасности;
- требование https (localhost по http допускается отдельной настройкой,
  поскольку локальный MCP-сервер — обычный сценарий);
- переиспользование чёрного списка адресов от `http_fetch` — защита от
  обращений во внутреннюю сеть здесь нужна ровно та же;
- таймаут запроса: у `fetch` своего предела нет, а таймаут в `executeTool`
  отпускает ожидание, но не разрывает соединение;
- потолок размера ответа: ответ вытесняет из контекста историю и системный
  промпт, то есть в том числе правила поведения агента;
- лимит MCP-вызовов за один ход;
- пометка ответа как данных, а не указаний.

Подтверждённые MCP-хосты хранятся отдельно от подтверждённых адресов
`http_fetch`: разрешение «звонить на этот MCP-сервер» и разрешение «сходить
по этому адресу» — разные по смыслу решения.

**Отдельно:** если в аргументах вызова обнаружена строка, похожая на ключ
доступа, подтверждение запрашивается всегда — даже на уже одобренном
сервере и в минимальном режиме. Пользователь разрешил обращаться к адресу;
он не разрешал отправлять туда ключи, и одно из другого не следует.

### Исправленный дефект в клиенте MCP

JSON-RPC возвращает ошибки со статусом 200, поэтому проверка `resp.ok`
их не ловила: объект с полем `error` уходил модели как успешный результат,
и она принимала неудачу за ответ. Теперь разбираются и `error` уровня
протокола, и признак `isError` уровня MCP. Попутно разделены случаи
«сервер недоступен» и «запрос заблокирован CORS» — браузер отдаёт на оба
одинаковый `TypeError`, и без подсказки причина ищется не там.

### Контроль зацикливания инструментов

Общий счётчик `writes` не ловил случай, когда агент застревает на одном
инструменте: сто вызовов `http_fetch` — это ноль записей. Добавлен потолок
вызовов **одного** инструмента за ход, срабатывающий во всех режимах, в том
числе для безобидных read-инструментов: бесконечный цикл из `calculator`
ничем не лучше бесконечного цикла из чего угодно другого.

Статический анализ кода создаваемых инструментов дополнен шестью
признаками: обращение к хранилищу секретов, чтение настроек подключения,
подгрузка стороннего скрипта, декодирование строк (`atob`, `fromCharCode`),
работа с буфером обмена и `sendBeacon`, обмен сообщениями между контекстами.

### Набор подключений к LLM

Раньше подключение было одно, в записи `settings/llm`. Заведено отдельное
хранилище `llm_connections` (версия схемы 8 → 9): подключений много, они
перебираются при отказе и сортируются по приоритету — для этого нужен
индекс, которого у key-value записи в `settings` быть не может.

Секреты (`apiKey`, `customHeaderValue`) шифруются существующим
`SecretsVault`. Остальные поля лежат открыто: они нужны, чтобы построить
список и выбрать подключение, а расшифровывать всю таблицу на каждый выбор
бессмысленно — модель угроз от этого не меняется.

Старая одиночная запись `settings/llm` мигрирует в первое подключение
списка при первом запуске.

У каждого подключения есть флаг `allowAgentSwitch`: снятый, он оставляет
подключение доступным пользователю вручную, но закрывает его для агента.
Это для дорогих или чувствительных по приватности провайдеров.

### Переключение при отказе

Новый `llm-pool.js`. Три режима, выбираются в интерфейсе:

- **priority** — цепочка: работает первое доступное, после сбоя агент
  остаётся на запасном;
- **priority-restore** — то же, но с автоматическим возвратом на основное
  после его восстановления;
- **round-robin** — запросы распределяются по кругу между рабочими
  подключениями.

Поверх всех режимов работает размыкатель: после N подряд неудач
подключение выводится из ротации на время остывания. Состояние здоровья
живёт **в памяти** и обнуляется при перезагрузке страницы — иначе один
неудачный вечер помечал бы подключение нерабочим навсегда, хотя провайдер
давно починился.

`LLMGateway.chat()` стал обёрткой над `_chatOnce()`. Публичный интерфейс не
изменился, поэтому `ui-chat.js` не потребовал правок; если пул не
подключён, поведение остаётся прежним.

Два ограничения заложены намеренно и вынесены в комментарии к модулю:

1. **Переключение возможно только до первого полученного токена.** Если
   поток оборвался на середине ответа, повтор на другой модели начал бы
   генерацию заново, и пользователь увидел бы склейку двух разных ответов.
   Такие ошибки помечаются `streamStarted` и пробрасываются без повтора.

2. **Ошибки конфигурации перебор не вызывают.** Неверный ключ, отсутствующая
   модель, опечатка в адресе — это не отказ провайдера. Перебор в таком
   случае показал бы пользователю ошибку от последнего подключения в списке
   вместо настоящей причины.

Число переключений за один ход ограничено (по умолчанию 3), иначе цикл
«переключился → снова ошибка → переключился» прошёл бы по всему списку,
потратив по запросу на каждом провайдере. Каждое переключение попадает в
журнал безопасности и показывается в чате отдельной строкой: смена модели
меняет качество и стиль ответа, и молчать об этом нельзя — иначе
пользователь решит, что модель внезапно поглупела, и будет искать причину
не там.

### Инструменты и навык управления моделями

Пять инструментов: `llm_list`, `llm_status`, `llm_switch`, `llm_test`,
`llm_strategy`. Секреты через них не отдаются — всё проходит через
`pool.sanitize()`.

Пользователь выбрал вариант, в котором агент переключается **без
подтверждения**. Сдерживают его четыре независимых механизма: инструменты
и навык созданы выключенными; флаг `allowAgentSwitch` у каждого
подключения; предел переключений за ход; запись каждого переключения в
журнал. В максимальном режиме безопасности подтверждение всё же
запрашивается.

Добавлен встроенный навык «Маршрутизация моделей» (выключен по умолчанию).
В его системном промпте отдельно оговорено, чего делать нельзя: перебирать
подключения в поисках устраивающего ответа (это подгонка, а не работа),
переключаться молча, дублировать автоматический failover и предлагать смену
модели как ответ на любую ошибку.

### Интерфейс

Новый `ui-connections.js` — список подключений с проверкой доступности,
редактор подключения, настройки режима и порогов. Вынесен в отдельный файл,
а не добавлен вкладкой в настройки: настройки описывают **одно** подключение
полями формы, а здесь список объектов со своим жизненным циклом. Смешивать
их — значит получить форму, где половина полей относится к выбранному
элементу, а половина к приложению.

Пустое поле ключа при редактировании означает «не менять»: иначе открытие
редактора ради смены модели стирало бы ключ.

### Доработка: рассогласования, найденные при сверке

После разбивки проведена сверка всех мест, которых коснулось изменение
источника правды. Найдено и исправлено шесть расхождений.

**Форма настроек и список подключений расходились.** Окно «⚙ Настройки»
писало в `settings/llm`, а пул читал список — изменения из формы терялись
при первом же переключении или при перезагрузке. Форма теперь считается
редактором **активного** подключения: `pool.syncFromSettingsForm()`
переносит в него введённое, сохраняя поля, которых в старой форме нет
(приоритет, окно контекста, разрешение агенту). Если список пуст, форма
создаёт первое подключение — привычный путь настройки «с нуля» работает
по-прежнему.

**Уведомление о переключении писалось в несуществующий контейнер.**
`notifyModelSwitch` обращалось к `#messages`, тогда как в разметке
`#chat-messages`: сообщение о смене модели просто не появлялось.

**Журнал безопасности не показывал новые записи.** Он знал только о
решениях `approved/denied/blocked` и о полях `risks/reason`, а
переключения пишутся как `executed/switched` с полем `detail` — строки
выводились без значка и без причины.

**Окно контекста не учитывало подключение.** `effectiveContextLimit()`
угадывал предел по имени модели, хотя у подключения есть заданное
пользователем поле. Одна и та же модель у разных провайдеров может
отдаваться с разным окном — урезанные тарифы, self-hosted сборки, — и имя
модели об этом ничего не говорит. Порядок теперь: ручная настройка →
окно подключения → таблица моделей.

**Диагностика описывала устаревшую картину.** `diagnose` видел только поля
шлюза. Добавлены проверки: подключений нет вовсе; подключение только одно
(переключаться не на что); выведенные из ротации после сбоев; включённые
без ключа или без выбранной модели.

**Справка не знала о подключениях.** В `explain_agent` добавлена тема
`models`, объясняющая устройство переключения — включая оба его
ограничения, чтобы агент не обещал пользователю невозможного.

### Интерфейс политик MCP

Политики, добавленные в этом цикле, настраивались только через запись в
БД. В раздел безопасности добавлены: список разрешённых MCP-серверов,
требование https, разрешение локальных серверов, пометка ответов как
данных, таймаут, предел размера ответа, лимит вызовов за ход и потолок
вызовов одного инструмента.

Отдельная панель показывает подключённые MCP-серверы, сгруппированные по
адресу, с числом включённых инструментов и отметкой, проходит ли сервер
белый список. Без неё «разрешённые серверы» настраивались вслепую: имена
инструментов ничего не говорят об их происхождении.

Подсказки к режимам безопасности дополнены — раньше они не упоминали ни
MCP, ни смену модели, и было непонятно, что меняется при переключении

## Цикл 22. Провайдеры и модели: двухуровневая настройка

Настройка подключений из цикла 21 оказалась неудобной: список подключений
жил в отдельном окне, модель задавалась строкой в другой вкладке, а связи
между ними в интерфейсе видно не было. Переделано.

### Один уровень стал двумя

Вкладки «Подключение» и «Модель» слиты в одну — «Провайдеры и модели».
Внутри раскрывающийся список: провайдер, под ним его модели. Разделять их
не имело смысла — настраивают их всегда вместе: добавил провайдера, сразу
выбираешь у него модели.

| Уровень | Что описывает |
|---|---|
| Провайдер | адрес API, ключ, способ авторизации |
| Модель | идентификатор, класс сложности, окно контекста, max_tokens, температура, заметка |

Модели вложены в запись провайдера, а не лежат отдельным хранилищем:
модель не существует без провайдера, читаются они всегда вместе, и
вложенность избавляет от каскадного удаления и рассинхронизации. Ссылка
на модель — строка `идентификатор_провайдера::идентификатор_модели`; её
можно положить в запись чата, не заводя вторичных индексов.

### Добавление моделей из списка провайдера

Кнопка «Загрузить у провайдера» запрашивает `/models` и показывает, что
там есть. Из выдачи в отдельный спойлер убраны эмбеддинги, озвучка,
генерация изображений и модерация — для чата они не годятся, но и
выбрасывать их совсем нельзя: у самодельных сборок имена бывают любые.

Класс сложности и окно контекста подставляются по имени модели и помечены
как догадка. Окно контекста провайдеры в API не сообщают вовсе, поэтому
оно задаётся руками — по нему считается индикатор заполнения и
подрезается история.

Класс сложности — «Простая», «Обычная», «Сильная», «Рассуждающая» — ни на
что в работе не влияет и нужен только при выборе модели в чате: по
идентификатору вроде `qwen2.5-72b-instruct` непонятно, за чем к этой
модели идти.

### Выбор модели в чате

Устроено как навыки: у чата свой короткий набор моделей, из которого
выбрана ровно одна. Плоский выпадающий список всех моделей провайдера не
годился — их бывают десятки, а в конкретном чате нужны две-три.

Клик по значку выбирает модель, правая кнопка убирает её из набора.
Отдельного крестика на значке нет: он занимал бы место в и без того
плотной панели.

Модель применяется к шлюзу и при переключении чата, и перед каждой
отправкой. Шлюз один на приложение, а модель — свойство чата: без этого
открытый ранее чат оставлял бы в шлюзе свою модель.

Ссылки на удалённые модели отфильтровываются при чтении, а не вычищаются
при удалении: чатов могут быть сотни, и переписывать их все ради одной
убранной модели неоправданно.

### Убрано автоматическое переключение

Механизм failover из цикла 21 удалён по требованию: `llm-pool.js`,
стратегии, размыкатель, лимит переключений за ход, обёртка `chat()` в
шлюзе. `LLMGateway.chat()` снова просто транспорт.

Причина, по которой это правильно: подмена модели посреди работы меняет
качество и стиль ответа, а пользователю причина не видна. Инструмент
`llm_strategy` удалён, `llm_switch` теперь меняет модель текущего чата, а
не активное подключение.

Код механизма остался в истории цикла 21 — если отказоустойчивость
понадобится, восстанавливать его с нуля не придётся.

### Ручной лимит контекста убран

Он был один на всё приложение и врал, как только в чатах оказывались
разные модели. Теперь окно контекста — свойство модели. В настройках
остался только порог, при котором предупреждать о заполнении.

### Что переехало следом

- `diagnose` проверяет реестр: нет провайдеров, нет моделей, провайдер без
  ключа, модель без окна контекста, не выбрана модель по умолчанию.
- `explain_agent`, тема `models` — переписана под двухуровневую настройку.
- Навык переименован в «Выбор модели»; из промпта убрано всё про
  автоматическое переключение, добавлен запрет выдумывать названия моделей.
- Категория `llm` в блоке безопасности сохранена: `llm_switch` меняет то,
  чем агент думает дальше, и в максимальном режиме подтверждается.

### Перенос старых настроек

Реестр при первом запуске переносит `settings/llm` в первого провайдера с
одной моделью. Повторный запуск дубля не создаёт. Записи `llm_connections`
из цикла 21 читаются как провайдеры без моделей — модели к ним добавляются
кнопкой «Загрузить у провайдера».

### Тесты

`test-pool.js` удалён вместе с механизмом, который проверял. Добавлен
`test-registry.js` (44 проверки): два уровня и вложенность, ссылки на
модели, применение к шлюзу, модель по умолчанию и её судьба при удалении,
каскад при удалении провайдера, перенос старых настроек и защита от
повторного переноса, запрос списка моделей с обоими способами авторизации,
разбор ошибок.

Общий счёт: 118 проверок в трёх наборах.

## Цикл 23. Модальные окна настроек и модель чата при старте

Три жалобы на панель «Провайдеры и модели» оказались тремя независимыми
дефектами — исправлены по очереди, каждый следующий вскрылся только после
починки предыдущего.

### «Сохранить» не закрывал редактор провайдера/модели

`_backToProviders()` вызывал `this.showSettings()` — метода с таким именем
не существует, правильное имя `showSettingsModal()`. Данные при этом реально
сохранялись в БД, но возврат к списку падал с `TypeError`, и в обработчике
кнопки «Сохранить» строка, закрывающая модалку, не выполнялась: окно
оставалось висеть открытым без видимой причины.

### Клик мимо окна закрывал редактор

`showProviderEditor`, `showModelEditor` и `showModelPicker` открывались без
`{ modal: true }` — в отличие от главного окна настроек, где это уже сделано
специально. Добавлен флаг всем трём; заодно найден и исправлен более общий
дефект в `_showModal()`: кнопка «Сохранить» стирала контейнер `#modals`
**после** вызова `onSave`, а `onSave` в этих окнах сам открывает следующее —
возврат к настройкам или повторный показ формы при ошибке валидации — и эта
строка сносила то, что `onSave` только что отрисовал. Стирание сделано
условным: только если после `onSave` в DOM всё ещё то самое окно, а не
новое, показанное самим `onSave`.

> Флага `{ modal: true }` больше нет: в Цикле 29 строгими стали ВСЕ окна,
> а опция и обработчик клика по оверлею убраны совсем. Тогда же появился
> Esc как замена закрытию мышью мимо окна.

### Кнопка «+ В чат» ничего не делала

Окно «Модели для этого чата» позволяло добавить только одну модель за заход
— после первого клика оно закрывалось целиком, вместо того чтобы остаться
открытым для добавления следующей. Исправлено: список моделей теперь
перерисовывается на месте через делегирование клика на контейнер, а не
закрывается.

После этой правки кнопка отвечала клику, но по-прежнему не добавляла
модель — без единой ошибки в консоли. Причина оказалась глубже: `agent.js`
после инициализации сразу вызывал `updateChatToolbar()`, ни разу не загрузив
ни один чат — панель чата (быстрый выбор модели, статистика) рисовалась и
выглядела рабочей, а `this.currentChatId` оставался `null`. `setChatModel()`
при отсутствии текущего чата тихо ничего не делает — ни ошибки, ни эффекта.

Исправлено в источнике: при запуске приложение теперь открывает последний
использованный чат (по `updatedAt`), а не оставляет пустое состояние — как
это делает большинство чат-приложений. Отдельно, на случай самого первого
запуска без единого чата, `showChatModelPicker()` создаёт чат сам, если
`currentChatId` всё ещё пуст.

## Цикл 24. MCP-серверы как отдельная сущность

До этого цикла MCP-сервер не существовал как сущность вовсе: адрес и
токен просто повторялись на каждом импортированном с него tool. Изменить
имя или токен можно было только пересоздав все инструменты заново, удалить
сервер целиком — только вручную, по одному tool, а органайзер (иерархия
папок) не различал, какому серверу что принадлежит.

### Новое хранилище и связь с деревом Tools

Добавлен store `mcp_servers` (версия схемы БД 9 → 10): имя, URL, токен
(зашифрован), ссылка на папку-контейнер. При подключении сервера
(`connectMcpServer` в `tools-mcp.js`) создаётся папка-контейнер в корне
раздела Tools с полем `mcpServerId` — она и представляет сервер в дереве
(значок 🧩 вместо 📁, действия «Настроить»/«Удалить сервер» вместо
переименования/удаления папки). Импортированные tools получают то же поле
и кладутся в эту папку.

Внутри контейнера разрешена обычная вложенная иерархия подпапок — тот же
`FoldersEngine`, без изменений. Изоляция обеспечена не структурой данных, а
проверкой при перетаскивании: `_mcpScopeOf()` в `ui-navigation.js` находит
у папки (поднимаясь по `parentId`) ближайшего предка с `mcpServerId` и
сравнивает область видимости источника и цели. Перемещение, смешивающее
инструменты разных серверов — или сервер с обычными папками, — молча
отклоняется, тем же приёмом, что уже применён к защите от циклов в
`FoldersEngine.move()`. Контейнер сервера сам не перетаскивается: он всегда
лежит в корне.

### Правка и удаление

`updateMcpServer` меняет имя и токен; адрес — нет, он совпадает с
`mcpServer` на уже импортированных tools, и его смена потребовала бы либо
их перепривязки, либо расхождения между записью сервера и его же
инструментами. Пустой токен при правке означает «не менять» — та же
договорённость, что и в редакторе провайдеров LLM. Смена токена обновляет
`mcpToken` у всех tools сервера и переоткрывает их обработчики — иначе
следующий вызов ушёл бы со старым токеном, застрявшим в замыкании
`_registerMcpHandler`.

`removeMcpServer` удаляет сервер целиком: все его tools (в каком бы
подпапке поддерева они ни лежали — поиск идёт по `mcpServerId`, а не по
структуре папок), все папки поддерева и саму запись сервера. Обычный
`FoldersEngine.remove()` здесь не годится — он поднимает содержимое папки
на уровень выше, а сервер должен исчезнуть вместе со всем, что в нём
организовано.

### Что переехало следом

- Карточка MCP-инструмента помечена значком 🧩; кнопка «Редактировать»
  для неё скрыта — общая форма показывает поле Handler Code, бессмысленное
  для проксированного вызова.
- Ручное создание custom-tool внутри чужого сервера автоматически уводится
  в корень раздела — та же граница, что и при перетаскивании.
- `listMcpServers()` (панель безопасности, диагностика) стал гибридным:
  именованные серверы — из `mcp_servers`, а инструменты без `mcpServerId`
  (данные, добавленные до этого цикла) по-прежнему группируются по хосту,
  как раньше, — не выпадают из списка молча.

### Тесты

12 новых проверок в `test-tools.js`: подключение с импортом tools, вложенная
подпапка, переименование, смена токена (с обновлением у всех tools),
каскадное удаление (tools, вложенные папки, запись сервера). Общий счёт
пакета — 66 проверок.

## Цикл 25. Структура `js/` по подпапкам

К 30 файлам без единой вложенности плоский список перестал быть навигируемым
списком — стал вычитыванием оглавления. Разложено по той же логике, что уже
применена внутри `tools-*.js` и `ui-*.js`: по **роли кода**, а не по
предметным группам.

| Подпапка | Состав |
|---|---|
| `core/` | `agent.js`, `db.js`, `crypto-utils.js`, `markdown.js` — то, на чём держится всё остальное |
| `llm/` | `llm-gateway.js`, `llm-registry.js` |
| `tools/` | все семь модулей `tools-*.js` |
| `engines/` | `skills-engine.js`, `prompts-library.js`, `folders-engine.js`, `files-engine.js`, `security-engine.js` — движки без общего префикса имени |
| `ui/` | все восемь модулей `ui-*.js` |
| `tests/` | четыре набора функциональных тестов на Node |

`app.js` остался в корне `js/` — как единственная точка входа, ему не нужна

(`/home/claude/app/`, унаследованный от прежней облачной среды выполнения)
остался как есть — он не имеет отношения к переносу и ломает локальный
запуск тестов независимо от него.

Правильность переноса проверена в два прохода: все четыре набора тестов

цепочка загрузки `index.html` — эмулирована в Node (`vm`, тот же общий

до точки, где для дальнейшей проверки нужен уже настоящий браузерный
IndexedDB, а не заглушка.

## Цикл 26. Продакшен-сборка с обфускацией

Приложение и дальше не требует сборки для разработки — открыл `index.html`
через локальный сервер и работаешь. Но для раздачи наружу код стоит хотя
бы обфусцировать: 27 читаемых файлов с говорящими именами методов и
комментариями на русском — не то, что хочется отдавать как есть.

### Почему нельзя просто прогнать обфускатор по каждому файлу

Классы вроде `ToolsEngine` или `UI` объявляются в одном файле и
дополняются через `Object.assign(X.prototype, {...})` в остальных —
имя класса должно остаться **одинаковым** между всеми файлами, которые на
него ссылаются. Обфускатор, запущенный на каждый файл отдельно, переименовал
бы `ToolsEngine` в разных файлах в разные имена (у него нет информации о
том, что это один и тот же класс) — приложение сломалось бы тихо, без
единой ошибки на этапе сборки: `ReferenceError` вылез бы только в рантайме,
на конкретном действии пользователя.

Решение — собрать все файлы в один бандл **в том же порядке**, что в
`index.html` (файлы и так делят общий scope, порядок уже был важен и до
сборки), и обфусцировать результат одним проходом. Тогда переименование
проходит согласованно по всему коду разом.

### `scripts/build-prod.js`

Сам вычитывает порядок `<script src="js/...">` из `index.html` — отдельного
списка файлов на поддержку в скрипте нет, источник правды один. Между
файлами при склейке вставлен `;\n` — страховка от случайного склеивания
выражений через ASI на границе файлов (если один файл заканчивается вызовом
без `;`, а следующий начинается с `(` или `[`, без разделителя два оператора
слились бы в один).

Обфускация — `javascript-obfuscator` с осознанно умеренными настройками:

- `controlFlowFlattening` и `deadCodeInjection` выключены — заметно тяжелят
  рантайм, а для чата в реальном времени (streaming, циклы tool-calling)
  это ощутимая цена не только за красоту кода;
- `selfDefending` и `debugProtection` выключены — ломают обычную
  минификацию и отладку, а реальной защиты не дают: код всё равно исполняется
  в браузере пользователя и разворачивается в DevTools за разумное время;
- `renameGlobals` выключен (значение по умолчанию) — **осознанно**, а не
  забыто: верхнеуровневые имена (классы, `agent`, `uid`) это не только связки
  между файлами, но и точка входа для отладки прямо в консоли браузера
  (`agent.tools.debug = true`, `agent.llm.debug = true` — задокументировано
  в комментариях `tools-engine.js`/`agent.js`). Переименование локальных
  переменных внутри функций и извлечение строк в `stringArray` от этого
  никак не страдают и дают основной эффект.

### `dist/` — что внутри

Самодостаточная папка: `app.min.js` (единственный обфусцированный бандл),
`index.html` (тот же файл, но блок из 27 `<script>` и поясняющих
HTML-комментариев про порядок подпапок заменён на один тег), `css/styles.css`
(копия без изменений — обфусцировать разметку смысла нет). Раздаётся любым
статическим веб-сервером без дополнительной настройки.

**Коммитится в git как есть** — вместе с `node_modules/` инструмент сборки
не нужен, чтобы просто получить готовый продакшен-бандл: `git clone` и сразу
раздавать `dist/`, без `npm install`.

### Проверка

`javascript-obfuscator` добавлен как единственная `devDependency` в новом
`package.json` (`npm run build` запускает сборку). Корректность бандла
проверена тем же приёмом, что и перенос путей в Цикле 25: эмуляция запуска
в Node (`vm`) в общем глобальном контексте — единый обфусцированный файл
выполнился без ошибок и дошёл до реального вызова `AgentDB.open()`, то есть
до той же точки, что и до обфускации и до объединения в один файл. Класс
`AIAgent` и вся цепочка примесей внутри него пережили и склейку, и
переименование идентификаторов без единого расхождения в поведении.

## Цикл 27. Ход генерации — состояние по чату, а не по приложению

Две жалобы, вторая — на куда более серьёзный дефект, чем казалось на
первый взгляд.

### max_tokens по умолчанию — окно контекста

При добавлении модели `max_tokens` предлагался фиксированным (4096)
независимо от того, какое окно контекста только что было угадано или
введено. Теперь по умолчанию `max_tokens` = окно контекста, а поле
следует за окном контекста при правке — пока пользователь не поменяет
`max_tokens` вручную (после этого автоследование для этой формы
прекращается, чтобы не затирать намеренный выбор).

### Переключение чатов ломало визуализацию — и не только её

Ход ответа (стриминг, панель статуса, счётчики лимитов, `AbortController`)
хранился в плоских полях `this._turnStartedAt`, `this._abortCtl` и
подобных — **одно значение на всё приложение**, а не на чат. Пока чат A
ждал ответ, переключение на чат B продолжало дописывать в `#chat-messages`
то, что приходило для A: это тот же самый DOM-узел, простое переключение
чата не создаёт новый. При возврате в A индикатор хода исчезал совсем —
восстанавливать его было неоткуда.

Проверка кода вскрыла кое-что серьёзнее видимого симптома: `chatId:
this.currentChatId` читалось **на протяжении всей** асинхронной цепочки
генерации — на входе, при каждом сохранении сообщения, при подсчёте
статистики. Переключение чата посреди хода не просто портило картинку —
оно **дописывало сообщения не в тот чат**. Хуже того: `loadChat()`
безусловно вызывает `applyChatModel()` для просматриваемого чата, то есть
простой просмотр другого чата уже переключает общий шлюз LLM на его
модель. Если это происходило между наборами данных для запроса и самим
`fetch`, ответ на исходный вопрос мог уйти с чужими API-параметрами, а
завершившееся сообщение — подписаться чужой моделью, хотя фактический
запрос ушёл с правильной.

### Решение: состояние хода — в Map по chatId

Новое `this._chatRuns` (Map, ключ — chatId) в `UI`: каждый активный ход —
отдельная запись `{ startedAt, stage, partialContent, streamEl,
turnToolCalls, turnUserMsgId, stopRequested, abortCtl, statusTimer }`.
`sendMessage()` захватывает `chatId` **один раз**, в самом начале, и дальше
использует только его — не `this.currentChatId`, который может измениться
в любой момент от клика по сайдбару. `_generateResponse(chatId, depth)`
принимает chatId явным параметром и пробрасывает его через всю рекурсию
tool-calling; каждое обращение к DOM идёт через `dom()`, отрисовывающую в
`#chat-messages`, только если `chatId === this.currentChatId` прямо в
момент вызова — не раньше и не по значению, закэшированному в начале функции.

Гонку за общий шлюз закрыли переприменением модели чата дважды: один раз
в начале сбора контекста (для `_trimHistory`, которому нужно верное окно
контекста именно этого чата — `effectiveContextLimit()` получил
необязательный параметр `ref`) и ещё раз непосредственно перед вызовом
`llm.chat()` — между ними несколько `await` (навыки, файлы, список
инструментов), за время которых пользователь мог успеть заглянуть в
другой чат. Имя модели для метаданных сообщения (`modelUsed`) фиксируется
сразу после этого второго переприменения, а не читается заново из
`this.agent.llm.model` после `await` на сетевой запрос, — иначе поздний
просмотр другого чата мог бы задним числом переприписать уже готовый ответ
чужой моделью.

Восстановление при возврате: `loadChat()` после отрисовки сохранённых в
БД сообщений проверяет `this._chatRuns.get(chatId)` — если ход ещё активен,
дорисовывает накопленный `run.partialContent` отдельным пузырём (тот же
DOM-узел кладётся в `run.streamEl`, чтобы дальнейшие чанки дописывались
именно в него) и восстанавливает панель статуса по `run.stage`.

### Один общий шлюз — одна активная генерация

Шлюз LLM как был, так и остался один на приложение — параллельно
генерировать в двух чатах он не умеет технически (общее mutable-состояние
модели/URL/ключа). Переключаться и **смотреть** на любой чат во время
чужой генерации теперь можно свободно, но отправка сообщения во ВТОРОМ
чате, пока первый ещё отвечает, отклоняется — только не молча, как раньше
(когда кнопка отправки была задизейблена глобально без всякого объяснения
почему), а с понятным сообщением, в каком именно чате ждать.

### Индикатор в списке чатов

Чат, для которого сейчас есть запись в `this._chatRuns`, помечается
спиннером в дереве сайдбара — единственный способ узнать, что где-то
идёт работа, не переключаясь в этот чат специально.

### Попутно

- `_trimNoticeShownFor` (одно значение — id последнего чата, которому
  показали уведомление об обрезке истории) заменён на `Set`: раньше
  переключение между двумя чатами, каждому из которых нужна обрезка,
  показывало уведомление заново при каждом возврате.
- `_showTruncationNotice`/`_stopTurn`/`_showTrimNotice` перестали получать
  `container` параметром (готовый, потенциально уже нерелевантный узел) —
  теперь сами проверяют chatId и берут `#chat-messages` заново.

### Тесты

Новый `test-chat-switching.js` (20 проверок, `jsdom` — впервые в проекте
понадобился настоящий DOM, а не `vm`-песочница: суть проверки — реальные
`insertAdjacentHTML`/`innerHTML`/`querySelector` в конкретных DOM-узлах, а
не только факт вызова функций). Сценарий: чат A получает первый чанк →
переключение на чат B → второй чank чата A не должен попасть в DOM
чата B → попытка отправить сообщение в B отклоняется с объяснением →
возврат в A восстанавливает и текст, и панель статуса → третий чанк
дописывается в тот же узел без дублей → переключение на B и завершение
ответа A → итоговое сообщение сохранено под правильным chatId и с
правильной моделью, run снят, индикатор в списке погас.

`javascript-obfuscator`, добавленный в Цикле 26, не тронут — `jsdom` идёт
отдельной `devDependency` только для тестов. Из трёх старых наборов (132
проверки, Циклы 21–25) ни один не задет: они целиком про `ToolsEngine`/
`LLMRegistry`/`SecurityEngine` в `vm`-песочнице без DOM. Общий счёт по
проекту — 172 проверки в четырёх наборах (после Циклов 28–32 — 333 в семи).

## Цикл 28. Тема оформления, дыра в изоляции выключенных tools, переключатель папки

Три отдельных запроса за один заход.

### 1. Тема оформления: Системная / Тёмная / Светлая

До этого цикла в `styles.css` была ровно одна, тёмная, палитра — переменные
`--bg-primary`, `--text-primary` и т.п. заданы один раз в `:root` и
используются по всему файлу через `var(...)`. Это и позволило добавить тему
почти без переписывания CSS: достаточно переопределить те же переменные.

- `:root[data-theme="light"]` — светлая палитра, побеждает всегда;
- `@media (prefers-color-scheme: light) { :root:not([data-theme]) {...} }` —
  та же палитра, но только когда атрибут не выставлен явно (режим
  «Системная») и ОС/браузер просит светлую. Тёмная — по-прежнему то, что
  в `:root` без модификаторов, отдельного `[data-theme="dark"]` не
  потребовалось.
- Два места, которые были захардкожены под тёмный фон мимо переменных
  (`.tree-folder` на `rgba(255,255,255,0.02)`, `.boot-error` на
  `rgba(15,15,20,0.94)`), заведены под новые переменные `--tint-soft` и
  `--overlay-strong` — иначе в светлой теме это были бы нечитаемые пятна.
  Остальные `rgba(...)` в файле — тонировки самих акцентных/семантических
  цветов (`--accent`, `--warning`, `--danger`) под их же цвет текста и от
  темы не зависят.
- `UI.applyTheme(theme)` (`ui-core.js`) ставит/снимает атрибут на
  `<html>`; вызывается из `agent.js` сразу после создания `UI` (до первой
  отрисовки чата — так меньше шанс мигнуть тёмным перед переключением) и
  из `ui-settings.js` при сохранении вкладки «👁 Отображение». Хранится в
  `settings/theme`.

### 2. Выключенный инструмент был доступен модели в обход тумблера

Наблюдение пользователя: «даже отключённые tool агент пытается
использовать». Проверка показала, что это не ощущение, а настоящая дыра.

`getEnabledToolsForAPI()` (единственное место, что описывает инструменты
модели) фильтрует по `t.enabled` корректно — модель не видит выключенный
tool в схеме function-calling. Но `executeTool()` (`tools-executor.js`)
искал вызываемый инструмент по имени во ВСЁМ списке `loadTools()`, без
проверки `enabled`, и просто выполнял найденный обработчик. Если модель
всё же выпускала `tool_call` с именем выключенного инструмента — по памяти
о нём из более раннего момента диалога, когда он ещё был включён, или
просто выдумав вызов — движок его честно исполнял.

Добавлена явная проверка перед диспетчеризацией: выключенный инструмент
возвращает `{ error: 'Инструмент "..." отключён и недоступен для вызова.' }`
вместо выполнения. Проверка не применяется при `bypassSecurity: true`
(вызовы, которые инициирует сам пользователь кнопкой интерфейса, — там
инструмент по построению всегда доступен) — то же исключение, что уже
было у проверки политики безопасности чуть выше по той же функции.
Новый тест в `test-tools.js` («Выключенный инструмент недоступен для
вызова») временно отключает `security`, чтобы проверить именно эту
проверку, а не политику. Итог — 67 проверок в наборе, 173 по проекту.

### 3. Включение/выключение инструментов папкой целиком

Раньше тумблер был только у каждого инструмента отдельно на карточке —
выключить десяток tools одного MCP-сервера или одной темы означало
щёлкать по одному. Теперь у каждой папки в дереве раздела Tools (в
`_renderSidebarTree`, `ui-navigation.js`) есть свой переключатель:

- область действия — сама папка и все вложенные в неё папки любой
  глубины (`_folderSubtreeIds` — новый общий хелпер, вытеснил локальную
  версию той же рекурсии, которая раньше жила только внутри
  `_renderSidebarTree`);
- если в области виден результат не «все включены» и не «все выключены»,
  переключатель показывает нативное `indeterminate`-состояние чекбокса
  (ставится только через DOM-свойство, HTML-атрибута для него не бывает);
- клик выравнивает все инструменты области в одну сторону одним проходом
  `db.put` по каждому;
- работает и для MCP-серверов — их корневая папка ничем не отличается от
  обычной, просто дополнительно помечена `mcpServerId`.

Компактный вариант переключателя — `.toggle-switch.sm` в `styles.css`
(28×16 вместо обычных 44×24, иначе не помещался в строку дерева рядом с
кнопками папки). Клик по переключателю не должен выбирать папку — строка
дерева и так завязана на клик, поэтому обработчик выбора папки получил
дополнительный guard `e.target.closest('.toggle-switch')`, по аналогии с
уже существовавшим guard'ом на `.tw-actions`.

## Цикл 29. Модальность всех окон и связь навыков с инструментами

### 1. Клик мимо окна больше не закрывает форму

`_showModal` умел два режима: строгий (`{ modal: true }`) и обычный, где
клик по затемнённому оверлею закрывал окно. Строгим был помечен десяток
окон, остальные — нет, и в них промах мышью молча стирал введённое:
половину форм здесь заполняют вручную (промпт навыка, JSON Schema
инструмента, ключ провайдера).

Опция убрана целиком — вместе с обработчиком клика по оверлею. Модальны
теперь ВСЕ окна без исключения, включая `_prompt`/`_confirm`/`askUser`.
Все вызовы, передававшие `{ modal: true }`, почищены: остался только
`{ wide: true }` там, где он был.

Взамен добавлена клавиша **Esc** — она равносильна «Отмене». Без неё
единственным способом закрыть окно осталась бы мышь, а часть окон
(статистика, журнал безопасности, список MCP-серверов) вообще ничего не
редактирует. Слушатель Esc снимает сам себя, если его окна в документе
уже нет: окно может быть заменено другим прямо из `onSave` (переход
«модель → список провайдеров»), и старый слушатель не должен ни гасить
чужое окно, ни вызывать свой `onCancel` задним числом.

### 2. Связь навыков с инструментами (многие-ко-многим)

Навык теперь знает, какими инструментами пользуется: `skill.toolIds`.
Один навык — сколько угодно инструментов, один инструмент — сколько
угодно навыков. Хранится связь односторонне, массивом в записи навыка;
обратное направление («какие навыки используют этот инструмент»)
вычисляется перебором — навыков десятки, а вторая копия связи была бы
вторым местом, где она расходится с первой.

**Привязка не управляет доступностью — это главное в постановке.**
Инструмент по-прежнему вызывается тогда и только тогда, когда включён
его собственный тумблер; навык действует, когда включён он сам. Привязка
отвечает на другой вопрос и работает через системный промпт: активный
навык перечисляет свои инструменты, а отдельной строкой — привязанные,
но выключенные, с прямым указанием не пытаться их вызвать и сказать
пользователю, какой включить. Это продолжение Цикла 28: там выключенный
инструмент перестал исполняться, здесь модель узнаёт, почему его нет.

Что изменилось по местам:

- `SkillsEngine` — методы `toolIdsOf`, `toolsOfSkill`, `skillsUsingTool`,
  `resolveToolIds` (принимает имена и id вперемешку), `setSkillTools`
  (`set`/`add`/`remove`), `forgetTool`. Встроенные навыки получили
  привязки по умолчанию — ровно те инструменты, которые они и так
  перечисляли прозой в своих промптах (`skill_llm_router` → `llm_*`,
  `skill_organizer` → работа с папками, `skill_tool_dev` → `create_tool`).
- Разовая миграция в `loadSkills()`: у записи, заведённой до появления
  связи, поля нет вовсе — ей проставляется привязка по умолчанию.
  ПУСТОЙ массив при этом не трогается: это осознанное «инструментов нет»
  от пользователя, а не отсутствие поля.
- Интерфейс: в редакторе навыка — список инструментов с галочками,
  фильтром и пометкой «включён/выключен»; на карточке навыка — чипы
  привязанных инструментов (выключенные зачёркнуты) и счётчик
  выключенных; на карточке инструмента — навыки, где он используется.
  Удаление инструмента предупреждает о привязках и снимает их
  (`forgetTool`), удаление MCP-сервера — тоже, для всех его инструментов.
- Встроенные инструменты: новый `link_skill_tools`
  (`add`/`remove`/`set`/`list`); `create_skill`, `update_skill` и
  `import_skill_from_text` получили параметр `tools`; `list_workspace`
  отдаёт связь в обе стороны (`tools` у навыков, `usedBySkills` у
  инструментов); `explain_agent` объясняет её в темах skills и tools;
  `diagnose` отдельно предупреждает про включённый навык с выключенными
  привязанными инструментами — снаружи это выглядит как «агент
  игнорирует навык». `link_skill_tools` отнесён к категории `write`.
- `ToolsEngine._skills()` — доступ к движку навыков (инжектится в
  `agent.js`, как `folders`/`files`; при отдельном поднятии движка
  создаётся лениво).

### Заодно: навык звал несуществующий инструмент

Найдено при сверке документации с кодом. Встроенный навык «Маршрутизация
моделей» в разделе «ЧЕМ ПОЛЬЗОВАТЬСЯ» перечислял `llm_strategy` — инструмент,
удалённый ещё в Цикле 22 вместе с механизмом пула подключений. Ровно та
болезнь, от которой лечит связь навыков с инструментами, только в самом
тексте навыка: модель получала указание пользоваться тем, чего нет.
Строка убрана, описание `llm_switch` уточнено (он меняет модель текущего
чата, а не «подключение»).

Важно: правка касается `_defaultSkills()`, то есть новых баз. У того, кто
уже пользуется агентом, навык лежит в IndexedDB со старым текстом —
обновится он только при удалении записи навыка (после чего досеется заново).

### Тесты

Два новых набора, оба на переносимых путях (`__dirname`), в отличие от
старых трёх:

- `test-skill-tools.js` (39 проверок, `vm`): многие-ко-многим в обе
  стороны, дедупликация, разрешение имён и id, миграция старых записей
  (включая то, что осознанно пустой список не восстанавливается),
  системный промпт с предупреждением о выключенных, все режимы
  `link_skill_tools`, `create_skill`/`update_skill`, `list_workspace`,
  `diagnose`. Отдельно закреплено главное свойство: привязка выключенного
  инструмента не делает его ни видимым для модели, ни вызываемым.
- `test-modals.js` (23 проверки, `jsdom`): клик по оверлею не закрывает
  окно и не теряет введённое, «Отмена»/«Сохранить»/Esc закрывают и зовут
  нужный колбэк ровно один раз, окно, открытое из `onSave`, не стирается,
  а слушатель заменённого окна безвреден. Первый прогон провалился на
  проверке про «чужой Esc» — ошибочным оказалось ожидание в самом тесте
  (окно на экране одно, и Esc обязан закрывать именно его), но проверить
  это было дешевле, чем додумать.

Итого 213 проверок в шести наборах (после Цикла 30 — 248).

## Цикл 30. Связь с двух сторон, разбор инструментов при включении навыка, системный навык

### 1. Управление связью со стороны инструмента

Связь навыков с инструментами (Цикл 29) настраивалась только из навыка.
Теперь у каждой карточки инструмента есть кнопка «🧩 Навыки», открывающая
тот же список с галочками, но с другой стороны: к каким навыкам относится
ЭТОТ инструмент.

Отдельным окном, а не полем в редакторе инструмента, — потому что редактор
открывается только у собственных инструментов, а привязывать нужно и
встроенные, и пришедшие с MCP-сервера.

`SkillsEngine.setToolSkills(toolId, skillIds)` замещает список: инструмент
добавляется в отмеченные навыки и убирается из всех остальных. Иначе одно
сохранение формы не смогло бы снять привязку — только добавить.

### 2. Включил навык в чате — разберись с его инструментами

Навык может опираться на инструменты, которые сейчас выключены. Тогда он
включается наполовину: указания модель получит, а выполнить их не сможет —
со стороны это выглядит как «навык не работает».

При включении навыка чипом в чате агент один раз показывает окно со
списком его выключенных инструментов и галочками (по умолчанию отмечены
все). «Сохранить» включает отмеченные и пишет об этом в чат, «Отмена»
оставляет как есть — навык при этом остаётся включённым в любом случае,
отказ касается только инструментов.

Проверка сделана ровно там, где просили, — в обработчике клика по чипу, а
не в отрисовке панели. Постоянный контроль здесь и не нужен: состояние
инструментов пользователь меняет сам и видит на вкладке Tools, а
напоминание в каждом ответе быстро стало бы шумом, который перестают
читать. Расхождения вне этого момента ловит `diagnose` (Цикл 29).

### 3. Системный навык и системные инструменты

Появился навык **«Системный»** (`skill_system`, флаг `locked`) — первый,
который нельзя выключить и удалить. Он описывает не роль, а УСТРОЙСТВО
агента: то, о чём модель иначе не знает и что поэтому выглядит для неё
как необъяснимый сбой.

Что в нём:

- **Память** (`persistent_memory`) — что переписка не бесконечна, между
  чатами ничего не помнится, что записывать (устойчивые решения, а не
  пересказ разговора), чего не записывать никогда (пароли и ключи) и что
  перед «я не помню» стоит заглянуть в память.
- **Подтверждение операций** — часть действий пользователь подтверждает
  вручную; отказ политики — не сбой и не повод искать обходной путь.
- **Инструменты** — передаются только включённые, выключенный вызвать
  нельзя, надо назвать его и попросить включить, а не выдумывать результат.
- **Навыки** — что это и что привязка инструментов сама ничего не включает.
- **Контекст** — окно ограничено, начало истории отбрасывается штатно;
  это не забывчивость модели, и об этом стоит сказать прямо.
- **Момент смены модели** — действует со следующего запроса.
- **Файлы** — не читать по своей инициативе.
- **Изменение самого агента** — созданный или изменённый инструмент
  сохраняется выключенным, включение — решение пользователя.
- **Честность** — не выдавать предположение за результат, не заявлять о
  выполненном действии при ошибке инструмента, спрашивать вместо догадок.

Неотключаемыми сделаны и четыре инструмента, на которых эти механизмы
держатся: **`persistent_memory`** (память), **`ask_user`** (спросить, а не
угадать), **`explain_agent`** и **`diagnose`** (объяснить устройство и
найти причину странного поведения). Набор выбран по одному правилу: только
локальные инструменты, которые ничего не разрушают и не ходят в сеть.
Поэтому в него не попали ни `http_fetch`, ни `create_tool` — что бы ни
говорил системный навык, эти двери остаются под контролем пользователя.

Побочный эффект: `ask_user` был выключен по умолчанию и теперь включается
у всех. Это осознанно — без него агент не может задать уточняющий вопрос,
а системный навык прямо велит спрашивать вместо догадок.

Запрет держится на четырёх рубежах, а не на одном `disabled` у чекбокса:
тумблер в интерфейсе заблокирован и вдобавок отбивает попытку снять
`disabled` через DevTools; `update_skill`/`update_tool` отказывают модели с
объяснением; `loadSkills`/`loadTools` на КАЖДОЙ загрузке возвращают флаг и
включённое состояние (в старых базах эти записи уже есть и могли быть
выключены до появления запрета); `buildSystemPrompt` добавляет системный
навык в промпт независимо от флага в записи и ставит его первым.
Переключатель папки в дереве Tools системные инструменты не считает и не
трогает — иначе он навсегда застрял бы в промежуточном состоянии.

## Цикл 31. Запросы через локальный прокси (`proxy_fetch`)

В папке `proxy/` появился отдельный Node-процесс, который пользователь
запускает сам: `proxy.js` + `config.js`. Он принимает запрос из браузера
(`?url=<цель>` или заголовок `X-Target-Url`), ходит к цели и возвращает
ответ как есть, с `Access-Control-Allow-Origin: *`. Плюс режим SSO
(`?sso=1` / `X-Use-Sso: 1`): вместо `http`/`https` запрос выполняет
`curl --ntlm --negotiate -u :`, то есть с доменными правами текущего
пользователя Windows через SSPI. Свои границы у прокси тоже есть —
`config.allowlist` и лимиты размеров.

Под него сделан инструмент **`proxy_fetch`**. Параметры и описание
согласованы отдельно, до реализации.

### Что выяснилось при чтении прокси

Две вещи, которые определили форму инструмента:

1. **Произвольные заголовки через браузер не пройдут.** В `setCors()`
   список `Access-Control-Allow-Headers` фиксированный: `Content-Type,
   X-Target-Url, Authorization, X-Custom-Headers, X-Use-Sso`. Заголовок с
   другим именем браузер срежет на preflight — до прокси он не дойдёт.
   Поэтому инструмент принимает только `Content-Type` и `Authorization`, а
   на остальные ОТВЕЧАЕТ ОШИБКОЙ с объяснением, вместо того чтобы молча их
   выбросить: молчание означало бы, что модель считает `Authorization`
   отправленным и объясняет 401 чем угодно, кроме настоящей причины.
2. **`X-Custom-Headers` в прокси не реализован.** Он есть в списке
   разрешённых, но `proxy.js` его не разбирает — пересылает цели дословно.
   Задуманный «конверт для остальных заголовков» не работает, и опираться
   на него нельзя.

### Параметры

`url` (обязательный), `method` (GET/POST/PUT/DELETE/PATCH/HEAD),
`body`, `headers`, `sso`, `max_chars`.

Адрес самого прокси в параметрах **отсутствует намеренно** — только из
настроек. Иначе модель могла бы назвать «прокси» любой хост и отправить
туда тело и заголовки, включая `Authorization`.

Целевой адрес назван именно `url`, а не `target`, не случайно:
`SecurityEngine._hostOf()` читает `args.url`, поэтому политика
подтверждений и белый список доменов видят **хост цели**, а не
`localhost:3000`. Назови параметр иначе — и вся сетевая политика
проверяла бы адрес прокси, то есть ничего.

### Границы

Приватные адреса через `proxy_fetch` РАЗРЕШЕНЫ — ради интранета
инструмент и нужен, и `_isBlockedFetchHost` (защита `http_fetch`) здесь не
применяется. Модель доверия другая: канал открыл сам пользователь,
запустив процесс и указав его адрес, а у процесса есть свой allowlist.

Запрещённым осталось одно: link-local и cloud-metadata
(`169.254.0.0/16`, `fe80::/10`) — отдельная проверка
`_isBlockedProxyTarget`. Полезного применения у них здесь не бывает, а
«сходи по 169.254.169.254» — классический способ вытащить учётные данные
облачной машины текстом, подставленным в контекст.

### SSO: разрешение и подтверждение

Флаг необязательный, по умолчанию `false`. Два рубежа сверху:

- **Настройка.** `settings/proxy.allowSso`, по умолчанию выключена. Пока
  не включена, вызов с `sso: true` отклоняется до отправки запроса.
- **Подтверждение всегда.** Правило стоит в `SecurityEngine.check()` ДО
  всего остального, включая `if (this.mode === 'off')`. Причина не в
  категории операции, а в том, чем платят за ошибку: запрос уходит с
  доменными правами пользователя, а адрес выбирает модель — в том числе
  под влиянием текста из внешнего источника. Поэтому нет ни режима,
  который разрешает это молча, ни «больше не спрашивать про этот адрес»:
  в вердикте выставлен `noRemember`, и диалог подтверждения (ui-chat.js)
  по этому флагу прячет галочку и пишет, что спрашивать будут каждый раз.
  Ранее одобренный хост (`approvedHosts`) правило тоже не отменяет —
  проверка стоит раньше.

### Развод с `http_fetch`

Два независимых инструмента, без автоматического фолбэка: молча подменять
канал, у которого есть режим SSO, — плохая идея. Правило выбора вписано в
описания обоих (`http_fetch` — первый выбор для публичного интернета, при
CORS/запрете адреса/нужде в методе-теле-заголовке-SSO → `proxy_fetch`) и
подробно разложено в новом навыке **«Работа через прокси»** (выключен по
умолчанию), к которому привязаны оба инструмента. Навык, помимо правила
выбора, запрещает ставить `sso: true` «на всякий случай, проверить» и
требует сначала убедиться, что сервер действительно просит NTLM/Negotiate.

`proxy_fetch` — встроенный, но **выключен по умолчанию** и НЕ системный
(не `locked`): пока прокси не запущен и адрес не задан, включать его
нечего, а сетевой канал с режимом SSO должен оставаться под тумблером
пользователя. По тому же правилу, по которому в системный набор Цикла 30
не попали `http_fetch` и `create_tool`.

### Настройки

Новый блок в 🛡 Безопасность → «Локальный прокси»: адрес, разрешение SSO,
предел ответа в символах (по умолчанию 8000 — прокси умеет отдавать
мегабайты, а большой ответ вытесняет из контекста историю переписки) и
кнопка «Проверить». Проверка берёт адрес из ПОЛЯ, а не из сохранённых
настроек: иначе «проверить» означало бы «сохрани, закрой, открой снова».
Хранится в `settings/proxy` — отдельным ключом, а не внутри `security`,
чтобы не смешивать политику подтверждений с настройкой канала.
Инструмент читает эти настройки из БД на каждый вызов: пользователь может
поменять их посреди диалога.

### Тесты

Новый `test-proxy-fetch.js` — 54 проверки на переносимых путях,
с подменённым `fetch`, который запоминает, что инструмент собирался
отправить: сборка адреса (цель кодируется целиком, вместе со своими

подтверждение в режиме `off`, `noRemember`, бессилие `approvedHosts`.
Плюс проверка, что диалог включения инструментов навыка (Цикл 30)
предложит для нового навыка именно `proxy_fetch`.

Итого 302 проверки в семи наборах (после Цикла 32 — 333).

## Цикл 32. Генератор прокси, консолидация ограничений, поиск в списках, неприкосновенность системного навыка

### 1. Генератор файлов прокси

Прокси — отдельный процесс, и до сих пор его файлы нужно было добывать
самому. Кнопка «📦 Сгенерировать файлы прокси» (⚙ Настройки →
Безопасность) открывает форму — порт, белый список хостов, разрешённые
методы, размеры, параметры curl для SSO — и собирает комплект:
`config.js` с подставленными значениями, `proxy.js` и скрипты запуска
`start-proxy.bat` / `start-proxy.sh`. Файлы предлагается сохранить в одну
папку (`showDirectoryPicker`), а если браузер этого не умеет или выбор
сорвался — скачиваются по одному. Заодно предлагается прописать
`http://localhost:<порт>` в настройки агента.

Два решения, которые стоит объяснить:

- **`proxy.js` не хранится копией внутри приложения.** Он забирается
  `fetch('proxy/proxy.js')` с того же адреса, откуда открыта страница, а
  сборка кладёт `proxy/` и в `dist/`. Встроенная копия 470 строк рано
  или поздно разошлась бы с оригиналом в репозитории, и пользователь
  получал бы прокси, отличающийся от того, что читает разработчик. Если
  `proxy.js` недоступен, генератор честно об этом говорит и отдаёт
  остальное. (В Цикле 33 копия в `dist/` стала обфусцированной — см. там же
  про последствия.)
- **`config.js` генерируется с комментариями**, а не голыми значениями:
  этот файл правят руками после генерации, и через месяц `allowlist: []`
  без пояснения читается как «здесь ничего не нужно».

`.bat` пишется с CRLF и `pause` в конце (иначе окно закрывается раньше,
чем видна причина падения), `.sh` — с шебангом и LF; оба сначала
проверяют наличие `node` в PATH.

### 2. Ограничения: три числа про одно и то же

Проверка настроек на повторы нашла три проблемы.

**Предел ответа существовал в трёх видах.** Своя настройка у MCP
(100 000), своя у прокси (8000) и зашитые 4000 внутри `http_fetch` —
при одном и том же смысле «сколько чужого ответа пустить в контекст».
Сведено к одной настройке `maxToolResponseChars` (⏱ Ограничения,
20 000 по умолчанию), которую спрашивают все три канала. У MCP она
по-прежнему означает «отклонить ответ целиком» (обрезанный JSON — мусор),
у остальных — обрезку, но ЧИСЛО одно.

**Таймаут существовал в двух.** `limits.toolTimeoutSeconds` применяется
в `executeTool` ко всем инструментам, включая MCP, а `mcpLimits.
timeoutSeconds` — внутри MCP-клиента. Для MCP-вызова работали оба, и
срабатывал меньший. Свой `AbortController` у MCP остался (общий таймаут
отпускает ожидание, но не разрывает соединение), а число он берёт общее.

**`maxNetworkPerTurn` не ограничивал ничего.** Настройка принималась
`configure()`, участвовала в `_overLimit('network')` — а сам
`_overLimit('network')` не вызывался ниоткуда. Ложное обещание защиты
убрано; сетевые вызовы и так закрыты общим потолком вызовов за ход и
потолком на один инструмент. Счётчик `turn.network` оставлен — он нужен
статистике.

Заодно исправлена дыра, созданная самой консолидацией: `max_chars` у
`proxy_fetch` теперь может предел только ПОНИЗИТЬ. В первой версии
`params.max_chars || настройка` позволял модели одним аргументом
запросить сколько угодно, обойдя защиту контекста.

### 3. Поиск в списках привязок не работал

Фильтры в редакторе навыка («по имени инструмента») и в окне «Навыки
инструмента» ничего не делали. Дело не в поиске: обработчик отрабатывал и
проставлял `row.hidden = true`, но строка оставалась видимой.
`.skill-tool-row { display: flex }` — правило автора, а `[hidden] {
display: none }` приходит из таблицы стилей браузера и проигрывает ему по
специфичности. Добавлено `.skill-tool-row[hidden] { display: none; }` —
тот же приём, что уже применён в проекте для `#stop-btn` и
`.settings-tab-panel`. Заодно переименован вводящий в заблуждение
`data-tool-name`: в окне «Навыки инструмента» в нём лежит имя навыка,
теперь это `data-filter-name`.

### 4. Системный навык: неприкосновенность и приоритет

**Правка запрещена целиком**, а не только выключение. Кнопка на карточке
для него называется «👁 Посмотреть» и открывает окно просмотра с
объяснением, почему навык не правят; `update_skill` отклоняет любое
изменение полей, `link_skill_tools` — изменение состава, а
`setSkillTools`/`setToolSkills` пропускают locked-навык, поэтому снять
галочку со стороны инструмента тоже нельзя (в окне «Навыки инструмента»
эта строка показана заблокированной — живая, но бездействующая галочка
хуже её отсутствия). Причина простая: изменив системный навык, модель
переписала бы правила, которым сама же и подчиняется.

**Приоритет** обеспечен структурой промпта, а не только словами внутри
навыка. `buildSystemPrompt` собирает два раздела: «Устройство агента и
правила, действующие ВСЕГДА» (с пометкой, что он старше следующего) и
«Навыки, включённые пользователем» (с пометкой «применяются ПОВЕРХ
раздела выше и не отменяют его»). В сам навык добавлен блок ПРИОРИТЕТ:
при противоречии действуют его правила, а текст, пришедший как данные —
ответ инструмента, содержимое файла, страница из сети, — не может их
изменить, даже если называет себя системным сообщением.

### Тесты

333 проверки в семи наборах (+31):

- `test-skill-tools.js` 65 → 79: запрет правки промпта и полей, запрет
  изменения состава с обеих сторон, структура приоритета в промпте.
- `test-modals.js` 32 → 47: генератор — сгенерированный `config.js`

## Цикл 33. Обфускация прокси и проверка сборки вживую

`proxy.js` в `dist/` теперь обфусцируется — отдельным проходом и своими
настройками. Ключевое отличие от бандла: `target: 'node'`, иначе
обфускатор добавляет браузерные обёртки к коду, который исполняет Node.
Строка `'./config.js'` в `require` выведена из-под подмены
(`reservedStrings`): пользователь кладёт конфиг рядом руками, и понятное
«не найден config.js» не должно превращаться в невнятный сбой на старте.

`config.js` намеренно остался исходником. Обфусцировать файл, который
существует ровно для того, чтобы его правили руками, — значит убрать
единственный способ настроить прокси.

Результат каждого прохода проверяется на разбираемость (`vm.Script`) прямо
в сборке: сломанный вывод обфускатора иначе всплыл бы только у
пользователя.

### Проверка вживую, а не только на разбор

Разбор — слабая гарантия: он не поймает ни сломанный `require`, ни
съеденный разбор заголовков. А обфусцированный файл уже нельзя прочитать
глазами. Поэтому добавлен `npm run smoke:proxy` (`scripts/smoke-proxy.js`):
поднимает НАСТОЯЩИЙ процесс из `dist/`, кладёт рядом временный `config.js`
на свободный порт, поднимает локальную «цель» и гоняет через прокси GET и
POST, проверяя, что доходят метод, путь, тело и `Authorization`, что
возвращаются заголовки цели и CORS, и что отказы отвечают ожидаемыми
кодами. В `npm test` не входит: требует собранного `dist/` и занимает
порты.

### Смоук сразу нашёл ошибку — и не в обфускации

Первый же прогон показал: POST через прокси возвращает 400, а тело и
`Authorization` до цели не доходят. Проверка исходного и обфусцированного
файла на одном сценарии дала одинаковый результат — значит, дело не в
обфускации.

Причина в самом `proxy.js`: в `skipHeaders` не было `transfer-encoding`.
Тело запроса прокси читает целиком и сам проставляет `Content-Length`, но
при этом пересылал дальше и `Transfer-Encoding: chunked` от клиента — то
есть отправлял запрос, где длина тела задана двумя способами сразу. Node
такие отвергает, клиент получает 400 без пояснений. Ошибка пряталась за
поведением браузера: для строкового тела он ставит `Content-Length`, и
через `proxy_fetch` всё работало, — а http-клиент Node по умолчанию шлёт
chunked и воспроизводит проблему с первой попытки. Показательно, что в
ответе те же hop-by-hop заголовки уже вычищались: сторону запроса просто
пропустили.

После исправления смоук проходит целиком — 16 проверок.

## Цикл 34. Сертификаты внутренних серверов

Пользователь сообщил: прокси возвращает 502 из-за проверки SSL-сертификата,
и попросил добавить возможность её отключать.

Отключение — правильный ответ только на часть случаев, поэтому сделано три
уровня, а не один рубильник:

- `tls.caFile` — путь к PEM с корпоративным CA. Проверка ОСТАЁТСЯ
  включённой, Node просто узнаёт про ваш центр. Это и есть настоящее
  решение задачи «внутренний сервер с корпоративным сертификатом», а не
  обход её.
- `tls.insecureHosts` — снять проверку у перечисленных хостов. Компромисс,
  когда до CA-файла не добраться: остальные адреса остаются защищёнными.
- `tls.insecure` — снять везде. То, о чём просили; оставлено крайним
  вариантом с красным предупреждением при старте, потому что отключает
  защиту от подмены сервера и на внешних адресах тоже.

Все три действуют и на обычный путь (`ca`/`rejectUnauthorized` у
`https.request`), и на SSO через curl (`--cacert`/`-k`). Иначе получилось
бы, что один и тот же адрес работает в одном режиме и падает в другом —
ровно та несогласованность, которую пришлось бы отлаживать вслепую.
Прежний `sso.insecure` продолжает работать: старые config.js не ломаются.

### Ошибку теперь можно прочитать

Отдельная часть проблемы была не в самой проверке, а в том, что о ней
нельзя было догадаться. Обработчик схлопывал любой сбой соединения в
`502 Error contacting the target server: <текст Node>`; чтобы понять, что
дело в сертификате, нужно было знать, как выглядят коды OpenSSL.

Теперь коды (`DEPTH_ZERO_SELF_SIGNED_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`,
`CERT_HAS_EXPIRED`, `ERR_TLS_CERT_ALTNAME_INVALID` и прочие) переводятся в
понятную фразу, а ответ 502 содержит `tlsError: true`, код и три готовых
варианта решения — в том же порядке, от правильного к крайнему.
`proxy_fetch` распознаёт такой ответ и отдаёт модели ошибку с пометкой, что
править нужно `config.js` прокси и перезапустить его, а не искать обходной
путь другим инструментом.

Генератор файлов прокси получил соответствующие поля, иначе свежесозданный
`config.js` не помогал бы против той самой ошибки, из-за которой всё
затевалось.

### Тесты

Смоук вырос с 16 до 28 проверок и теперь выпускает НАСТОЯЩИЙ самоподписанный
сертификат (openssl, на время прогона, в репозитории ничего не остаётся) и
поднимает на нём https-цель. Проверяется всё: неизвестный сертификат
отвергается и объясняется, с `caFile` запрос проходит, исключение по хосту
снимает проверку только своему хосту, глобальное отключение работает и
сопровождается предупреждением. Если openssl недоступен, блок пропускается —
это проверка сборки, а не повод уронить её на чужой машине.

В обычных наборах: `test-proxy-fetch.js` 55 → 61 (разбор ошибки сертификата
инструментом, включая то, что прочий 502 за неё не выдаётся),
`test-modals.js` 47 → 53 (раздел tls в сгенерированном config.js). Итого 345
проверок в семи наборах плюс 28 смоук.

## Цикл 35. Внутренние вики: Confluence и xWiki

Два набора инструментов к корпоративным вики-системам (On-Premise) и по
навыку на каждый: Confluence через персональный токен (Bearer), xWiki через
Basic-авторизацию. По семь инструментов в наборе — настройка доступа,
проверка связи, список пространств, поиск, чтение, создание и правка
страницы.

Оба набора делят транспорт: адреса внутренние, CORS у таких систем закрыт,
поэтому запросы идут через локальный прокси (Цикл 31), если он настроен, и
напрямую, если нет. Сбой сертификата от прокси (Цикл 34) доносится
разобранным, с вариантами решения.

### Где хранить учётные данные

Просьба была «сохранять в долговременную память». Буквально — это
`persistent_memory`, и туда класть их нельзя: эта память читается моделью
(`persistent_memory read/list`), поэтому токен попал бы в контекст диалога,
а оттуда — в каждый следующий запрос к провайдеру модели и в его логи.
Системный навык (Цикл 30) прямо запрещает класть в память ключи и пароли.

Суть просьбы при этом выполнена полностью: данные сохраняются в БД
(`settings/wiki_confluence`, `settings/wiki_xwiki`), переживают перезапуск,
и повторно агент их не спрашивает. Секрет шифруется `SecretsVault` — тем
же механизмом, что ключи провайдеров и токены MCP-серверов — и не
возвращается ни одним инструментом: наружу идут только адрес, имя учётной
записи и признак «настроено».

### Почему секрет вводится в форме, а не через ask_user

Соблазнительно было бы дать агенту спросить токен через `ask_user`: коротко
и «агент сам запрашивает у пользователя», как и просили. Но ответ
`ask_user` — это результат вызова инструмента, то есть часть истории
диалога: токен уехал бы провайдеру модели при первом же следующем запросе
и остался бы в переписке навсегда.

Поэтому `*_configure` открывает форму интерфейса (как подключение
MCP-сервера), и значение уходит из поля прямо в шифрованное хранилище.
Агент инициирует запрос данных, но самих данных не видит — он получает
«настроено, адрес такой-то». В описания инструментов и в оба навыка
добавлено прямое: НИКОГДА не проси прислать токен или пароль сообщением и
не принимай их текстом.

### Категории безопасности

Чтение помечено `read`, запись — `write`, а не `network`, хотя запрос и
уходит наружу. Категория `network` существует ради случая, когда адрес
выбирает МОДЕЛЬ (`http_fetch`) — там нужен вопрос про каждый хост. Здесь
адрес задан пользователем в настройках и модели неподконтролен, а вот
потолок изменений за ход для создания страниц — как раз по делу.

### Правка как отдельный риск

`*_update_page` заменяет содержимое страницы целиком, поэтому это выделено
и в описании инструмента, и в навыке: прочитать текущую версию, показать
пользователю правку, дождаться согласия. Номер версии Confluence инструмент
берёт с сервера сам — если бы его подставляла модель, она бы его выдумала,
и правка молча уходила бы в конфликт. `xwiki_create_page` намеренно
откажется трогать существующую страницу и подскажет `xwiki_update_page`.

Чтение возвращает текст без разметки (таблицы и макросы теряются), и навык
требует говорить об этом прямо, а не додумывать их содержимое.

### Тесты

Новый `test-wiki.js` — 45 проверок с фейковой вики, которая запоминает
запросы. Главное, за чем они следят, — не «запрос собрался», а что секрет
не течёт: в БД лежит шифротекст, `*_status` его не отдаёт, в тексте ошибки
401 его нет. Плюс: Bearer у Confluence и Basic у xWiki собираются верно,
маршрут переключается на прокси при его настройке, номер версии берётся с
сервера и увеличивается на единицу, создание существующей страницы в xWiki
отклоняется с подсказкой, категории безопасности расставлены, а диалог
включения навыка предложит именно инструменты этого набора.

Итого 390 проверок в восьми наборах плюс 28 смоук.

## Цикл 36. Решение задач по частям: экономия контекста и устойчивость к сбоям

Одна выкачанная страница на 150 КБ навсегда занимала десятки тысяч токенов,
цепочка из двадцати вызовов ехала в модель на каждом следующем шаге, а
вытесненное начало переписки просто исчезало. Всё это упиралось в одно:
работа агента жила исключительно в переписке, и другого места для неё не было.
Цикл добавляет четыре таких места — плюс журнал, переживающий сбой.

### Артефакты: большие результаты вне переписки

Раньше результат вызова целиком уходил в сообщение `role:'tool'` и с этого
момента отправлялся модели в КАЖДОМ следующем запросе хода. Перечитывать его
никто не просил — платили за него всегда.

Теперь результат крупнее порога (`artifactThresholdChars`, по умолчанию 2000)
сохраняется в новом хранилище `artifacts`, а в переписку идёт шапка: чем
получено, размер, структура (`JSON-объект, ключи верхнего уровня: items(50)…`),
начало текста и идентификатор. Дочитывает модель сама — `artifact_read`,
`artifact_grep`, `artifact_list`.

Две детали, без которых механизм работал бы хуже, чем задумано. Первая: если у
результата есть доминирующее строковое поле (больше 60 % объёма — `body` у
`http_fetch`, `text` у `read_file`), в артефакт уходит только оно, а `status` и
`url` остаются в шапке: прятать то, что стоит копейки и нужно сразу,
бессмысленно. Вторая: результаты самих `artifact_*` в артефакты не выносятся —
иначе чтение куска артефакта плодило бы новый артефакт, и модель ходила бы по
матрёшке вместо данных.

Инструменты сделаны системными (`locked`): подмена результата происходит
автоматически, и если бы читать артефакт было нечем, экономия контекста
превратилась бы в потерю данных.

### Подзадачи: часть работы отдельным ходом

`run_subtask` выполняет кусок задачи в отдельном чате с чистым контекстом и
возвращает в основной разговор только итог. Это единственный из четырёх
механизмов с асимптотическим эффектом: стоимость подзадачи для родительского
контекста постоянна и не зависит от того, сколько шагов она заняла.

Цикл подзадачи написан отдельно от `_generateResponse`, и это осознанно: тот
цикл связан с интерфейсом чата — стриминг в DOM, панель статуса, состояние
занятости, набор `_chatRuns`, где ход на чат ровно один. Подзадача же
выполняется ВНУТРИ хода родителя, то есть когда его `run` активен. Цикл в
`ui-subtask.js` не трогает DOM вовсе: пишет сообщения в базу и возвращает
значение, а видимой частью остаётся один статус в родительском чате.

Границы: вложенные подзадачи запрещены (список инструментов подзадачи не
содержит `run_subtask`); бюджет времени хода принадлежит родителю и проверяется
внутри цикла — его таймер рвёт родительский запрос, но не запрос подзадачи, у
которой свой `AbortController`; кнопка останова теперь рвёт и его. Модель
подзадачи применяется прямо перед запросом, а после возвращается родительская —
шлюз общий на приложение. Расход токенов пишется в статистику под-чата, а не
родителя: иначе одни и те же токены считались бы дважды.

Переписка подзадачи скрыта из списка чатов (агент заводит их десятками), но не
спрятана: в блок вызова добавлена кнопка входа, а внутри — плашка с возвратом.
Удаляется вместе с родительским чатом и своими артефактами.

### План задачи вне переписки

`task_plan` хранит цель, шаги, их состояние и попутные факты в новом хранилище
`tasks`. Компактная сводка подставляется в системный промпт при каждом запросе,
поэтому состояние длинной работы больше не зависит ни от подрезки истории, ни
от перезагрузки страницы.

Решения по мелочам, каждое — ответ на конкретную неприятность: один активный
план на чат (два плана означали бы два ответа на вопрос «что дальше», и агенту
пришлось бы выбирать); одновременно «в работе» только один шаг (иначе сводка
перестаёт отвечать на вопрос «чем ты занят сейчас»); план закрывается сам,
когда закрыты все шаги (иначе напоминал бы о законченной работе в каждом
запросе); в `result` кладётся то, что переживёт шаг, — путь, идентификатор,
вывод, а не пересказ работы. Действий у инструмента девять, но инструмент один:
описания уходят в каждый запрос, и девять почти одинаковых стоили бы дороже
самого плана.

### Свёртка контекста вместо потери начала

Раньше `_trimHistory` выбрасывал не поместившееся начало и вставлял заглушку
«попроси пользователя повторить». То есть принятые решения, найденные пути и
выясненные ограничения для агента исчезали, и дальше он либо переспрашивал уже
отвеченное, либо действовал по догадке.

Теперь вытесняемая часть один раз прогоняется через модель и превращается в
структурированное резюме (задача, сделанное, выясненное, решения, открытые
вопросы), которое сохраняется сообщением `kind:'context-summary'` и дальше
едет в запросы ВМЕСТО покрытых сообщений. Метка времени резюме ставится на
границе покрытой части, поэтому при сборке контекста понятно, что именно оно
заменяет, и за одно и то же не платят дважды. Промпт свёртки требует приводить
значения точно, а не приблизительно: именно за ними к резюме и возвращаются.

Свёртка стоит одного запроса, поэтому делается только при реальном
переполнении; если она сорвалась (сеть, отказ провайдера) — работает прежнее
поведение, ответ не срывается. Пользователь видит свёрнутую часть в переписке
и может её раскрыть.

Отдельно и без всякой модели: старые результаты инструментов (кроме последних
шести) уходят в запрос сокращёнными до 400 символов, с пометкой, где взять
полный текст. Они почти всегда уже отработаны, но ехали целиком в каждый запрос.

### Устойчивость к сбою и возобновление

Ход агента жил только в памяти вкладки. Закрытая вкладка, обновление страницы
или падение браузера обрывали работу молча: недописанный ответ пропадал.
Отдельная беда — обрыв посреди цепочки инструментов: в истории оставался вызов
без результата, а такой запрос провайдер отвергает целиком, и чат становился
нерабочим совсем, без всякой возможности исправить это из интерфейса.

Добавлено хранилище `runs` — журнал активного хода: стадия, номер шага, модель
и накопленный текст ответа. Пишется не чаще раза в полторы секунды: запись на
каждый токен заметно тормозила бы стриминг. Сбой самого журнала не роняет ход —
его операции логируются, но наружу не пробрасываются.

При запуске ходы, оставшиеся в состоянии «выполняется», разбираются:
недописанный ответ сохраняется в переписку с пометкой «прерван», незакрытые
вызовы получают честный результат «выполнение прервано» (цепочка снова
валидна), а в чате появляется предложение продолжить с указанием стадии, на
которой всё оборвалось. Та же починка идёт перед обычной отправкой сообщения —
чтобы чат, испорченный старым сбоем, чинился сам собой.

Возобновление не создаёт нового сообщения пользователя: агент продолжает с уже
имеющейся истории, включая результаты успевших выполниться инструментов. Само
оно не запускается намеренно: автоматический перезапуск в момент открытия
страницы повторил бы действие, из-за которого всё и упало, и потратил бы деньги
на ход, который может быть уже не нужен. Плюс `beforeunload` предупреждает при
